# Critique: decisions D50, D51, D52 (preview2 Feature 8)

Verdicts: D50 REVISE · D51 REVISE · D52 REVISE

## D52 — stubs (the most damaging; it rests on a wrong premise)

Blockers
1. D52 and D47 reverse the only precedent the human pointed at. The reference repo keeps rules FULL and the standard points to the rule (8.1.2 hand-back:16-17: weighingms `coding-standards.md:3` "The enforceable guardrails live in `.claude/rules/*.md` ... This file points to them"). Design note weighingms memory-bank.md:136: rules are guardrails, standards are technical decisions. The orchestrator's own run.v2.md:99 records this as "opposite of D47". The decision was made while the evidence said otherwise, and the human was not shown that.
   Fix: invert D52. Rules stay full in `.claude/rules/` and `.github/instructions/`; the standard is a short catalog entry that links to the rule.
2. Enforcement is unverified and is the whole point of a rule. 8.1.2:36 states it did not verify whether Claude Code or Copilot follow a relative link or @-import inside a rule file; 8.1.5 is still in-progress. A stub with "see `.forgeline/...`" loads ~3 lines. The model then has to choose to Read the target. A path-scoped rule (`paths: ["**/*.cs"]`) exists precisely so the content arrives at edit time without the model choosing. A stub turns a guaranteed load into a hope. Do not move any rule body until 8.1.5 returns with a vendor-doc citation for both hosts.
3. docs-status cannot be a stub. It has no `paths:`/`applyTo: "**"` (8.1.2:22) and is loaded every session, so a stub saves zero tokens and adds a hop. It also binds every agent and is installed into every consumer repo by `docs-rules` (SKILL.md:20-29). Exempt always-on rules explicitly.

Major
4. "A rule can be Claude- or Copilot-specific" (D52's reason) is not a reason for stubs. Repo evidence is the opposite: `init` requires identical bodies with only frontmatter differing (init SKILL.md:173), and `sync-harness` treats any body difference as drift (sync-harness.mjs:182, 327-335). Host-specific content in one standard is a smell, not a feature. If the human really has Claude-only rules, say which. None exist today.
5. Twin drift risk is real and new. A stub written to one twin only is drift and the newer file wins (sync-harness.mjs:78-81, 218-220). Stubs must be generated identically, and every consumer-installed template (`docs-rules`, `dotnet-rules`, `node-rules`) would change what `init` installs everywhere. That is plugin-code change, not a layout tweak.
6. Pointers to `.forgeline/memory-bank/...` are dead links in any consumer repo that has not migrated. Older installs would keep full rules while new ones get stubs: two behaviours for one plugin version.

Minor
7. Stubs add a hop to every rule edit: `agent-manager` and `documentation-writer` now touch two places per change.

Recommended alternative: weighingms pattern. Rules full and still the enforcement source. `.forgeline/memory-bank/project/standards/*.md` are 5-15 line catalog entries (name, scope, link to the rule, rationale). Add stubs only for a rule proven to need host-specific content, one at a time, after 8.1.5.

## D51 — product/project split of standards

Blockers
1. It contradicts the approved G2 spec and ADR-0013. Spec 001 reserves ONE home: `memory-bank/project/standards/`, key `standards`, optional until 1.0.0 (spec:63, :88, :98). ADR-0013 is "one home per artifact type". D51 creates two homes for one type, with no new key in `ARTIFACT_TYPES` (spec §2.3 fixes 13 keys; the AC-8.1 key-equality test would fail on a 14th). Upstream specsmd is flat `standards/` (8.1.2:4). The product/project split is the team's own invention and is not justified anywhere in the evidence.
   Fix: one home, `.forgeline/memory-bank/project/standards/` (spec already places it there). If licensing/compliance deserve a spot, they are standards entries in the same folder, or product docs under `product/` that are NOT typed "standards".
2. The boundary is undefined. Where do these go: security, accessibility, documentation policy (`docs-status`), testing policy, API conventions, tech stack? D51 names only "licensing, compliance" (product) and "code and architecture" (project). Security and accessibility are both. specsmd's catalog (tech-stack, coding-standards, system-architecture, api-conventions, ux-guide, decision-index) is project-level by definition, so "product standards" would be nearly empty and exist only to be argued about.

Major
3. Authorship is unresolved. ADR-0014 makes `documentation-writer` the single writer of memory-bank; run.v2.md settles that a bank tree counts as documentation. Yet `docs-status.md:17-19` excludes lifecycle artifacts and does not name the bank (8.1.2:28). If standards (agent-governing rules) are bank files, then `agent-manager` edits to rules become findings under docs-status "Reviews". A rules change would need a documentation-writer round for every guardrail tweak. Weighingms assigns standards to software-architect. Decide the writer and add the docs-status clause BEFORE moving anything.
4. `plugin-development.md` is a repo-only maintenance rule, not a "standard". It enforces "do X after every edit" and must stay a rule.

Recommended alternative: single `project/standards/` as in spec 001; catalog entries per D52-alternative; add an explicit clause that standards entries are authored by `software-architect` (or documentation-writer, human's pick) and say which in one line in docs-status.

## D50 — plugin-wide move now

Blockers
1. It contradicts a frozen, human-approved decision: D16 ("`.ai-dlc/` folder and `AI_DLC_*` stay as family names") and ADR-0015:31, :58 ("Rename `.ai-dlc/` ... (D16)" listed as rejected). D46 moves `.ai-dlc/` to `.forgeline/ai-dlc/`, renames `model-metadata` to `models/claude/metadata`, and splits `auto-handoff` and `cache-keepalive` into `cost-saving/`. Fixed names in settings keys, env docs, lens `.ai-dlc/lens.json`, and the managed block markers all assume that family. The run state lists no ADR amendment and no G2 reopening.
   Fix: write an ADR amending ADR-0013/0015 and get the human to reopen G2 for the changed ACs, or reduce scope (below).
2. It pre-empts and collides with the G3 bolt plan. The plan has 14 bolts and a critical path 002 → 004 → 008 → 009 → 010 → 014 → ITEM-121 → 011 (task plan:42). Bolt 002 is the `ARTIFACT_TYPES` resolver and `workflow.mjs`; 011 is the path sweep; 009/010 touch lens paths; ITEM-121 is the dogfood migration that moves THIS repo's docs and settings. D50 does all of this by hand, now, in one change, before the resolver exists, so the code it writes will be thrown away by bolt 002. D9 ("old paths read for one release, with a warning") has no story: after D50, every consumer on preview1 has `.ai-dlc/` and no code reads it. Run.v2.md:120 admits "G3 will need re-planning".
3. Blast radius is not bounded. 8.1.1 is PARTIAL and self-declares it did not sweep `agents/`, most `skills/`, `tests/workflow/`, `tests/model-metadata/`, or the bank link counts (8.1.1:5, :37, :66, :78). Known: `.ai-dlc/` literals in `workflow.mjs`, `check-workflow.mjs`, `update-model-metadata.mjs`, auto-handoff `config.ts:9`, keepalive `keepalive.ts:37`, lens `settings.ts`/`register.tsx`, three test suites with exact-string assertions. `check-workflow.mjs:46` exits 0 silently when `.ai-dlc/workflow.json` is missing, so a half-done move silently disables the workflow gate (8.1.1:16). A change this size in one AAWP round with a team sets up a failure with no sweep to measure against. (Also: 8.1.1's claim that `.ai-dlc/` is absent in this worktree was shown false, run.v2.md:98, so even its "gate inert" conclusion was wrong.)

Major
4. Ordering against the rename: D50 moves paths to `.forgeline/...` while plugin, prefixes, memory folder names (`engine-<agent>`) and the rename bolt 004/005 are not done. Two path migrations stacked on each other double the sweep (bolt 011) and the upgrade-guide story (ITEM-123).
5. The agent-memory exception (D49) is correct, but 8.1.3 itself flags that the host folder may already be `<name>` not `ai-dlc-<name>` (8.1.3:33): a plugin-wide path change is being planned while this live question is open.

Recommended alternative: do NOT move code now. Treat D50 as bolt(s) in the existing plan: (a) now, only the dogfood part for THIS repo with the paths unchanged in code (docs/data moves where the resolver does not matter: `memory-bank/`, `execution-plans/`, `handoffs/` under `.forgeline/` using `artifacts.*` overrides in this repo's `workflow.json`, which workflow.mjs already supports and Feature 6 used for D42); (b) the plugin-wide `.forgeline/ai-dlc/` etc. move becomes a new bolt after bolt 002 (resolver) with a stated migration story for D9 and a `/engine:migrate` map entry, and an explicit human decision reversing D16. Anything that moves hard-coded constants (`config.ts`, `keepalive.ts`, `check-workflow.mjs`, `update-model-metadata.mjs` plus their template twins) goes in one bolt after the full 4-pass sweep that 8.1.1 asked for.
