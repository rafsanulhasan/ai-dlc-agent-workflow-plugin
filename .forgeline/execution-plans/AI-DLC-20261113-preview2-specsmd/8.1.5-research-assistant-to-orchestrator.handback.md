# Research Findings: can pointer stubs load the standards they point to?

## Answer in one line
Not on both hosts. A pure-pointer design (D52 as written) loads the standard on Claude Code only through an unsupported-in-docs `@import` in rule files, and on Copilot not at all. Do not use stubs on the Copilot side; generate full copies instead.

## Findings

Q1. Claude Code `.claude/rules/*.md`
- `@path` imports are documented for CLAUDE.md only. The page says "CLAUDE.md files can import additional files using @path/to/import syntax" [1]. It does not say rule files support them.
- The syntax rules [1]:
  - Relative paths resolve relative to the file containing the import, not the working directory.
  - Maximum depth is four hops.
  - Imports inside Markdown code spans and fenced code blocks are skipped.
  - A path that resolves outside the working directory is an "external import": a one-time approval dialog per project, and if declined the import stays disabled.
- Evidence from an issue report that imports in rule files do work [2]:
  - A rule `.claude/rules/python.md` containing `@../../docs/python-conventions.md` had the target inlined into context.
  - It happened at session start even though the rule had `paths: ["**/*.py"]`, so the `paths:` scope does not gate the import.
  - Reported on Claude Code 2.1.168, reproduced on Linux and macOS, closed "not planned" by the stale bot with no Anthropic response.
  - This is an inference from a bug report, not documented behaviour.
- A dot-folder target (`.forgeline/...`) is not mentioned in the docs or in the issue. Nothing suggests it differs; the rule file itself sits in `.claude/`. Unverified.
- Rule scope [1]:
  - `paths` is the only frontmatter field Claude reads.
  - A rule without `paths` loads at launch, at the same priority as `.claude/CLAUDE.md`.
  - A rule with `paths` loads when Claude Read/Write/Edits a matching file.
- A plain markdown link loads nothing. The issue thread says the agent may not read linked files [2]. The VS Code reference says a link "doesn't guarantee" the content is included [3].
- Symlinks in `.claude/rules/` are supported, with an external-import approval for targets outside the working directory [1]. Windows needs Developer Mode or Administrator, and Git checks a committed symlink out as plain text unless `core.symlinks` is enabled [1].

Q2. GitHub Copilot
- Copilot CLI [4]:
  - It reads `.github/copilot-instructions.md`, `.github/instructions/**/*.instructions.md`, `AGENTS.md`, `CLAUDE.md` and `.claude/CLAUDE.md`, and it does not list `.claude/rules`.
  - `@relative/path` includes another file, and references inside referenced files are followed. It applies only in `copilot-instructions.md`, `AGENTS.md` and `CLAUDE.md`.
  - The page states references are not expanded in `*.instructions.md` or `GEMINI.md`. Referenced files must stay inside the repository; absolute and `~/` paths are not loaded.
  - So an `.instructions.md` stub with `@path` would be inert text on the CLI.
- VS Code [3]:
  - There is no include or import syntax for instruction files.
  - Relative markdown links resolve from the instructions file, but inclusion is not guaranteed. The Local harness has `chat.includeReferencedInstructions`, off by default; other harnesses are not described.
  - The Local harness is deprecated and removed February 2027 [3].
- The documented way to share one body across files: there is none. Docs offer `AGENTS.md` / `copilot-instructions.md` / `CLAUDE.md` as shared project files, and these are the only places the CLI expands `@` [3][4].
- GitHub.com (cloud agent / code review) [5]:
  - It supports path-specific `*.instructions.md` with `applyTo`, plus `excludeAgent`.
  - The page says nothing about links or imports.

Q3. Alternatives
- (a) Claude `@import` stub in the rule, full Copilot copy [1][2][4]:
  - Loads the standard on Claude.
  - If the rule has `paths`, the import loads eagerly anyway, so scoping is lost and the body costs context in every session.
  - If the rule has no `paths`, it loads at launch, which is correct behaviour.
  - Copilot side needs a full body (see recommendation).
- (b) VS Code `chat.instructionsFilesLocations` [3][6]:
  - It is a map of folder path to boolean. The defaults include `.github/instructions` and `.claude/rules`.
  - The docs do not state the format for arbitrary or relative dot-folders. Not verified.
  - Copilot CLI and the Copilot app do not inherit it [3]. This is VS Code only, so it is not a cross-host solution. It is also a per-user setting unless committed in workspace settings.
- (c) Copilot CLI `COPILOT_CUSTOM_INSTRUCTIONS_DIRS` [4]:
  - It adds `AGENTS.md` and `*.instructions.md` from the listed directories.
  - Recursion and `applyTo` handling in those directories are undocumented.
  - It is an environment variable, so every contributor must set it. Subagents do not inherit directories loaded only through it [7].
- (d) CLAUDE.md imports [1]:
  - They load eagerly at launch (documented, depth 4), so the whole standards folder would always be in context.
  - They give up per-file `paths` scoping.
  - They suit small, always-on standards only.
- (e) Generated full copies [1][4]:
  - A script writes `.claude/rules/<n>.md` and `.github/instructions/<n>.instructions.md` from `.forgeline/memory-bank/project/standards/<n>.md`, adding front matter.
  - Both hosts get working, scoped, self-contained files with no host feature dependency.

Q4. Repo fit: `.claude/scripts/sync-harness.mjs` (read in full)
- The rules pair walks `.claude/rules/**/*.md` against `.github/instructions/**/*.instructions.md` (lines 472-475).
- Drift is defined by `ruleDiffers` (lines 331-335): different `description`, different scope (`paths`/`globs` vs `applyTo`, `**` and `**/*` normalised equal), or a different body after trimming leading and trailing whitespace (`sameBody`, line 182).
- An `@import` stub on the Claude side with a different body on the Copilot side therefore counts as drift. Both sides are rewritten from the newer file (`winner`, lines 78-81), and the stub is overwritten with the full body or the reverse, with no `--check` pass.
- Two stubs identical to each other would not drift, but the Copilot stub would be inert text (Q2).
- `walk` skips dot-prefixed names (line 65), which covers subfolders of the rules directories. The script never reads `memory-bank/` or `.forgeline/`, so generated files appear to it as ordinary twin sources.
- Consequence: option (a) needs a sync-harness exemption, which is an `agent-manager` change.

## Recommendation
Option (e). Keep `.forgeline/memory-bank/project/standards/*.md` as the single source and generate both twins as full, byte-identical bodies:
- Front matter on the Claude file: `paths`, or none for always-on.
- Front matter on the Copilot file: `applyTo` and `description`.
- `sync-harness` then sees no drift, because the bodies match.
- Add a generator `--check` to CI beside the existing sync check, and mark the files "generated from <standard>; do not edit".
- Run the generator before `sync-harness`, as the existing Stop hook chain already orders the build before the check.

Fallback if D52 insists on pointer stubs on Claude:
- Use an `@import` stub only in rules without `paths`.
- Copilot still needs full copies.
- `sync-harness` must be taught to skip or compare that pair, since the bodies differ by design.

Do not use stubs for path-scoped Claude rules, because the import ignores `paths:` [2].

## Confidence
Medium-High on Copilot CLI (official GitHub docs, explicit text), Claude CLAUDE.md imports and rules scoping (official docs), and the sync-harness behaviour (script read in full). Medium-Low on `@import` inside rule files: it rests on one unmaintained, closed issue report, not the docs, and could change in a Claude Code release. These docs pages move quickly, so re-verify before building.
