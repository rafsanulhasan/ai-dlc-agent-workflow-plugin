`claude plugin test` runs the hooks module tests with types stripped, so a type error passes. To check types (2026-10-22, run AAW-20261022-auto-handoff-chain): copy `types/claude-code.d.ts` from the `plugin-authoring` skill's bundled folder (under the temp `claude/bundled-skills/<version>/<hash>/plugin-authoring/`) into `.scratch/<task>/tc/`, add a tsconfig listing it plus the module files (`strict`, `lib: es2023`, `allowImportingTsExtensions`, `jsxImportSource: claude-code`), and run `npx -p typescript@5 tsc -p`. Ignore TS2875 (no jsx-runtime types); since 2026-10-22 the `session.usage` mock returns `as never`, so no other error is expected. The live window run used this setup in `.scratch/window-observability/tc/`.

`tools/build-copilot.mjs` copies every plugin skill to Copilot except those listed in `tools/claude-only-skills.json` (since 2026-10-23: `cache-keepalive`, `cache-keepalive-install`, `-merge`, `-configure`). A Claude-only skill still copied (e.g. `configure-auto-handoff`) says on its first lines that it does not apply on Copilot and stops; listing it is the alternative.

**Why:** `plugin test` and CI never check the module's types, so a type error ships unnoticed unless this is run by hand.

**How to apply:** run the typecheck after any change to `hooks/auto-handoff/*.ts(x)`; re-locate the types file for the current Claude Code build first. Related: [[claude-plugin-config-facts]].

Since 2026-10-23 keep-alive is `hooks/keepalive/` (imported by `auto-handoff/register.tsx` from `../keepalive/`; one module in `hooks.json`): `plugin validate --strict` follows imports into a sibling folder under `hooks/` (same module analysis as before the move) and `plugin test` picks up `hooks/keepalive/tests/`. Add the `keepalive/*.ts` files to the tsc file list; one type error in `keepalive/tests/keepalive.test.ts` (TS2345, the GATED table's budgetMultiplier probe) predates that move; the `options` one went with keep-alive's `/config` rows (2026-10-23). The `tsconfig.json` in `hooks/auto-handoff/` and `hooks/keepalive/` (identical, extending the gitignored local `.claude-plugin/types/tsconfig.json`) is for editors only; the tsc recipe above uses its own scratch tsconfig and does not need them.

Test engine (`claude-code/testing`): the test body's `$` has no `env` or `process` (only events), so a helper that calls them needs a stub object; a failing `$.ui.status`/`$.ui.log` hook is dropped by the engine, never thrown to the caller. The harness loads its own copy of the module, so a module-level seam a test sets through an import never reaches the code under test; `userConfig` options are validated (no functions). The module analyser also refuses `$` passed to a member call (`obj.fn($)`): `$` goes only to a function called by its name (2026-10-23, the `orLog` wiring gap).

Engine types (2.1.306): `SessionUsage.context.window` is a required `number`, so the "no window reported" fallback path is defensive; whether a live host ever omits it is unverified. `session.compact` (trigger auto) hands off whatever the threshold, so a line above the window means "waits for auto-compact", never "no handoff". `$.session.usage({ breakdown: 'summary' })` estimates locally (`'full'` calls the token-count API); `context.breakdown` carries `autocompactSource` and `autoCompactThreshold?`; the mock's event payload `e` is the call's args.

Keep-alive has no `/config` rows since 2026-10-23 (human): precedence is the `/ai-dlc:cache-keepalive` override (per track, `--track 1h|5m|both`) > settings.local env > settings.json env > `.ai-dlc/cache-keepalive.json` > default. Its CLI (`skills/cache-keepalive-configure/templates/cache-keepalive.mjs`; install and merge skills call it by relative path; `set` is internal only) keeps its own copy of the trust and settings-env helpers: the human ruled configure-auto-handoff off-limits in that run, so never import from it.

Since 2026-10-23 the automatic handoff has no `/config` rows either: the manifest declares no `userConfig`, `resolveConfig(levels)` takes no options, and hook tests set values through the engine's `env` (process environment), never `{ options }`. The module runs only the built-in `/rename` and `/clear`; those keep their names.

Since 2026-10-23 (FEAT ai-dlc-lens step 17): when the session runs an older build than the installed one, get the installed build's types by loading the skill headless from a folder outside the repo: `claude -p "/plugin-authoring" --max-turns 1` (exits "Reached max turns"; it still writes `bundled-skills/<installed version>/<hash>/plugin-authoring/types/claude-code.d.ts`). Mod-state facts: an `atom(..., { shape })` key must be declared `Shaped<T>` in the `PluginState` contract (else `never`), the contract may not `import` (`Shaped` resolves inside `declare module 'claude-code'`), and `plugin validate` needs the atom's `plugin` as a string literal, not a const. Test kit: register every `on(...)` stub before the first `$` call; `turn.complete` stubs return `{ text }`; `settings.read` stubs return a settings object.

Since 2026-10-23 (FEAT ai-dlc-lens step 17.l1): chat-side drawing for Agent calls is the `ToolUse` row (`ToolGroup` folds only reads/searches/listings); a mounted row redraws on any `$.state` write it read, also in `claude plugin test` (no `ui.redraw()` needed); `Svg` is limited by surface, not site. Parallel Agent calls of one message are grouped from `turn.step` `tool` chunks (id + name). `claude -p "/reload-plugins"` needs `MSYS_NO_PATHCONV=1` in Git Bash; `--debug-file` names the load errors ("Plugin loading errors:").

Since 2026-10-23 (FEAT ai-dlc-lens step 17.l2): a subagent's own `turn.start` fires before an `agent.spawn` hook resumes after `next(e)` (headless E9 probe), so "the agent already exists" is no respawn signal, and any create-if-absent must decide inside the `update` callback (read-then-write from an earlier read clobbers). Test kit: `fs.read`/`fs.write` stubs get the path resolved to an absolute one (match by tail); a stub that throws makes the engine skip the hook (it falls through, which serves as "file missing"); a `turn.start` stub must return `{ turnId }`. VS Code raises no prompt-toolbar render site (`PromptHint`/`AbovePrompt` are terminal and desktop only).
