# ai-dlc-lens

A Claude Code plugin that shows an AI-DLC run while it happens. When the orchestrator spawns agents, the **AI-DLC Lens** view appears: one workflow per run (the work item, its `docs/handoffs/<run>/` folder), each a collapsible panel holding one flowchart per top-level step of the run (**in progress**, see [Panels and controls](#panels-and-controls)), with its agents drawn as avatars (persona name, model, role and a status dot). A new run never hides an earlier one, and agents of a different run never join an earlier run's workflow. Pressing an avatar opens the agent's panel (usage, tokens, context window, cost, tool calls, background tasks, thinking); pressing an arrow opens the hand-off panel (the handoff record and the hand-back, or the prompt). The chat card of a workflow's first spawn names the workflow, draws its flowchart and opens the view.

- **Drill-in or tab.** An avatar or arrow opens its panel inside the card or view it was pressed in, with `< Back` (`drill-in`, `panelOpenMode`'s default), or as a separate pane (a tab, `tab`). The **Panel Type** switch `◉ Drill in  ○ Tab` changes it for the session (see [Panels and controls](#panels-and-controls)).
- **Pinned or docked.** The mode switch (the first row of the view) decides where the view is drawn. Pinned (`workflowPlace`, the default) draws it in the band above the prompt on the terminal and the desktop app; docked draws it in the pane, which the surface places. **In progress:** in VS Code the mode follows the pane's seat: `docked` when the pane is in the right panel, `pinned` when it sits above the prompt. The switch there moves the view between the pane and the band above the prompt (pinned closes the pane and draws the band; docked opens the pane). The view has one form: the older "AI-DLC lens" card is gone, and an older build's card is closed on the first draw after `/reload-plugins`. No mod can make a pane full screen or minimise it, so the lens draws those controls itself, as [MANUAL-CHECKS.md](MANUAL-CHECKS.md) (*Step 1.5*) explains; see [The bands and the pane](#the-bands-and-the-pane). [Full screen](#full-screen) shows one step of one run alone.
- **Wide or narrow.** Every site (the band and the pane) shows either the **list** (the runs, one row each) or one run's **workflow** (its step charts), never both side by side; the combined wide layout is retired. A wide band (from `wideColumns` columns, 70) shows the list only and opens a run in the pane; a narrow band opens it inside itself.

**In progress:** this plugin is being built in the run `FEAT-20261020-ai-dlc-lens`, and its reviews are still open. It started as spike ITEM-027 (round 6) and has since been extended (steps 8.1.2 to 8.6.1.l1 of that run: robot avatars, keep-alive figures, the anomaly detector, Panel Type, full screen, one chart per step). It still goes through that run's scope pass and gates G1, G2 and G3 before it is released. Until then the commands, settings and panes can change. Step 44's lens requirements (R44.4, R44.5, R44.8 to R44.10, R44.12, R44.14 to R44.23) are built: M32 and M33 passed in VS Code, and M33's terminal part is not yet checked; the live checks of R44.21 and R44.23, M34 in [MANUAL-CHECKS.md](MANUAL-CHECKS.md), is not yet run. Critique and code review are pending. This README describes only what exists now.

**Claude Code only.** The lens is a Claude Code mod (a hooks module). The GitHub Copilot build (`tools/build-copilot.mjs`) skips this plugin, and only the Claude marketplace (`.claude-plugin/marketplace.json`) lists it. It does not depend on the `ai-dlc` plugin for its panes, and `ai-dlc` does not depend on it; the `/ai-dlc:lens*` commands are skills of `ai-dlc`. When `ai-dlc` is installed and its keep-alive is pinging, the workflow pane shows one keep-alive line under its controls (`keep-alive: 5m ping 1/20, next 14:05:07`), read-only from the state keep-alive publishes; without it, or with no track running, the line is not drawn. The minimum Claude Code version is decided at G2; the repository `README.md` (*Setup*) and [MANUAL-CHECKS.md](MANUAL-CHECKS.md) give the version the checks name, and neither is the final answer until then.

## Install

From the repository root, with the `ai-dlc-agent-workflow` marketplace registered (see the repository's `CLAUDE.md`):

```text
claude plugin marketplace update ai-dlc-agent-workflow
claude plugin install ai-dlc-lens@ai-dlc-agent-workflow --scope local
```

Then run `/reload-plugins`, or open a new session. For one terminal session without installing: `claude --plugin-dir plugins/claude/ai-dlc-lens`.

## Commands

The commands are named by thin skills of the `ai-dlc` plugin, so Claude Code lists them as `/ai-dlc:<name>`; this plugin's hooks module answers each run itself (a hooks module can only register a name without `:`). Claude Code lists the commands only when `ai-dlc` is installed; typed in full without it, the lens still answered them in a headless run (`claude -p "/ai-dlc:lens-gate off"`). The panes and the chat card work with this plugin alone.

| Command | What it does |
|---|---|
| `/ai-dlc:lens` | Opens or brings forward the AI-DLC Lens view (see [The bands and the pane](#the-bands-and-the-pane)). **In progress:** the command follows the session's own surface, the first attached one (`terminal` under the REPL). In a terminal or Desktop session, pinned, it shows the band minimised and opens no pane (the pane is opened from the band's `⤢`), unless a VS Code panel is attached: then it also opens the pane for that panel, and the terminal shows that pane beside its band. Docked, or where no band is drawn, it opens the pane on the newest workflow in progress, else on the run list. In a VS Code session, and in any session whose own surface is none of terminal, Desktop or VS Code (for example mobile, or none), the VS Code rules apply (see *Bands in VS Code*). In a wide VS Code panel it opens the workflow tab, and the Run List tab only in Tab mode. The view also appears on its own at the first spawn. |
| `/ai-dlc:lens-init [--force]` | Writes `.ai-dlc/lens.json` with every default, and its schema. |
| `/ai-dlc:lens-configure [<key> [<value>\|--unset]]` | Shows the lens settings and the level each comes from, or sets or unsets one in `.ai-dlc/lens.json`. |
| `/ai-dlc:lens-keepalive [on\|off]` | Shows or hides the **Keep Alive** sub-accordion of Cache Lab, with its Master, 1h and 5m buttons, in the agent panel (setting `keepaliveSection`, on by default), then reports its figures. |
| `/ai-dlc:lens-gate [on\|off]` | Turns anomaly reporting on or off (setting `gateAlert`); bare, it lists the current anomalies, then the runs it read and the `anomalyRunScope` in force. See [Anomaly alert](#anomaly-alert). |
| `/ai-dlc:lens-kit` | Opens the round-0 kit pane (manual checks K1 to K5). |

The agent panel's former **Cache keep-alive** section is now the **Keep Alive** sub-accordion of the panel's Cache Lab section (see [Cache Lab](#cache-lab)). It shows how long keep-alive kept the prompt cache warm on the 5m and 1h tracks (from each arming to the cache's expiry, read from the state `ai-dlc` publishes; `0s` without it) and what cache reads saved, for the agent and for the session: cache-read tokens times the input price minus the cache-read price, from the model metadata file (`costingPath`), `—` when a price is missing.

The spike's experiments E1, E2, E4, E5, E7, E9 and E10 log to `PROBE-LOG.jsonl` in the plugin's folder while the `probes` setting is on (off by default). The pane ids are `ai-dlc-lens`, `ai-dlc-lens-chart`, `ai-dlc-lens-edge`, `ai-dlc-lens-agent` and `ai-dlc-lens-kit` (a pane id takes no `:`).

## Panels and controls

- **Workflow view** (title "AI-DLC Lens"). In list mode, the runs (one row each); in workflow mode, one run with a step accordion each: see *Step charts* below and [The bands and the pane](#the-bands-and-the-pane). The first row has the pinned/docked switch (in VS Code it moves the view between the band above the prompt and the pane) and the size controls (minimise, restore), which act on the band or the pane according to where they are pressed (the band has a `⤢` that opens the pane; the pane's title row has none, and full screen starts from a step chart's `⤢`); below it is the **Panel Type** switch `◉ Drill in  ○ Tab` (drill-in by default; `◉` marks the current choice and each choice is its own button). The switch also appears in the `/ai-dlc:lens` pane, changes the session only and never writes `.ai-dlc/lens.json`. Every `[+]`/`[-]` section starts collapsed unless `collapsedByDefault` is off. Below each step chart are `Agents:` and `Connections:` button rows (renamed from `Avatars:` and `Arrows:`). The workflow's orchestrator thinking and gathered context are sections of the view.
- **Chat card.** The first spawn of a workflow leaves a card that names it and draws its flowchart (`chartInChat`), or a chip with an "Open flowchart" button when the row is narrower than `chartMode` allows. **In progress:** when the card's agents work on unrelated tasks (a task is a run plus a feature root), the card draws one titled chart per task, with an agent that has no record (or a gone one) joining the first task's chart; with one task the card is unchanged.
- **Agent panel** ("Agents: ..."). A header with the avatar, persona name, model and role (the **Agents** panel, opened from an agent), then these sections: Context Lab (context, input, output, cache read and write, uncached, cost, the model it ran on, limits from the metadata file; renamed from Usage), Cache Lab (see [Cache Lab](#cache-lab); it replaces the former Cache keep-alive section), Tool calls, Background tasks (each task listed once, starting collapsed, and toggling on its own), Thinking; and the bottom row of buttons, centred: View transcript, Refresh and, on the orchestrator's panel only, a red **Stop** (Stop ends the whole current turn, like `Esc`; subagent panels have none; the Stop note appears only under it, while the View transcript and Refresh note appears on every panel). The panel's order is the Panel Type switch; a separator; `< Back` (drill-in) and the agent's avatar, name, model and role; a separator; the agent's own Anomalies (absent while none); a separator; Context Lab; a separator; Cache Lab; then the other sections, each after a separator. Cache Lab follows `collapsedByDefault` like the other sections.
- **Hand-off panel** ("Connections: ..."). This is the **Connections** panel, opened from a connection (arrow). Top to bottom: Anomalies; a Hand-off line with the sizes of the brief and the hand-back in characters (Usage is removed); the Hand-off and Hand-back sections (the prompt when the brief names no record); and a Send Message accordion. It has no Context Lab or Cache Lab, and a **Stop turn** button at the bottom, centred, with its press note and the Stop note under it. A SendMessage receiver maps to a connection: `team-lead` and `main` to the orchestrator, a teammate's id, name or persona name to that agent; any other name stays unmatched. SendMessage rows are hidden in the chat; `ctrl+o` still shows them.
- **Status.** A dot per run and a ring per agent. Colours (settings, hex): in progress `statusInProgressColor` (blinks, `statusBlink`), pending `statusPendingColor`, halted `statusHaltedColor` (an agent failed or was killed, or the run is blocked), waiting `statusWaitingColor`, completed `statusCompletedColor`.
- **Keep-alive line.** One dim line under the controls row of the pane, `keep-alive: 5m ping 1/20, next 14:05:07`, only while `ai-dlc`'s keep-alive runs a track. The minimised one-line view has none, and the band no longer draws it: keep-alive has a band of its own (see [The bands and the pane](#the-bands-and-the-pane)).
- **Layout.** List mode: a list of runs, one row each; choosing one opens its workflow, and `< Runs` goes back to the list. Workflow mode, top to bottom: the Panel Type switch (in the controls row), a separator, Anomalies (absent while there are none), a separator, `< Runs`, the status, the run name and its metadata, then one accordion per step (highest first). Every run stays listed; finished runs are dimmed in the list. **In progress:** the list (wide and narrow) and the full-screen `Runs:` row are ordered newest first by each run's start: its first spawn, else the date in its folder name, else `started:` in its run state. A run resumed later keeps its place, and the selected run stays selected.
- **Parent runs.** **In progress:** a run whose run state's front matter has `parent: <run id>` is drawn inside its parent's workflow, its step charts titled `<child run>: Step N` (a child keeps its own step numbers), and is not listed on its own. A chain of parents goes to the top run; an unknown parent or a cycle keeps the run as its own. The merged run is ordered by the parent's start, and a child's anomalies keep the child run's name.
- **Merged-away runs.** **In progress:** a brief that names a run folder which no longer exists joins the run that keeps a `merged-from-<run>.md` record for it, at the step shifted by the merge offset (when the run state has the Offset table).
- **Chart rows wrap.** **In progress:** a chart row holds at most `chartAvatarsPerRow` avatars (default 8, see [Settings](#settings)); a level with more wraps onto further rows. It applies inside each step chart, the chat card and full screen (full screen enlarges the sizes, not the count).
- **Run status.** A step halted and then started again shows its latest attempt (an agent that failed or was killed is ignored once a later agent of the same workflow carries the same handoff record step code). A run state `status: done` makes the run completed and a *Stages* row `done` makes its step completed, so pending placeholders and records without a hand-back no longer hold a finished step back; `blocked` still halts. **In progress:** the run list, the band, the chat card and each step chart's heading read one rule. A run whose current run state says `status:` other than `done` (`active`, a blank, or a status the lens does not know) never reads completed, so a finished step of it reads waiting, even when its *Stages* row is `done`. With no agent at work, such a run reads waiting (a `blocked` run reads halted, as before). A run whose run state says `done` can read completed. A run with no readable run state has no status to read: its run list and its step charts read waiting, never completed. The current run state is the highest version of the run state. The lens re-reads a run state another session changed within about 2 seconds, so a halted run continued in a new session shows the new status in both.
- **Run identity.** A workflow is a run (its `docs/handoffs/<run>/` folder). Agents of another run never join it; when a spawn names no run, the same request text joins, else it starts a new workflow.
- **Step charts.** **In progress:** a run has one chart per feature root (top-level step), read from the record files in its `docs/handoffs/<run>/` folder as well as from live spawns, so earlier steps are drawn without having been spawned in this session.
  - Each chart is headed by its status, its ▲ anomaly marker, a title `Step N · <feature>`, a **Stop turn** button (white on red), a `–` (collapse) or `□` (open) button just left of a `⤢` button (on the band, opens the pane on this run with this step open and leaves the band as it is (in VS Code only in a wide panel, see *Step flowcharts in VS Code*); in the pane or the docked view, shows that step in full screen), then the chart, then its `Agents:` and `Connections:` button rows. The feature name comes from the *Features* table of the run state, falling back to its *Stages* table, then to `Step N`.
  - The chart's root is the step itself, drawn as its sender (usually the orchestrator). The step's own record is a node under it, with its loop rounds (`17.l1`) under that node; sub-steps (`28.1`) hang under the root and deeper codes under their prefix. In the current naming a loop has no record of its own: its rounds (`8.2.l1.1`, `8.2.l1.2`, `8.2.l2.1`) hang under their sub-root (`8.2`) joined to it by a two-way arrow, a round's own sub-numbers (`8.2.l1.1.1`) hang under the round, and the loop code (`8.2.l1`) is never a node. Review axes are sub-numbers too (`8.4.1` and `8.4.2` under the review step `8.4`). A loop code that does have a record (the older naming) is drawn as described above. Each node's second line starts with its step code (`28.1 · sonnet`).
  - A node drawn only from a record is green with a hand-back and grey without. A code with no record of its own that sits between the root and a record (`1.2` above `1.2.l1`) is drawn as the orchestrator, steady (not blinking). A live spawn takes the node of the record its brief names; loop rounds, resumed agents, spawns from earlier sessions or from before `/clear`, and absolute or worktree paths join the chart of their step.
  - Charts are ordered by step code, highest first, live or not; sub-steps inside a chart are in code order. After the run's own charts come those of child runs (by child folder, then step, highest first), then the chart of spawns that name no step, then the `Briefs naming records no longer on disk` line (next bullet). Step numbers decide the order, not file times.
  - Old briefs written before a run was renumbered join the node their record was renamed to. **In progress:** a run folder may hold rename sources, `.json` or `.md` files whose name has the word `rename` at its start or after a character that is not a letter or digit (`renames.json`, `2026_renames.json` and `un-renamed-notes.md` are sources; `prename.json` and `unrenamed-notes.md` are not), and that are neither records nor run states: a `.json` source with a `codeMap` object (old code to new code), or a `.md` source with a table whose first two header cells are `Old code` and `New code`. Only pairs of step codes are kept, an unreadable file gives no map, and several sources are read oldest name first and composed (a later source that repeats an old code wins); codes inside one file are not chained, since one file is one renaming. For a run with renames (a `renames` prefix map in its source or a `codeMap`), the lens looks a brief's record up on disk under, in order: its own name; the map; the *Features* table's `Old steps` followed by the map; the `Old steps` alone. The first name that is listed wins. A brief whose record is not listed yet (the listing can lag behind a live spawn) is drawn at its own code when that code's step exists in the run (in its *Features* table or among its records). Otherwise, a brief whose record is no longer on disk gets no chart: it appears only in one collapsed line, `Briefs naming records no longer on disk (n)`, under the charts (not drawn when there is none).
  - Run-state file names are matched in lower case only, as the `handoff` skill and auto-handoff write them (`RUN.V1.MD` and `Run.v1.md` are neither run states nor records). The run state is the highest versioned `run.v<major>.md` or `run.v<major>.<minor>.md` that can be read, else `run.md`: versions are read highest first and reading stops at the first readable one (an unreadable one is skipped), and each read is cached until the file's size or modified time changes. Versions are ordered by major, then minor, numerically (`v2` > `v1.2` > `v1.1` > `v1`, `v1.10` > `v1.9`); a part with a zero or a leading zero (`run.v0.md`, `run.v01.md`, `run.v1.0.md`) is not a version. An older version is deprecated by a newer `.1` minor saying so, never by its own front matter, so the lens reads no deprecation field. Run-state files are never taken for records and never appear as chart nodes.
- **Idle orchestrator.** In a step whose agents have all ended, the orchestrator (the step's root) is drawn idle, not running.
- **Failures stay contained.** A lens error never replaces Claude Code's own Agent row: the card falls back to that row. A pane that fails to draw shows one red line, `lens: the <pane> could not be drawn (…)`, instead of going blank.
- **Live markers.** The ▲ anomaly markers on the chat card and in the `/ai-dlc:lens` pane update while they are shown, and clear when the cause is gone.
- **Pollers.** The lens's blink and poll timers stop when the session ends, but not at `/clear` (no new session start follows a `/clear`, so stopping there would leave the lens without them).

### The bands and the pane

Pinned, the lens and keep-alive each have a band of their own above the prompt: first the **AI-DLC Lens** band, then `ai-dlc`'s **keep-alive** band (drawn by `ai-dlc`'s hooks module, see [keep-alive](../ai-dlc/hooks/keepalive/README.md)). **In progress:** the lens band is drawn on the Terminal and the Desktop app whatever else is attached (R44.21: the render's own surface decides), and in VS Code only while the person chose pinned with the mode switch, with the pane closed (see *Bands in VS Code* below). Keep-alive's band is drawn on every surface. They are never combined, each has its own controls, and both minimise the same way: `–` minimises a band and `□` restores it. The lens band is described below; the lens band and the lens pane are never drawn together for more than one frame.

- **Minimised.** The lens band starts minimised and shows one line: the top 3 workflows ordered in progress, waiting, halted, pending, completed, followed by `(n)`, the number of runs in progress, else "Nothing Here". `□` brings back the list; `–` minimises it again. `–` and `□` change only the band, from the band or from the pane, never the pane.
- **Keep-alive band, minimised.** It starts minimised each time the module loads and shows one row: whether keep-alive is `on` or `off` (the tracks decide it, see keep-alive, [The head row](../ai-dlc/hooks/keepalive/README.md#the-head-row)), glyph buttons for the master switch (`⏻`), ping now (`⟳`), `□` and `×` (the full band uses words: off/on, Ping now, Minimise, Close). Keep-alive opens no Pane. Restored, it shows its title row, the 5m and 1h track rows and their buttons. Without `ai-dlc`'s keep-alive, or with its status off, there is no keep-alive band.
- **Close.** The band has a `×` only while no workflow is in progress. Closed, it stays away until the next spawn, `/ai-dlc:lens` or a new session.
- **The pane.** The pane is at its normal size, never the band's minimised size. Minimising the band does not change it.
- **Modes.** The band and the pane each show the run list or one run's workflow. The controls depend on the site:
  - **`⤢` on the band** opens the pane at once: from a minimised band or the list, the pane shows the list; from a band in workflow mode, the pane shows that workflow. The band is unchanged. The title row of the pane, beside the band or docked, has no `⤢` (its step charts do, see *Step charts*).
  - **`□` (maximise) on the band** restores it to the list; a run chosen in a narrow band opens in the band, and in a wide band opens in the pane while the band stays on the list. From the pane, `□` sets the band to the list, never to a workflow.
  - **`↺` (restore)** on a band in workflow mode returns it to the list. On the pane it applies only while the band is closed (dismissed with `×`, or not drawn for `bandGoneMs`, 10 seconds by default): it closes the pane and shows the band in the mode the pane had. With the band open, the pane keeps its controls as before.
  - **Agents and connections (avatars and arrows)** follow the site: in a narrow band they open inside the band, in a wide band they open in the pane, and in the pane they open there; **Panel Type** still chooses drill-in or tab.
  - **The chat card's "Open flowchart"** opens the pane on that card's run, in workflow mode, with that step's accordion open.
- **Bands in VS Code (in progress).** In VS Code the switch word follows the seat: `docked` when the pane is in the right panel, `pinned` when it sits above the prompt, whether or not the switch was pressed. Where the pane is seated above the prompt (a narrow panel) and the person has not pressed the switch to move the lens into the band, the pane is the lens's view, and keep-alive's band sits above the prompt as a separate view. Pressing the switch in the pane draws the lens band above the prompt and closes the pane (`placePress`); pressing it on the band opens the pane again. The lens draws its band in VS Code only in that case, so the band and the pane are never up together for more than one frame (R44.4, R44.16). The VS Code rules apply only where the session's own surface is VS Code: a terminal or desktop session draws the lens band whatever else is attached, also when the list of attached surfaces is unknown (R44.21, `bandAllowed`). A VS Code panel attached to a terminal or Desktop session has a lens view while pinned, except after the person closed it by hand (decisions 10, 11 and 12, below). The command opens the lens pane for it, and the terminal keeps its band and shows that pane too, since a pane belongs to the session, not to one surface (R44.23 amended). The mode switch acts by where it is pressed: in the VS Code panel it moves the lens between the pane and the VS Code band, as in a VS Code session; in the terminal or Desktop it switches pinned and docked, and while the VS Code panel is attached the pane stays open either way. **In progress (code review round 2):** a press from another surface, such as the mobile app, in a terminal or Desktop session also switches pinned and docked, as a terminal press does (only a `vscode` press takes the VS Code path, register.tsx:1333). The host may keep that tab undrawn below its floor (144 columns, or 110 once you have opened the tab and not closed it by hand) until the panel widens or you open it. Narrowing closes the Run List tab, and the pane follows the region back above the prompt, with the switch reading `pinned`. **In progress (decision 9):** only the VS Code panel's own renders of the pane do this; a terminal or Desktop render of the same pane never changes the place, the seat the command lays out, or the Run List tab.
- **`/ai-dlc:lens`** shows the band minimised when pinned and a lens band is drawn (a terminal or Desktop session with no VS Code panel attached, or a VS Code panel where the person chose pinned; see *Bands in VS Code*); docked, or where no band is drawn, it opens the pane on the newest workflow in progress, else on the list.
- **Step flowcharts in VS Code (in progress).** A step's flowchart is drawn only in the docked pane, the right panel. Above the prompt (the inline pane, or the band chosen with the mode switch) an open step shows the line "Widen the Claude panel to see the flowchart in the right panel." in place of its chart, and its full-screen `⤢` is dim text that does nothing while the panel is narrow. On the band in a wide panel, the step's `⤢` still opens the right pane on that step. A plugin cannot widen the Claude panel, so you widen it by hand. The terminal and the Desktop app still draw step flowcharts in their band and panes; the terminal part of the manual check M33 is not yet live-checked.

### Cache Lab

A section of the agent panel, opened by pressing an avatar (drill-in or tab), placed right after Context Lab; it is no longer at the head of the pane, and it replaces the agent panel's former Cache keep-alive section. It follows `collapsedByDefault` like the other sections, and starts collapsed after a reload or in a new session. Collapsed until opened; nothing is read from disk while it is closed. It reads the session transcripts when opened, when the window changes, on `↻` and when a turn ends.

- **Window.** Buttons `This session`, `Today`, `7d` (default), `30d` and `All`; the chosen one is shown in brackets. `This session` covers the whole automatic handoff chain, from the chain `ai-dlc`'s keep-alive publishes. The window resets to `7d` at `/reload-plugins` unless `cacheLabKeepWindowOnReload` is on.
- **Figures.** Saved by cache, Lost to busts, NET, Cache Hit %, Tokens Saved, Bust events and Median baseline; money figures need prices from `costingPath` and read `no price` without them.
- **Miss attribution.** Busts counted as TTL lapse, Prefix change or Unknown. **TTL mix:** cache writes by lifetime (5m, 1h, unknown) with their share.
- **Invalidation Gallery.** A sub-accordion of the busts, newest first, at most 50, each as one line of text (time, model, 8-character session id, stream if not the main one, attribution, tokens written, cost) and the turn it happened in.
- **Keep Alive.** The last sub-accordion: what the Cache keep-alive section showed, for the agent and the session (how long keep-alive kept the cache warm on the 5m and 1h tracks, and what cache reads saved). `/ai-dlc:lens-keepalive` / `keepaliveSection` show or hide it and the buttons below.
- **Master, 1h and 5m buttons.** A row of on/off buttons for all caches (`Master: on [off]`, `1h: on [off]`, `5m: on [off]`) with the same effect as the keep-alive band's buttons: they switch this session only (they run `/ai-dlc:cache-keepalive-configure <on|off> [--track 1h|5m] --session`). They are drawn only while `ai-dlc`'s keep-alive publishes a usable state and `keepaliveSection` is on.

### Diagrams

A closed `mermaid` fence in an assistant message is drawn as a picture right after its source (a PNG on the terminal, an SVG elsewhere), offline, by a renderer process in `renderer/` with its vendored code in `renderer/vendor/` (see [renderer/BUILD.md](renderer/BUILD.md) and [NOTICE.md](NOTICE.md)). A picture that takes over 300 ms shows `rendering…` and is drawn at the next redraw; pictures are cached in memory and on disk (the disk cache stops writing at 200 files). A diagram type the renderer cannot draw offline (for example `pie`) shows its source and a one-line reason. Other fence kinds (math, PlantUML) are found but still drawn as source. `diagramMermaid` turns this off; the check is row D1 of [MANUAL-CHECKS.md](MANUAL-CHECKS.md).

### Full screen

The pane's title row has no `⤢` (the docked pane included); full screen starts from a step chart's `⤢`. **In progress:** in VS Code a step's full screen is reached only in the docked pane (see *Step flowcharts in VS Code* under *The bands and the pane*). It brings the pane to the front and shows that step of the selected run alone: a note, a `Runs:` row to switch runs (with several runs), and the step's chart 1.5 times larger. The run list, notices, keep-alive line and Anomalies section are hidden until `⤡` restores the view; while in full screen, `⤡` is the title row's button, and the step heading reads status, ▲, title, Stop turn, `⤡` (no minimise). An open step ends with the note of Stop turn's last press and the dim Stop note: it interrupts the whole current turn, like `Esc`, never a single agent. There is no `Steps:` row, and large charts are fitted with no blank space.

VS Code sizes its own panel: maximise it for more room. In the terminal, full screen leaves the band for the pane, which is at most 45% wide when docked; restoring returns to the band. No host lets a plugin take the whole window.

## Settings

### Avatars

Each agent is drawn as a robot, the same robot for every agent of a type (`hooks/avatar.ts`), with its status as the ring around it. `avatarStyle` is `robot` (default), `image` or `initials`. `avatarImage.<agent>` sets an agent's image: a `data:` URI, or a path to an image file inside a folder Claude Code trusts (`projects` in `~/.claude.json`); anything else, a remote URL included, is refused and never fetched. `<agent>` is the agent ID for an ai-dlc agent (`avatarImage.software-engineer`), else the whole agent type; its env name is `AI_DLC_LENS_AVATAR_IMAGE__<AGENT>` (capitals, `:` as `__`, `-` and `.` as `_`). `avatarImageTypes` (default `image/png`) and `avatarImageMaxBytes` (default 65,536) limit images, and an image that would push the chart past the 131,072-character Svg limit is left out with a note. `/ai-dlc:lens-configure` refuses an untrusted path.

## Anomaly alert

The lens reads each run's `run.md` (front matter, *Stages* and *Gates and loops* tables), the handoff records and hand-backs in the run folder, and the agents it tracks, and reports an anomaly once when it appears and clears it when its cause is gone. A malformed file is skipped, never an error. Done and abandoned runs report nothing. There is no command Stop hook and no marker file.

| Anomaly | Colour (setting) |
|---|---|
| A run is blocked (`status: blocked` in `run.md`); it names its blocked steps | red (`anomalyRunBlockedColor`) |
| A step is blocked (a *Stages* row whose status starts with `blocked`), even while the run is active | red (`anomalyStepBlockedColor`) |
| A gate waits for the human | orange (`anomalyGateWaitingColor`) |
| A gate was rejected | red (`anomalyGateRejectedColor`) |
| A loop is out of rounds | deep orange (`anomalyLoopOutOfRoundsColor`) |
| An agent failed or stopped | red (`anomalyAgentFailedColor`) |
| An agent was killed, or waited `anomalyWaitingMinutes` (default 30) or more | red (`anomalyAgentKilledColor`, `anomalyAgentWaitingLongColor`) |
| A hand-back failed its check | yellow (`anomalyHandbackFailedColor`), a marker on its record's arrow |

**In progress:** a gate row whose decision is written in words and has a date is decided, not waiting. "Gate waiting" is still raised for an empty or dash decision, a `pending`, `waiting`, `open`, `tbd`, `todo` or "not yet" decision, or a missing date.

Each is shown as a toast with the ▲ marker and in the **Anomalies (n)** section of the workflow view. Every check has its own on/off setting and colour (see the [Settings](#settings) table); `gateAlert` `false` turns all reporting off. A run reported blocked names its blocked steps instead of repeating them; with `anomalyRunBlocked` off, the steps are reported on their own. A blocked step's record is read from the *Stages* table's `Record` column, else its `Handback` column, else its `Handoff` column.

`anomalyRunScope` chooses the runs read: `session` (default) reads the runs this session's agent briefs name; `all` also reads every active or blocked `run.md` under `artifacts.handoffs` (default `docs/handoffs`). Bare `/ai-dlc:lens-gate` ends with the runs it read and the scope in force. Change it with `/ai-dlc:lens-configure anomalyRunScope all`, or set `AI_DLC_LENS_ANOMALY_RUN_SCOPE` in a settings file's `env`.

## Develop

From the repository root:

```text
npx @anthropic-ai/claude-code plugin validate --strict ./plugins/claude/ai-dlc-lens
npx @anthropic-ai/claude-code plugin test ./plugins/claude/ai-dlc-lens
```

`tsc` needs the Claude Code engine types, which are not committed. Copy `types/claude-code.d.ts` from the `plugin-authoring` skill bundled with your Claude Code build (written under the temp folder `claude/bundled-skills/<version>/<hash>/plugin-authoring/` when that skill loads) to `.tsc/claude-code.d.ts`, then run `npx -p typescript@5 tsc -p plugins/claude/ai-dlc-lens/.tsc`.
