# Plugin Management — one source, two plugins

This is how the **ai-dlc** plugin is built; use it as the recipe for any new plugin and as the rulebook when changing one. The Claude Code plugin is the **source of truth**; the GitHub Copilot plugin is **generated** from it by `build-copilot.mjs` (shipped next to this file in `templates/`). Nobody edits the Copilot tree by hand.

```
Skill("ai-dlc:plugin-management", args: "create <plugin-name>")   // new dual-platform plugin + marketplaces
Skill("ai-dlc:plugin-management", args: "update <change>")        // change agents, skills or manifests in an existing one
Skill("ai-dlc:plugin-management", args: "release <version>")      // bump, rebuild, validate, tag
```

## 1. Repository layout

```
<repo>/
├─ .claude-plugin/marketplace.json        Claude marketplace (lists plugins/claude/<name>)
├─ .github/plugin/marketplace.json        Copilot marketplace (lists plugins/copilot/<name>)
├─ .github/workflows/validate.yml         CI: build --check + both strict validations
├─ plugins/
│  ├─ claude/<name>/                      SOURCE OF TRUTH
│  │  ├─ .claude-plugin/plugin.json
│  │  ├─ agents/<agent>.md
│  │  ├─ skills/<skill>/SKILL.md (+ templates/, scripts/)
│  │  └─ hooks/hooks.json                 only for hooks that must run in EVERY project
│  └─ copilot/<name>/                     GENERATED — never hand-edit
├─ tools/build-copilot.mjs                the projection (copy of templates/build-copilot.mjs)
├─ tools/templates/                       sources for generated files (e.g. AGENTS.template.md)
├─ .claude/                               the plugin repo's own dev setup — never shipped (§8)
└─ README.md
```

## 2. Manifests

**`plugins/claude/<name>/.claude-plugin/plugin.json`** — `name` (kebab-case; it becomes the `<name>:` namespace of every agent and skill), `displayName`, `version` (SemVer), `description`, `author`, `homepage`, `repository`, `keywords`. Add `userConfig` only when a **plugin** hook or script reads it (`CLAUDE_PLUGIN_OPTION_<KEY>`); otherwise leave it out.

**`.claude-plugin/marketplace.json`** — `name` (the marketplace id users type after `@`), `owner`, `metadata.description`, and `plugins[]` entries `{ name, source: "./plugins/claude/<name>", description, category }`. The entry `name` must equal the manifest `name`. Relative `source` paths start at the repo root and never contain `..`.

**`.github/plugin/marketplace.json`** — same shape, `source: "./plugins/copilot/<name>"`, plus `version`. It is hand-maintained: keep its description and version in step with the Claude manifest.

The Copilot `plugin.json` is generated by the build (`agents/`, `skills/`, and `hooks` only when there are plugin hooks).

## 3. Agents (`agents/<agent>.md`)

- Frontmatter: `name`, `description` (with `<example>` blocks — it drives routing), `tools` (comma list; omit to inherit all), `model` (`opus` / `sonnet` aliases, never a pinned id), `color`, `memory: project`. `status: deprecated` makes the build skip the agent.
- Reference other agents and skills with the namespace: `Agent("<name>:software-engineer", …)`, `Skill("<name>:review")`. The build strips the prefix for Copilot.
- Give an agent the `Skill` tool if it calls skills, and `Agent` if it delegates.
- **Subagents cannot spawn subagents.** An agent that runs a team (an orchestrator) must be the session's main agent: `claude --agent <name>:orchestrator`, or `"agent": "<name>:orchestrator"` in the project's `.claude/settings.json`.

## 4. Skills (`skills/<skill>/SKILL.md`)

- Frontmatter: `name` (= folder name), `description` (when to use it — the model reads this to decide).
- Every skill is also a slash command (`/<name>:<skill>`), so **do not ship `commands/`**: a command and a skill with the same name collide. Fold command bodies into skills.
- Files next to the skill are addressed as `${CLAUDE_SKILL_DIR}/templates/…`; the build rewrites that prefix for Copilot.
- `disable-model-invocation: true` makes a skill user-only. Another skill cannot `Skill()`-call it — have the caller read `${CLAUDE_SKILL_DIR}/../<skill>/SKILL.md` and follow it instead.
- Keep generic skills stack-neutral; put stack-specific content (C#, `dotnet`, NuGet) in stack-specific skills.

## 5. Hooks and rules: plugin-wide vs project-installed

- A plugin `hooks/hooks.json` hook runs in **every** project that enables the plugin. Use it only for behaviour that is right everywhere; commands use `${CLAUDE_PLUGIN_ROOT}/scripts/…`. Stop hooks read the JSON payload from stdin, honour `stop_hook_active` (loop guard) and answer `{"decision":"block","reason":"…"}`.
- Plugins **cannot ship** project rules, `CLAUDE.md`, `AGENTS.md` or settings. Put those as templates in an `init` skill that writes them into the target repository after showing a diff.
- Stack-specific rules and hooks (for example a `dotnet test` gate) go in their own skills (`dotnet-rules`, `dotnet-test-gate`) that `init` runs only when it detects that stack. They install `.claude/hooks/*`, merge the hook into `.claude/settings.json`, and write the Copilot twin to `.github/hooks/<name>.json` (`{ "version": 1, "hooks": { "agentStop": [ { "type": "command", "bash": …, "powershell": …, "timeoutSec": … } ] } }`).

## 6. The build — `tools/build-copilot.mjs`

Copy `${CLAUDE_SKILL_DIR}/templates/build-copilot.mjs` to `tools/build-copilot.mjs` in a new plugin repo. It is zero-dependency (Node 18+) and plugin-agnostic (`--plugin <name>` when `plugins/claude/` holds several).

| Claude source | Copilot output |
|---|---|
| `agents/<a>.md` | `agents/<a>.agent.md` with a platform note; tools mapped `Read`→`read`, `Write`/`Edit`→`edit`, `Glob`/`Grep`→`search`, `Bash`→`execute`, `Agent`→`agent`, `WebFetch`/`WebSearch`→`web`, `TodoWrite`→`todo`; Claude-only tools dropped; `mcp__*` kept |
| `skills/**` | copied; `<name>:` and `${CLAUDE_SKILL_DIR}/` stripped in Markdown |
| `scripts/**` | copied verbatim |
| `hooks/hooks.json` (optional) | `hooks.json` in Copilot's `version: 1` format (`Stop`→`agentStop`, …) |
| manifest | generated `plugin.json` + `GENERATED.md` |

It also writes **generated sources** into the Claude plugin when their inputs exist (an `AGENTS.md` template built from `tools/templates/AGENTS.template.md` + the orchestrator persona; the copy of itself in this skill). Skills listed in `tools/project-skills.json` are also mirrored into the repo's own `.claude/skills/<name>/` for repo-local use. `--check` exits 1 when the Copilot tree or any generated source is stale — that is what CI and the Stop hook run. When the build warns `no Copilot alias for tool "X"`, add `X` to `ALIAS` or `DROP`.

## 7. Change workflow (every change)

1. Edit only `plugins/claude/<name>/` (or `tools/templates/` for generated sources).
2. `node tools/build-copilot.mjs`, then `node tools/build-copilot.mjs --check`. Remove empty folders the build leaves under `plugins/copilot/` after a rename or delete.
3. When a manifest changed, or an agent or skill was added, renamed or removed: `npx @anthropic-ai/claude-code plugin validate --strict ./plugins/claude/<name>` and `npx @anthropic-ai/claude-code plugin validate --strict .`
4. Update every reference to a renamed or removed agent/skill (`grep -rn '<old-name>' plugins/claude README.md`), then the README tables.
5. Prefer deleting a retired agent or skill outright in plugin scope (git keeps history); in project scope, deprecate instead.

## 8. The plugin repository's own `.claude/` (dogfooding)

The repo runs the plugin it builds — it keeps **no local copies** of agents, skills or commands.

- Register the repo as a local marketplace once per machine; this writes the machine path to the gitignored `.claude/settings.local.json`:

  ```
  claude plugin marketplace add ./ --scope local
  claude plugin install <name>@<marketplace> --scope local
  ```

  (`.` is rejected as a source; use `./`.) Edits apply on the next session or after `/reload-plugins`.
- `.claude/CLAUDE.md` — what the repo is, the build/validate commands, the layout, and the dogfooding steps.
- `.claude/rules/plugin-development.md` — edit only `plugins/claude/`, rebuild after every change, validate after manifest or roster changes, keep agents stack-neutral, never hand-edit generated files.
- `.claude/hooks/check-copilot-stale.mjs` + a `Stop` hook in `.claude/settings.json` — runs `build-copilot.mjs --check` and blocks finishing while anything generated is stale (with the `stop_hook_active` loop guard).
- `.claude/settings.json` permissions for `node tools/build-copilot.mjs[ --check]` and both `plugin validate` commands; no stack-specific permissions the repo does not use.

## 9. CI — `.github/workflows/validate.yml`

On push and pull request: checkout, `actions/setup-node` (22), `node tools/build-copilot.mjs --check`, then both `plugin validate --strict` commands.

## 10. Release

1. Bump `version` in the Claude `plugin.json` and the Copilot marketplace entry (SemVer).
2. Rebuild, `--check`, both validations.
3. Commit, tag `v<version>`, push. Users update with `/plugin marketplace update <marketplace>` (Claude) or `copilot plugin update` (Copilot).
4. README install section: Claude `/plugin marketplace add <owner>/<repo>` + `/plugin install <name>@<marketplace>`; Copilot `copilot plugin marketplace add <owner>/<repo>` + `copilot plugin install <name>@<marketplace>`.

## Checklist for `create`

- [ ] Layout from §1, both marketplaces and the Claude manifest from §2.
- [ ] At least one agent and one skill; namespace references use `<name>:`.
- [ ] `tools/build-copilot.mjs` copied from `templates/`; build + `--check` green.
- [ ] Both strict validations pass.
- [ ] `validate.yml` CI from §9.
- [ ] Repo `.claude/` dev setup from §8, plugin installed locally.
- [ ] README: what it is, the agent table, install for both platforms, the develop loop.
