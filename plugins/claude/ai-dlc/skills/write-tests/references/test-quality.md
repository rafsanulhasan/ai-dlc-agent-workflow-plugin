# Test Quality: What to Check and How

Companion to the `write-tests` skill. It applies to every test level and every stack; the examples are pseudo-code, so translate them into the project's test framework and conventions.

## Tests describe behaviour, not structure

A good test reads like a line of the specification — "an order with a valid cart is confirmed" — and keeps passing when the internals are rewritten, as long as behaviour is unchanged. It:

- uses only the public seam a caller would use;
- checks what a caller can observe (return value, published event, response, persisted state *as read back through the interface*);
- asserts one logical outcome;
- has a name that says **what** happens, not **how**.

The tell for a bad test: it breaks during a refactor that did not change behaviour.

## Anti-patterns

### Implementation-coupled

```text
// Weak: proves a collaborator was called, not that checkout works
test "checkout calls the payment client with the total"
    payment = mock(PaymentClient)
    checkout(cart, payment)
    assert payment.charge was called with cart.total

// Strong: proves the observable outcome
test "checkout with a valid cart is confirmed"
    result = checkout(cartWith(product), testPaymentMethod)
    assert result.status == Confirmed
```

Red flags: doubles that `test-doubles` forbids, tests of private methods, assertions on call counts or call order, names that describe the mechanism.

### Side-channel verification

```text
// Weak: bypasses the interface and couples the test to the schema
test "createUser writes a row"
    createUser(name: "Alice")
    assert db.query("select ... where name = 'Alice'") is not empty

// Strong: verifies through the interface the caller uses
test "a created user can be retrieved"
    user = createUser(name: "Alice")
    assert getUser(user.id).name == "Alice"
```

Reading storage directly is acceptable only when storage *is* the contract under test (for example a migration or a repository's mapping test that the plan marks as such).

### Tautological

```text
// Passes by construction: the expectation repeats the implementation
test "total sums line prices"
    items = [10, 5]
    expected = sum(items)
    assert calculateTotal(items) == expected

// Independent expectation: a literal worked out by hand
test "total sums line prices"
    assert calculateTotal([10, 5]) == 15
```

Expected values must come from somewhere the code cannot influence: a hand-worked literal, an example in the AC, a published reference value. The same applies to snapshots: a snapshot generated by running the code and never inspected is tautological.

### Horizontal slicing

Writing every test up front and then implementing (or running) them all at once. The tests end up checking imagined behaviour and the shape of the code. Work one test case at a time and let each cycle inform the next.

## Test doubles

Whether a test may use a mock, stub, fake, spy or route, and which kind, is decided by the `test-doubles` skill. Classify every double with it before writing the test.

## Testable boundaries (feedback for the engineer)

When a test is hard to write, the design is usually telling you something. Report these to the calling agent rather than working around them:

- **Dependencies created inside the component** instead of injected — the boundary cannot be replaced in a test.
- **One generic gateway** (`send(endpoint, options)`) instead of one operation per external call (`getUser`, `createOrder`) — every double needs branching logic, and a test cannot show which calls it exercises.
- **No public seam** that reaches the behaviour — the only way in is through internals.
