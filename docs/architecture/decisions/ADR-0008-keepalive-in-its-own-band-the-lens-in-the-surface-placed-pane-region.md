## Context

Two modules draw above the prompt: keep-alive (ai-dlc plugin, `hooks/keepalive/`, its band drawn from `hooks/auto-handoff/register.tsx`) and the lens (ai-dlc-lens plugin). Until step 44, keep-alive had three places for its state: a status line (spec D13, a short summary), an `AbovePrompt` band on the terminal and Desktop, and a Pane on VS Code (spec D9). The Pane existed because the types say the band is raised on the terminal and Desktop only (`claude-code.d.ts` 2.1.310, :10818).

Two host facts decide where each module can sit:

- **The surface places the panes, all of them together.** Every pane of every module is a tab of one framed region ("one shown, the rest tabs", d.ts :10867-10868). A module cannot choose where a pane sits: `placement` is read-only (:10897-10903) and `PaneOpenArgs` has no placement (:7589-7660). VS Code moves the whole region by the panel width: inline above the prompt when narrow, docked on the right when wide, at about 70 columns (probe, 2ff: `isFullscreen` flips). There is no resize event (:4098), a module cannot open or close a pane while drawing (:3494), and a pane opened later by a timer is "unasked" and may wait undrawn below 110 or 144 columns (:15067-15074).
- **`AbovePrompt` does render in VS Code.** The probe logged 76 renders with surface `vscode` (2ff), against the d.ts line :10818.

So while keep-alive was a pane, it docked with the lens whenever the panel grew. The human saw both tabs leave the area above the prompt and the band hide (R44.8; cause confirmed by the probe: nothing closed, the region docked). The human wants keep-alive to stay above the prompt at every width, and only the lens to move (R44.7, R44.9, R44.10). With keep-alive's band on every surface, the status-line summary only repeated it (R44.1).

Later the same day the human widened the lens's part. In Tab mode the lens brings its Run List tab when it docks (R44.12, R44.14). Its mode word follows its seat (R44.15). Its mode button moves it between the right pane and the band above the prompt (R44.16). The live check of that round then showed a host error, `state.set: denied … while the ui.render is being dispatched`, and a missing step chart (R44.17, R44.18). The cause: a `$.clock.after(0)` timer only moves a write past the render that asked for it. Renders here are frequent (each step of a resize, the lens's 500 ms blink, its 2 s poll), so the timer could fire inside a later render, and the host refused the write (d.ts :3494).

A last round (R44.19, R44.20) settled where the step flowchart goes. In Drill in mode, widening could leave the docked pane on the minimised list with no flowchart. The human asked for the flowchart in the right panel only, never in the band above the prompt. If the host lets a plugin widen the Claude panel, the lens should widen it; if not, the full-screen control should be off while the panel is narrow. A plugin cannot widen it (44.2.l1.7): no `$.ui` operation sizes a surface (d.ts 2382-2640), and `PaneOpenArgs.columns` only sizes the dock (7646-7657). After the build the human kept the rule as built: no flowchart above the prompt at all in VS Code, and the terminal and Desktop unchanged, since the terminal has no other windows to widen.

The G4 round for step 44 changed which surface decides the lens's view. Until then the lens drew its band, and the command and the mode button chose between band and pane, by the whole roster of attached surfaces (`bandEverywhere`: every attached surface a terminal or Desktop). The human saw that a terminal session lost its lens band as soon as VS Code attached, and also when the roster was unknown. He decided that the band follows the session's own surface (R44.21). He then decided that `/ai-dlc:lens` and the pinned/docked switch follow it too (R44.23). He amended that the next day: an attached VS Code panel has a lens view while pinned, except after the person closed it by hand (decisions 7, 10, 11 and 12). The host gives no direct "own surface" value: `command.run` carries no surface (CommandRunInput, d.ts 1828-1857; its `presentation` is the terminal's layout, d.ts 1797-1811). The design therefore rests on the stated assumptions A1 to A4 below.

## Decision

We will draw keep-alive only in its own `AbovePrompt` band, on every surface (VS Code included), with no pane and no status line, and we will keep the lens in the pane region, letting the surface decide where it sits and adapting the lens to that seat.

- **Keep-alive.**
  - One band (title row with the master Button, the 5m and 1h rows, the seed row while a track is on), at every panel width. It is outside the pane region, so a resize does not move it.
  - No keep-alive Pane: `/ai-dlc:cache-keepalive` opens none.
  - No status line: keep-alive writes nothing to `ui.status`. The published `$.state` lines are unchanged, so the lens and other readers keep the full text.
- **The lens.**
  - By default no band of its own in VS Code (R44.4). It is a pane, and the surface seats it: inline above the prompt when narrow, docked on the right when wide.
  - **Pinned and docked in VS Code (R44.16, the human's option (a)).** Docked means the lens pane, wherever the surface seats it. Pinned means the lens drawn in the `AbovePrompt` band, with its pane and its Run List tab closed. The mode button switches between the two. Pressed in the pane, it closes the pane and the Run List tab and draws the band, minimised. Pressed on the band, it opens the pane the way `/ai-dlc:lens` does; a press is the person's, so the host places the pane at any width. R44.4 is relaxed for this case only: the band is allowed in VS Code while the person chose pinned (the session value `vscodeBand`) and the lens pane is closed. Drawing any lens pane clears that choice, so the two lens views are never up together for more than one frame. In a narrow panel the pane sits above the prompt too, so there the button switches between two views that are both above the prompt. Outside a VS Code session the button acts by the surface it was pressed on (R44.23; see "Which surface decides").
  - **The mode follows the seat (R44.15).** In VS Code each change of seat sets the mode: `docked` when the pane is drawn in the right pane, `pinned` when it is drawn inline above the prompt. The `workflowPlace` setting is not changed. VS Code no longer shows the note "this surface has no band above the prompt".
  - It reads `placement` on each Pane render and adapts after the render, never during it. Going to inline, it closes its wide-only Run List tab, so the narrow view keeps one lens tab (R44.10). Going to dock after being inline (R44.12, R44.14, R44.19): in both panel types it lays the panel out as `/ai-dlc:lens` does in a wide panel, with the workflow tab active on the newest run and its current step open, so the step's flowchart is drawn in the right pane. Only when Panel Type is **Tab** does it also open the Run List tab, without focus; in **Drill in** it opens no Run List tab. `/ai-dlc:lens` in a wide panel of a VS Code session (own surface `vscode`, R44.23) follows the same rule: Tab opens the Run List tab (inactive) and the workflow tab (active); Drill in opens the workflow tab alone and closes an open Run List tab. The plugin makes the open on docking, not the person. So the host places the Run List tab only from 144 columns, or from 110 once the person has opened it and not closed it by hand; below that it stays open but undrawn until the panel widens or the person opens it (d.ts :15066-15074). The human accepted this (R44.12). In a terminal or Desktop session these VS Code seat rules never apply, even with the VS Code panel attached: the command opens the workflow pane at seat `dock` and opens no Run List tab, whatever the Panel Type (`openLens`, register.tsx:1415; R44.23).
  - **Writes a render asks for (R44.17, R44.18).** Every state write the lens makes because of a render (the seat follow, the band giving way to a pane, the band ping) runs through one helper, `afterRender`. It waits a 0 ms timer after the render. When the host refuses the write as made during a render dispatch, it runs the whole act again 100 ms later, up to 20 tries. Any other error, and the last refusal, show as a lens error, and every act given to it must be safe to repeat. This also fixes R44.18: when the seat follow's first write was refused, the act stopped before it laid out the workflow view, so the docked pane kept the minimised list and drew no step chart.
  - **Flowcharts in the right pane only, in VS Code (R44.20, choice 2).** A plugin cannot widen the Claude panel (44.2.l1.7), so the lens draws a step's flowchart, at normal size or in full screen, only in a lens pane seated `dock`. Above the prompt (a pane seated `inline`, or the band chosen with the mode button) an open step shows the dim line "Widen the Claude panel to see the flowchart in the right panel." in place of the chart (`chartOff`). While the panel is narrow its `⤢` is dim text, not a Button, so it does nothing (`fullOff`); the host's Button has no disabled flag (d.ts 1093-1198). On the band in a wide panel (the band's viewport reports `isFullscreen`, `ViewSite.wide`) the band still shows no chart, but `⤢` opens the right pane on that step. Terminal and Desktop are unchanged: their band and panes keep drawing flowcharts.
  - On the terminal and Desktop the band is drawn by the render's own surface (R44.21): a terminal or Desktop render draws the lens band whatever else is attached, including when the roster is unknown (`bandAllowed` with `e.surface`; `BAND_SURFACES` = terminal, desktop). A render on any other surface (VS Code, the mobile app) keeps the R44.4 and R44.16 rule: `bandEverywhere(roster)`, or `vscodeBand`.
- **Which surface decides (R44.21, R44.23 with its amendment, decisions 1, 6 to 12).**
  - **The band render:** its own surface, `e.surface` (above).
  - **The command and `showView`:** the session's own surface, `ownSurface`: the first entry of `$.session.surfaces()` (A1); `null` when the list is empty or the call fails (`surfacesNow` returns `[]`).
    - **Terminal or Desktop session, no `vscode` surface attached** (the mobile app or an unknown surface may be): a pinned view is the band alone. `/ai-dlc:lens` shows the band minimised and opens no pane (`viewBandOnly` true).
    - **Terminal or Desktop session with the VS Code panel attached:** the pane opens for that panel, unless the person moved the lens into the VS Code band (`vscodeBand`). The terminal or Desktop still draws its band, and also shows that pane, because a pane belongs to the session (A2). The human accepted pane plus band there (decision 7).
    - **VS Code session, own surface `null`, or any other own surface (for example `mobile`, none of `terminal`, `desktop` or `vscode`; `viewBandOnly` falls through to `bandAllowed`, register.tsx:1306):** the R44.4 and R44.16 rule, unchanged. The band is then drawn only while `vscodeBand` is true. So with an unknown roster in a terminal session, the command opens the pane and the terminal render still draws its band.
  - **The mode button: the surface it was pressed on (`press.surface`, A3).** Proposed by agent-manager in 44.2.l1.12 and ratified by the human on 2026-11-01 (decision 8): the mode button acts by the surface it was pressed on.
    - **A press from `vscode`, in any session:** takes the R44.16 path. From the pane, it closes the pane and the Run List tab and draws the VS Code band. From the band, it opens the pane. So the VS Code panel has a lens view while pinned, except after the person closed it by hand (decision 10, narrowed by decision 11: a band closed with its `×` comes back at the next agent spawn, at `/ai-dlc:lens`, or in a new session; decision 12: a press of the mode button in VS Code also brings it back).
    - **Any other press (or one with no surface, or from another surface such as `mobile`; only a `vscode` press is excluded, register.tsx:1333) in a terminal or Desktop session:** switches pinned and docked (`changeView`). While VS Code is attached, the pane stays open either way.
    - **In a VS Code session, or with own surface `null`:** every press takes the R44.16 path.
  - **The seat follow, driven only by VS Code renders (decision 9, 2026-11-01; source 44.2.l1.13; replaces Q44-C).** Only a lens pane render whose own surface is `vscode` drives the seat memory (`paneSeat`, `lastSeat`), the place, the band's hand-over and the Run List tab (`notePaneSeat` and `followSeat` return at once unless `e.surface` is `vscode`; register.tsx:1495 and :1549). A terminal or Desktop render of the same pane never changes any of them, so a terminal docked beside a narrow VS Code panel stays `docked`, and an inline terminal render no longer closes the Run List tab.
  - **Manual closes (decision 10, 2026-11-01; replaces Q44-D).** Decision 7's "never left with no lens view" covers the lens's own acts. When the person closes the pane by hand (Escape or its close), closes the band with its `×`, or the host leaves the pane undrawn (`isPlaced: false`), the VS Code panel may show no lens view until the person reopens it. The lens reopens nothing the person closed. Decision 11 (2026-11-01) narrows it for the band: a band closed with its `×` comes back at the next agent spawn, at `/ai-dlc:lens`, or in a new session (step 36's Amendment 8: `agent.spawn` resets `bandClosed`, register.tsx:4250); a pane closed by hand is not reopened by a spawn. Decision 12 (2026-11-01): the person's own mode-button press in VS Code (`placePress`, register.tsx:1348) and the pane's `↺` (`paneToBand`, register.tsx:1633) also bring back a band closed with its `×`; they are presses of the person, not lens acts, so decision 10 does not cover them.
  - **R44.22 (step chart headings use the run list's status rule, and a run with no readable run state reads waiting) is a status rule, not a placement decision.** It is recorded in `docs/product/ai-dlc-lens/stories.md` (AC-7.13, AC-7.14) and `docs/specs/lens-view.lld.md`, not in this record.
- **Rule for later modules.** A view that must stay above the prompt at every width is an `AbovePrompt` band, not a pane. A pane goes where the surface puts the region, and its module adapts to `placement`; it never tries to move itself. A write that a render triggers is never made in the render, and one timer is not enough to leave the render: the module retries a write the host refuses as made during a render dispatch, and keeps each such act safe to repeat.

## Assumptions

Each host behaviour the decision relies on, with its source and whether it has been seen live:

- **A1. The session's own surface is the first entry of `$.session.surfaces()`.**
  - **Source:** d.ts 2864-2875 ("terminal under the REPL first, then the remote ones in the order they attached"); d.ts 12309-12312 (`session.start`'s surface is `$.session.surfaces()[0]`, null for `-p` or the SDK).
  - **Terminal sessions:** documented.
  - **Desktop and VS Code sessions:** inferred. That the host's own client attaches first is not stated in the d.ts.
  - **Live status:** not verified live; M34 checks it (write down whether Desktop is the first surface).
  - **Consequence:** the list is re-read on every call. If the own client detaches and attaches again after another surface, the lens follows the new first entry.
- **A2. A pane belongs to the session, not to one surface.**
  - **Source:** `$.ui.open`'s `PaneOpenArgs` (d.ts 7588-7665) has no surface field; each surface that places panes asks for its render (`UiOpenResult` and `UiPane`, d.ts 15074-15111: "a session may draw on several").
  - **Effect:** with VS Code attached to a terminal session, the terminal shows the lens pane too.
  - **Live status:** read from the d.ts; not verified live; M34 checks it.
- **A3. A button press names the surface it came from.**
  - **Source:** `press.surface` (d.ts 1191-1196; `UiPressArgument`, 15167-15171).
  - **Live status:** read from the d.ts; not checked on its own. M34's press steps (in the VS Code pane, on the VS Code band, in the terminal) also test it, since each gives a different result.
- **A4. A plugin cannot widen the VS Code Claude panel.**
  - **Source:** research 44.2.l1.7: no `$.ui` operation sizes a surface (d.ts 2382-2640); `PaneOpenArgs.columns` only sizes the dock (d.ts 7646-7657).
  - **Live status:** a missing feature, so no live check can confirm it. The human accepted the rule built on it (R44.20) after the live check of 2026-10-31.
- **Already recorded above:** `AbovePrompt` renders in VS Code (probe 2ff, against d.ts :10818) and the shared pane region (F1, F2).

## Alternatives Considered

- **Keep-alive stays a tab of the shared pane, beside the lens** (research option (a)). Rejected by the human: it docks with the lens when the panel is wide, which is the R44.8 behaviour.
- **Keep-alive's rows live only inside the lens view** (research option (b)). Rejected: there would be no keep-alive view while the lens is closed, and the two plugins would be coupled for a keep-alive control.
- **The lens re-seats itself on resize** (close and reopen to force inline or dock). Rejected: the host gives no placement argument, no resize event, and no state writes while drawing, and a reopen from a timer is unasked and may stay undrawn (F1, F4 to F6).
- **Keep the status-line summary as a second view.** Rejected by the human (R44.1): it repeats the band, which now draws on every surface.
- **The mode button works only in a wide panel** (agent-manager's R44.16 option (b), 44.2.l1.5 plan). Not chosen: the human chose option (a). In a narrow panel the button would do nothing but say to widen the panel.
- **The mode button changes only its label** (R44.16 option (c)). Not recommended and not chosen: in VS Code pinned and docked would stay the same pane, which is why the lens read `pinned` while it sat in the right pane.
- **A bare `$.clock.after(0)` for render-triggered writes** (round 44.2.l1.5). Rejected after the live check (R44.17): the timer can fire inside a later render, and the host refuses the write.
- **The lens widens the Claude panel, then shows the flowchart in the right pane** (R44.20 choice 1, the human's first preference). Not possible: no host operation sizes the panel (d.ts 2382-2640; `PaneOpenArgs.columns`, 7646-7657, only sizes the dock), so choice 2 was built.
- **Block only full screen above the prompt, and keep the normal-size chart there** (the requirement-analyst's reading). Not chosen: the human kept the build, with no flowchart above the prompt at all.
- **The same rule on the terminal and Desktop.** Not chosen: the terminal has no other windows to make room for, so it keeps drawing flowcharts as before.
- **Gate the lens band on the whole attached-surface roster** (`bandEverywhere` for every render; the R44.4 rule as built until 44.2.l1.10). Rejected by the human (G4 decision 1): a terminal session lost its band whenever VS Code, or any surface other than a terminal or Desktop, attached, and also when the roster was unknown.
- **`/ai-dlc:lens` and the mode switch decided by every attached surface** (the rule before 44.2.l1.11). Rejected by the human (decision 6). A terminal session with only the mobile app attached got a pane. A press in the terminal took the VS Code path whenever any non-band surface was attached. VS Code's seat rules (`commandSeatOf`, the Run List tab) applied to a terminal session as soon as VS Code attached.
- **An attached VS Code panel with no lens view while pinned** (as built in 44.2.l1.11). Rejected by the human (decision 7): that panel showed no band and no pane, and its only way to the lens was the chat card.
- **Use `session.start`'s surface as the own surface.** Not chosen (44.2.l1.11): it covers only the terminal; it is null for `-p` and the SDK (d.ts 12309-12312).
- **Use the press's surface as the session's own surface for the command.** Not possible: a command has no press. The press surface is used only for the button (A3).
- **Show the lens pane on the VS Code surface only.** Not possible: a pane has no surface (A2).
- **The mode button acts by the session's own surface** (as in 44.2.l1.11). Not chosen (44.2.l1.12): a press in the attached VS Code panel would switch the terminal's place and could leave that panel with no lens view, which decision 7 rules out. Decision 8 ratified the press-surface rule instead.

## Consequences

### Positive

- Keep-alive's state and buttons stay above the prompt at every width and on every surface, in one place.
- A resize moves only the lens, and the lens no longer leaves an extra tab inline (R44.8, R44.10).
- Keep-alive has one view to keep right, not three; D13's surface rule is no longer needed, and the `statusText` setting is retired (R44.11).
- In VS Code the lens's mode word says where the lens is (R44.15), and the person can choose the band above the prompt instead of the pane (R44.16).
- Lens writes no longer fail now and then during a resize, and widening draws the step chart again (R44.17, R44.18).
- Widening shows the flowchart in the right pane in both panel types (R44.19), and in VS Code a flowchart is never squeezed above the prompt (R44.20).
- A terminal or Desktop session keeps its lens band whatever else attaches. An attached VS Code panel has a lens view while pinned, except after the person closed it by hand (R44.21, R44.23, decisions 10, 11 and 12).

### Negative / Trade-offs

- **It rests on observed behaviour, not on the types.** The d.ts still says `AbovePrompt` is terminal and Desktop only (:10818). If a later Claude Code stops drawing it in VS Code, keep-alive has no view there. The probe (2ff, 2.1.310) is the evidence; a live check after each host update covers it.
- **Other surfaces are unchecked.** Only the terminal, Desktop and VS Code have been seen drawing the band. A surface that does not draw `AbovePrompt` shows no keep-alive state, since the status line is gone.
- **The Run List tab may wait undrawn after widening.** In Tab mode the lens opens it itself on docking (R44.12, R44.14). The person did not ask for that open, so the host draws the tab only from 144 columns (110 once the person has opened it and not closed it by hand) and keeps it undrawn below that (d.ts :15066-15074). In Drill in mode no Run List tab opens.
- In a narrow VS Code panel, keep-alive's band and the lens's inline pane region both sit above the prompt, as two separate views. With pinned chosen, the lens's band takes the place of its pane there.
- **R44.4 has an exception.** In VS Code the lens may now draw its band, while the person chose pinned and the lens pane is closed (R44.16). On a VS Code surface the two lens views must never be up together. The band's hand-over to a pane (`followSeat`, through `afterRender`) keeps them apart, so any change there needs a test. On a terminal or Desktop surface with the VS Code panel attached, band plus pane is intended (R44.23 amended, A2).
- **Render-triggered writes can lag.** A write the host keeps refusing is retried for about 2 seconds (20 tries, 100 ms apart) before it shows as a lens error.
- **No flowchart in a narrow VS Code panel.** The person has to widen the Claude panel by hand, because a plugin cannot. Until then the lens shows a line saying so and a dim `⤢`. The rule is VS Code only, so the surfaces now differ: the terminal and Desktop still draw flowcharts in their band.
- **R44.21 and R44.23 rest on two assumptions not yet seen live** (A1 for Desktop and VS Code sessions, A2). If the host's own client is not the first surface, a Desktop session follows VS Code's rules. If a pane is not drawn on every surface, the terminal shows only its band. M34 checks both. Until it passes, the README's description of these cases is unverified.
- **With the VS Code panel attached, a terminal or Desktop session shows the lens twice while pinned:** its band and the pane it shares with VS Code (A2). The human accepted this (decision 7).
- **The surfaces now differ by session as well as by surface.** In a terminal session, the VS Code panel gets the workflow pane at seat `dock` with no Run List tab, whatever its width or Panel Type, because VS Code's seat rules apply to VS Code sessions only.

### Neutral

- Replaces spec decisions that had no ADR: D9's keep-alive Pane on VS Code, D13 (status-line summary, surface rule, `statusText`) and the "no band on VS Code" fallback, in `docs/specs/keepalive-cache-status.spec.r4-delta.md` (rev 4.8).
- The lens's layout already followed `placement`, never pixels (`docs/product/ai-dlc-lens/stories.md`, A16); this record adds the tab handling, the no-band rule in VS Code with its pinned exception (R44.16), the mode that follows the seat (R44.15), the rule for render-triggered writes (R44.17) and, in VS Code, flowcharts in the right pane only (R44.20). R44.22 changes no record here: it is a status rule (AC-7.13, AC-7.14, the LLD). R44.21 and R44.23 change no keep-alive rule: keep-alive's band does not look at any surface (docs/specs/keepalive-cache-status.spec.r4-delta.md, D9).
