## 3. The view follows the placement (R44.9, R44.10)

### 3.1 The rule

The lens does not move its panes; the surface does (F1, F2). The lens keeps what is shown consistent with where the surface has put the region (its **seat**, the pane's `placement`: `inline` or `dock`). On each change of seat it does three things: it sets the view's place to match (3.2); on `inline` it closes the Run List tab (`RUNS`), so the view is exactly one lens pane; on `dock` after `inline`, in VS Code, it lays the panel out as `/ai-dlc:lens` lays out a wide one, in both panel types (R44.19), and in Tab mode only it opens the Run List tab (R44.12, R44.14). Panel Type (the `panelOpenMode` setting, read with `openModeOf`) is Tab or Drill in; the Run List tab exists only in Tab mode.

| Transition (the lens pane's `placement`) | What the surface does | What the lens does |
|---|---|---|
| inline to dock (the panel grows from narrow to wide), R44.9, R44.12, R44.14, R44.19 | docks the whole region; the lens tab goes with it to the right pane | sets the place to `docked` (VS Code, R44.15). In **both** panel types it lays the panel out as `/ai-dlc:lens` lays out a wide one: the workflow tab on the newest run, its default steps open, so the current step's flowchart is drawn in the right pane (R44.19, R44.20). In **Tab** mode it then also opens the Run List tab without focus, so the workflow tab stays shown (the Run List tab inactive, the current run active). In **Drill in** mode it opens no Run List tab (R44.14). |
| dock to inline (the panel shrinks from wide to narrow), R44.10, R44.15 | moves the region back above the prompt; the right pane closes; the lens tab is in the band-position again | sets the place to `pinned` (VS Code, R44.15) and closes the Run List tab, so the view is one lens pane again |

Keep-alive is not in this region (its own band, keep-alive LLD 26) and so is never moved or closed by a resize.
The open on docking is unasked (d.ts `UiOpenResult`: "never a timer"), so the host places it only from 144 columns, or from 110 once the person has opened the Run List tab and not closed it by hand; below that it keeps the tab open but undrawn until the panel widens or the person opens it. The result is logged (`plog` `E3`, `via: 'docked again'`). The human accepted this (R44.12).

### 3.2 Mechanism

- Input: the `placement`, `bodyColumns` and `surface` of a lens Pane render, read in the Pane hooks of `CHART` (`R:4474`) and `RUNS` (`R:4486`), recorded by `notePaneSeat(placement, columns)` (module memory, no state write, `paneSeat`, also read by `commandSeatOf`), then `followSeat($, placement, surface, pinnedBand)`; `pinnedBand` is `await read($, vscodeBandA)` (a state read is allowed while drawing).
- Memory: `let lastSeat: 'dock' | 'inline' | null` (`R:1469`), `null` on load and reset to `null` by `placePress` (3.4). It is memory, not an atom: a state write while drawing is denied (F5, F7).
- `followSeat($, placement, surface, pinnedBand)` (`R:1498`): an unknown `placement` does nothing. (a) When `pinnedBand` is true and no hand-over is under way (`bandGivingWay`, `R:1496`), a lens pane is being drawn while the person chose pinned (a pane opened another way): the band gives way. It sets `bandGivingWay`, then, through `afterRender`, sets `vscodeBandA` to `false` and the view's place to `docked` (seat `dock`) or `pinned` (seat `inline`), and clears `bandGivingWay` in a `finally`. (b) When the seat equals `lastSeat` nothing more happens. Otherwise `lastSeat` takes the seat and `afterRender($, 'seat follow', () => seatChanged($, seat, was, surface))` is scheduled. One act per change of seat, not per render.
- `seatChanged($, seat, was, surface)` (`R:1521`), outside the render: in VS Code (`surface === 'vscode'`) it sets the view's place: `docked` for `dock`, `pinned` for `inline` (R44.15). On `inline` it closes `RUNS` and returns. On `dock` it returns unless `was` is `inline` and the surface is `vscode`. Then, in both panel types (R44.19), it takes `w`, the newest run (`latestFlow`), sets the view with `commandOpenView(view, 'dock', w)`, and, when there is a run, clears the open-card and step-selection keys of `w` (`withoutStepKeys` and the `stepSelA` entry), so the default steps are open and the current step's flowchart is drawn in the right pane (R44.20). Only then, in Tab mode (`openModeOf(...) === 'tab'`, R44.14), it opens `RUNS` with `$.ui.open({ id: RUNS, title: RUNS_TITLE, closeOnEscape: true })` and no focus, and logs the result (`plog` `E3`, `via: 'docked again'`); in Drill in mode it returns there.
- `afterRender($, site, act, tries = 20)` (`R:1483`; constants `AFTER_RENDER_TRIES = 20` and `AFTER_RENDER_RETRY_MS = 100`, `R:1480-1481`) (R44.17): runs `act` with `$.clock.after(0, ...)`, just after the render that asked for it. If `act` rejects with a refusal of the render kind (`isRenderDenial`, `R:1482`: the message matches `/ui\.render is being dispatched|drawing is pure/`) and tries remain, it schedules the whole act again with `$.clock.after(100, ...)`, `tries - 1`; any other error, or the last refusal, goes to `lensFail(site, err)`. It never throws (a throwing `$.clock.after` is caught and logged the same way). Every act given to it must be safe to repeat. It wraps the seat follow (`R:1517`), the band hand-over (`R:1505`) and the band ping of `pingBandSoon` (`R:1558`).
- Why: the first built form, `$.clock.after(0, ...)` only, was refused intermittently ("state.set: denied ... while the ui.render is being dispatched", live findings 4), because a timer fired while a later render was dispatched (F7). The first write of `seatChanged` is the place update, so when it was refused the act stopped before it laid out the workflow view, and the docked pane kept the minimised list: the step chart was not drawn. That is the cause of R44.18; no separate fix was needed. The Run List close and open are `$.ui` acts (allowed from a timer, d.ts 2538); the state writes are the ones the retry protects. The layout of the workflow view no longer depends on the panel type, so a refused first write still costs the same flowchart in both.
- Residual: the host's open of the Run List tab is unasked (3.1), so it may stay undrawn below the floors.

### 3.3 `/ai-dlc:lens` (unchanged, stated for the whole picture)

The command picks the seat from the last drawn lens pane: `commandSeatOf(seen, wideColumns)` is `dock` only for a docked pane at a wide width (the Run List and workflow tabs open), else `inline` (one pane, the minimised list; the safe choice for a narrow panel). On a surface with no lens band it opens the pane; on a surface that draws the band it follows the pinned or docked rules of 43.2, 3. The command and the seat follow on docking (3.2) are the only places the Run List tab is opened. Step 44 (R44.14), `openLens` (`R:1354`): in VS Code, seat `dock`, the command opens the Run List tab (inactive) and the workflow tab (active) only in Tab mode (`openModeOf(...) === 'tab'`, `openRunsTab`); in Drill in mode it closes an open Run List tab and opens the workflow tab alone (`openWorkflowPane`). The same rule as `seatChanged` (3.2); it holds in an already-wide panel too.

### 3.4 The mode button (`pane-place`): docked and pinned, option a (R44.15, R44.16)

- Where every attached surface draws the band (`bandEverywhere`, terminal and desktop), the button switches the place as before (`changeView`). Elsewhere (VS Code) the host seats the pane (F1), so the button switches what draws the view. `placePress($, place, where)` (`R:1293`, called from the button at `R:3069`) in VS Code: it sets `lastSeat = null` first, so the next pane drawn applies its seat again (R44.15). From the pane (`where` is not `'band'`; pressed as `pinned`): it closes `RUNS` and `CHART`, sets the view's place to `pinned`, sets `bandClosedA` to `false`, sets `vscodeBandA` to `true` and starts the band minimised (`bandStart`). From the band (`where === 'band'`; pressed as `docked`): it sets `vscodeBandA` to `false`, the place to `docked`, and opens the pane as `/ai-dlc:lens` opens it (`openLens`); a press is the person asking, so the pane is placed at any width.
- `vscodeBandA` (`R:296`: `atom({ plugin: 'ai-dlc-lens', key: 'vscodeBand' }, false)`, declared in `types/index.d.ts`) records that the person chose pinned in VS Code with the pane closed. `bandAllowed($)` (`R:1282`): `bandEverywhere(await surfacesNow($)) || (await read($, vscodeBandA))`. `onBand` (`R:1271`) and the band hook (`R:4515`) use it instead of `bandEverywhere` alone, so R44.4 ("the lens shows no band of its own in VS Code") is relaxed only while the person chose pinned and the lens pane is closed.
- The two lens views never show at once: any lens pane that is drawn while `vscodeBandA` is true makes the band give way (`followSeat`, 3.2, (a)). In a narrow VS Code panel the pane sits above the prompt too, so the button switches between the pane and the band, both above the prompt, and the mode reads `pinned` either way.
- The note "pinned: this surface has no band above the prompt, so the view stays a pane." no longer shows in VS Code (`R:3416`: the condition is `site.where === 'pane' && place === 'pinned' && !BAND_SURFACES.has(site.surface) && site.surface !== 'vscode'`).
- R44.20: the band chosen with the mode button draws no step flowchart in VS Code either (3.5); its `⤢` opens the right pane on that step only while the panel is wide.

### 3.5 Where a step's flowchart is drawn in VS Code (R44.20)

- Rule: in VS Code a step's flowchart (`chartNode`, with `chartInPane` on) is drawn only in a lens pane the host seats `dock`, the right panel. Never above the prompt: not in the pane seated `inline`, not on the band the mode button chose. Terminal and desktop are unchanged (their band and panes draw it).
- Why: no plugin can widen the Claude panel. None of the `$.ui` operations sizes a surface (d.ts 2382-2640), `PaneOpenArgs.columns` (7646-7657) only sizes the dock, and a plugin can only read the width (`viewport`, `bodyColumns`, `placement`). So the design shows how to get the chart (widen the panel by hand) rather than drawing it small or opening the right pane at a narrow width.
- Mechanism, in the step chart function of `workflowBody` (`R:3515-3564`): `chartOff = site.surface === 'vscode' && !(site.where === 'pane' && site.placement === 'dock')` (`R:3515`). When `chartOff` and the step is open (and `chartInPane`), the chart is replaced by the dim line `Widen the Claude panel to see the flowchart in the right panel.` (`R:3562-3564`); the heading, `Stop turn`, `–`/`□` and the agent buttons are unchanged. With `chartInPane` off, no chart and no line.
- The full-screen control: `fullOff = chartOff && !(site.where === 'band' && site.wide === true)` (`R:3518`). When `fullOff`, `⤢` is drawn as dim `Text`, not a `Button`, because ButtonProps has no disabled flag (d.ts 1093-1198), so it cannot be pressed and writes nothing (`R:3543`). On the band in a wide panel it stays a Button: a press stores the step as the chosen one and opens the right pane on that workflow (`expandBand`), where the chart is drawn. `site.wide` is new on `ViewSite` (`R:3244`); the band hook sets it from `e.viewport?.isFullscreen === true` (`R:4546`, the same signal the pane's seat follows); the pane sites do not set it (a pane is `inline` or `dock`, and `chartOff` already follows its `placement`).
- Both values are pure functions of `(surface, where, placement, wide)`, so the table in 6 tests them without a host.

## 4. `runListStatus` (R44.5)

```ts
// L:1552
export function runListStatus(members: readonly StatusMember[], runStatuses: readonly string[] = [], spawner: string | null = null): FlowStatus
```

- Rule: `runListStatus` is `workflowStatus(...)` except that a result of `completed` becomes `waiting` when any listed run's status is `active`. Every other result (`halted` for a `blocked` run or a failed or killed agent, `in-progress`, `waiting`, `pending`) passes through unchanged. `workflowStatus` keeps its own order: `blocked` run, then all runs `done`, then failed or killed agents, then running, waiting, pending, completed.
- The old fault: `workflowStatus` returned `completed` as soon as every agent had ended, whatever the run said (`L:1542` before step 44). A run waiting for its next stage or for the human is not completed, so it reads `waiting`.
- The run's status is that of its **current** run-state version: the newest version wins (`pickRunState`, `L:2769`; `readRunState`, `R:681`). Nothing changed there: the human's R44.5 ("the newest run-state version wins").
- Who calls which: the run list and the band take `runListStatus` (the run-list builder at `R:2005`: `status: runListStatus(settled, dirs.map(d => runs[d]?.status ?? ''), batch.parent)`). A step's chart and the step accordion keep `workflowStatus`, since a finished step of an active run is `completed`. This amends 43.2, 6.4 ("one input: the step accordion's status takes the same run statuses as the band"): the two take the same inputs but not the same function, on purpose.
- Truth table (members all ended, no failed or killed agent): run statuses `[]` gives `completed` (no run state, as before); `['done']` gives `completed`; `['active']` gives `waiting`; `['active', 'done']` gives `waiting`; `['blocked', 'active']` gives `halted`. A run with a failed agent is `halted` whatever its run state says (as before). In the minimised list the precedence is in progress, waiting, halted, pending, completed (the human, entries 2dd and 2de), so an active run now sorts above a halted one.

## 5. One lens view per surface, and the band gate (R44.4 revised)

- The lens band (the `AbovePrompt` hook, its gate at `R:4515`) is drawn only where `bandAllowed` holds (3.4): every attached surface draws the band (`bandEverywhere(surfaces)`, `L:2226`, true when the surface list is non-empty and every entry is in `BAND_SURFACES`, `terminal` and `desktop`, `L:2223`), or, in VS Code, the person chose pinned with the mode button (`vscodeBandA`, its pane closed). `/ai-dlc:lens` uses the same predicate through `onBand` to choose between the band and the pane. One predicate, so the command and the hook cannot disagree. In VS Code, or with the surfaces unknown, the pane is the view and no lens band is drawn, except while the person chose pinned: the second lens band the human saw is gone.
- `AbovePrompt` itself is raised in VS Code (the probe). The gate is the lens's own decision, not a limit of the host. Keep-alive's band is not gated (keep-alive LLD, 26.1), so in VS Code the order above the prompt is: auto-handoff's panel, keep-alive's band, with the lens in the pane region.
- `surfacesNow($)` reads the roster per render of the band hook; whether that cost is worth a cached copy is not decided here (code review's open suggestion, entry 2ez).
