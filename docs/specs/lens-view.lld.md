## 3. The view follows the placement (R44.9, R44.10)

### 3.1 The rule

The lens does not move its panes; the surface does (F1, F2). The lens keeps what is shown consistent with where the surface has put the region (its **seat**, the pane's `placement`: `inline` or `dock`). On each change of seat it does three things: it sets the view's place to match (3.2); on `inline` it closes the Run List tab (`RUNS`), so the view is exactly one lens pane; on `dock` after `inline`, in VS Code, it lays the panel out as `/ai-dlc:lens` lays out a wide one, in both panel types (R44.19), and in Tab mode only it opens the Run List tab (R44.12, R44.14). Panel Type (the `panelOpenMode` setting, read with `openModeOf`) is Tab or Drill in; the Run List tab exists only in Tab mode.

| Transition (the lens pane's `placement`) | What the surface does | What the lens does |
|---|---|---|
| inline to dock (the panel grows from narrow to wide), R44.9, R44.12, R44.14, R44.19 | docks the whole region; the lens tab goes with it to the right pane | sets the place to `docked` (VS Code, R44.15). In **both** panel types it lays the panel out as `/ai-dlc:lens` lays out a wide one: the workflow tab on the newest run, its default steps open, so the current step's flowchart is drawn in the right pane (R44.19, R44.20). In **Tab** mode it then also opens the Run List tab without focus, so the workflow tab stays shown (the Run List tab inactive, the current run active). In **Drill in** mode it opens no Run List tab (R44.14). |
| dock to inline (the panel shrinks from wide to narrow), R44.10, R44.15 | moves the region back above the prompt; the right pane closes; the lens tab is in the band-position again | sets the place to `pinned` (VS Code, R44.15) and closes the Run List tab, so the view is one lens pane again |

Keep-alive is not in this region (its own band, keep-alive LLD 26) and so is never moved or closed by a resize.
The open on docking is unasked (d.ts `UiOpenResult`: "never a timer"), so the host places it only from 144 columns, or from 110 once the person has opened the Run List tab and not closed it by hand; below that it keeps the tab open but undrawn until the panel widens or the person opens it. The result is logged (`plog` `E3`, `via: 'docked again'`). The human accepted this (R44.12).

### 3.2 Mechanism

- Input: the `placement`, `bodyColumns` and `surface` of a lens Pane render, read in the Pane hooks of `CHART` (`R:4560`) and `RUNS` (`R:4572`), recorded by `notePaneSeat(placement, columns)` (module memory, no state write, `paneSeat`, also read by `commandSeatOf`), then `followSeat($, placement, surface, pinnedBand)`; `pinnedBand` is `await read($, vscodeBandA)` (a state read is allowed while drawing).
- Memory: `let lastSeat: 'dock' | 'inline' | null` (`R:1515`), `null` on load and reset to `null` by `placePress` (3.4). It is memory, not an atom: a state write while drawing is denied (F5, F7).
- `followSeat($, placement, surface, pinnedBand)` (`R:1549`): an unknown `placement` does nothing. (a) When `pinnedBand` is true and no hand-over is under way (`bandGivingWay`, a module `let` boolean, `R:1547`), a lens pane is being drawn while the person chose pinned (a pane opened another way): the band gives way. It sets `bandGivingWay`, then, through `afterRender`, sets `vscodeBandA` to `false` and the view's place to `docked` (seat `dock`) or `pinned` (seat `inline`). **`bandGivingWay` is cleared in the act, after both writes succeed, or by the act's `gaveUp` callback when `afterRender` gives it up. It is never cleared between the retries of a refused act**, so the renders in that window ask for no second hand-over. There is no `finally` any more (G4 fix round, 44.2.l1.10): a `finally` would have cleared the flag on the first refusal and let a later render start a second hand-over. (b) When the seat equals `lastSeat` nothing more happens. Otherwise `lastSeat` takes the seat and `afterRender($, 'seat follow', () => seatChanged($, seat, was, surface))` is scheduled. One act per change of seat, not per render.
- `seatChanged($, seat, was, surface)` (`R:1583`), outside the render: in VS Code (`surface === 'vscode'`) it sets the view's place: `docked` for `dock`, `pinned` for `inline` (R44.15). On `inline` it closes `RUNS` and returns. On `dock` it returns unless `was` is `inline` and the surface is `vscode`. Then, in both panel types (R44.19), it takes `w`, the newest run (`latestFlow`), sets the view with `commandOpenView(view, 'dock', w)`, and, when there is a run, clears the open-card and step-selection keys of `w` (`withoutStepKeys` and the `stepSelA` entry), so the default steps are open and the current step's flowchart is drawn in the right pane (R44.20). Only then, in Tab mode (`openModeOf(...) === 'tab'`, R44.14), it opens `RUNS` with `$.ui.open({ id: RUNS, title: RUNS_TITLE, closeOnEscape: true })` and no focus, and logs the result (`plog` `E3`, `via: 'docked again'`); in Drill in mode it returns there.
- `afterRender($, site, act, gaveUp = () => {}, tries = AFTER_RENDER_TRIES)` (`R:1529`; constants `AFTER_RENDER_TRIES = 20` and `AFTER_RENDER_RETRY_MS = 100`, `R:1526-1527`; `isRenderDenial`, `R:1528`) (R44.17): runs `act` with `$.clock.after(0, ...)`, just after the render that asked for it. If `act` rejects with a refusal of the render kind (`isRenderDenial`, `R:1528`: the message matches `/ui\.render is being dispatched|drawing is pure/`) and tries remain, it schedules the whole act again with `$.clock.after(100, ...)`, `tries - 1`; any other error, or the last refusal, goes to `lensFail(site, err)`. It never throws (a throwing `$.clock.after` is caught and logged the same way). Every act given to it must be safe to repeat. `gaveUp` is a callback with no arguments, the 4th parameter (added in the G4 fix round; `tries` moved from 4th to 5th, and the recursion passes both). It runs exactly once when the act is given up: on any failure that is not a render refusal, on the last refusal, or when scheduling itself throws. It runs before `lensFail(site, err)`. It does not run when the act succeeds. Its one use is `bandGivingWay` (above). The default is a no-op, so the seat follow and the band ping pass none. It wraps the seat follow (`R:1579`), the band hand-over (`R:1563`) and the band ping of `pingBandSoon` (`R:1623`).
- Why: the first built form, `$.clock.after(0, ...)` only, was refused intermittently ("state.set: denied ... while the ui.render is being dispatched", live findings 4), because a timer fired while a later render was dispatched (F7). The first write of `seatChanged` is the place update, so when it was refused the act stopped before it laid out the workflow view, and the docked pane kept the minimised list: the step chart was not drawn. That is the cause of R44.18; no separate fix was needed. The Run List close and open are `$.ui` acts (allowed from a timer, d.ts 2538); the state writes are the ones the retry protects. The layout of the workflow view no longer depends on the panel type, so a refused first write still costs the same flowchart in both.
- Residual: the host's open of the Run List tab is unasked (3.1), so it may stay undrawn below the floors.

### 3.3 `/ai-dlc:lens` (unchanged, stated for the whole picture)

The command picks the seat from the last drawn lens pane: `commandSeatOf(seen, wideColumns)` is `dock` only for a docked pane at a wide width (the Run List and workflow tabs open), else `inline` (one pane, the minimised list; the safe choice for a narrow panel). On a surface with no lens band it opens the pane; on a surface that draws the band it follows the pinned or docked rules of 43.2, 3. The command and the seat follow on docking (3.2) are the only places the Run List tab is opened. Step 44 (R44.14), `openLens` (`R:1393`): in VS Code, seat `dock`, the command opens the Run List tab (inactive) and the workflow tab (active) only in Tab mode (`openModeOf(...) === 'tab'`, `openRunsTab`); in Drill in mode it closes an open Run List tab and opens the workflow tab alone (`openWorkflowPane`). The same rule as `seatChanged` (3.2); it holds in an already-wide panel too.

**The seat rule (R44.23, decision 6).** `openLens` reads `const vscode = (await ownSurface($)) === 'vscode'` and takes `seat = vscode ? commandSeatOf(paneSeat, wideColumns) : 'dock'`. The VS Code seat rules (`commandSeatOf`, the Run List tab in Tab mode, closing `RUNS` in Drill in mode) apply only when the **session's own surface** (A1) is `vscode`. In a terminal or Desktop session with VS Code attached, the seat is always `dock` and the Run List tab is never opened (the condition `seat === 'dock' && vscode && tab` is false), whatever `paneSeat` and Panel Type say. Before 44.2.l1.11 these rules applied whenever VS Code was attached. When the own surface is null (nothing draws, a `-p` run), `vscode` is false and the seat is `dock`. Whether the pane opens at all is decided by `onBand` (3.4, 3.6).

### 3.4 The mode button (`pane-place`): docked and pinned, option a (R44.15, R44.16)

- **The button acts by the surface it was pressed on and by the session's own surface (R44.16, R44.23 amended, decision 7; the press-surface rule ratified as decision 8, narrowed by decision 13: for a session whose own surface is `vscode`, a press on the terminal band takes the VS Code path).** `placePress($, place, where, pressSurface?)` (`R:1331`) is called from the `pane-place` Button as `placePress($, place, where, press?.surface)` (`R:3134`). `pressSurface` is `press.surface` (A3); it is `undefined` when the press carries no argument.
  1. **The own-surface path, as in a terminal alone (`changeView`).** The press surface may be any surface other than `vscode`, for example `mobile`: such a press toggles the place as a terminal press does (register.tsx:1333; 2026-11-01 code review round 2). That `mobile` press is decision 14's: planned for the mobile epic (3.6). Taken when `pressSurface !== 'vscode'` and `ownSurface($)` is `terminal` or `desktop` (an entry of `BAND_SURFACES`). The place is toggled with `changeView` (`pinned` to `docked` and back). `vscodeBandA` is not touched. A press with no argument in a terminal or Desktop session takes this path. While a VS Code panel is attached, the pane stays open either way (3.6).
  2. **The VS Code path (R44.16).** Every other case: a press from `vscode` in any session (including a VS Code panel attached to a terminal or Desktop session), or a session whose own surface is `vscode`, or none of the three (`null`, or another surface such as `mobile`; 2026-11-01 code review round 2). The mobile case is decision 14's (3.6). `lastSeat` is set to `null` first, so the next lens pane drawn applies its seat afresh (R44.15). From the pane (`where` is not `'band'`; pressed as `pinned`): it closes `RUNS` and `CHART`, sets the view's place to `pinned`, `bandClosedA` to `false`, `vscodeBandA` to `true`, and starts the band minimised (`bandStart`). From the band (`where === 'band'`; pressed as `docked`): it sets `vscodeBandA` to `false` and the place to `docked`, and opens the pane as `/ai-dlc:lens` opens it (`openLens`). A press is the person asking, so the pane is placed at any width.
  3. **Consequence.** The VS Code panel of a terminal or Desktop session has a lens view while pinned: the pane or, after its own mode press, the VS Code band. Only a person's manual close can leave it without one (decisions 10, 11 and 12, 3.6). A press from `desktop` in a `['vscode', 'desktop']` session takes path 2, because the own surface is `vscode`.
- `vscodeBandA` (`R:296`: `atom({ plugin: 'ai-dlc-lens', key: 'vscodeBand' }, false)`, declared in `types/index.d.ts`) records that the person chose pinned in VS Code with the pane closed. `bandAllowed($, surface?)` (`R:1316`) is the band's gate, used by the `AbovePrompt` hook (`R:4603`) as `bandAllowed($, e.surface)`. With a `surface` that is `terminal` or `desktop` (`BAND_SURFACES`), it returns `true` whatever else is attached, and also when the roster is unknown (R44.21, decision 1). With any other surface, or none, it keeps the older rule `bandEverywhere(await surfacesNow($)) || (await read($, vscodeBandA))`, so a VS Code render works as in revision 3 (R44.4, R44.16). The commands (`onBand`, `showView`, `placePress`) pass no surface; they use `viewBandOnly` (3.6). R44.4 ("the lens shows no band of its own in VS Code") is relaxed only while the person chose pinned and the lens pane is closed.
- The two lens views never show at once: any lens pane that is drawn while `vscodeBandA` is true makes the band give way (`followSeat`, 3.2, (a)). In a narrow VS Code panel the pane sits above the prompt too, so the button switches between the pane and the band, both above the prompt, and the mode reads `pinned` either way.
- The note "pinned: this surface has no band above the prompt, so the view stays a pane." no longer shows in VS Code (`R:3484`: the condition is `site.where === 'pane' && place === 'pinned' && !BAND_SURFACES.has(site.surface) && site.surface !== 'vscode'`).
- R44.20: the band chosen with the mode button draws no step flowchart in VS Code either (3.5); its `⤢` opens the right pane on that step only while the panel is wide.

### 3.5 Where a step's flowchart is drawn in VS Code (R44.20)

- Rule: in VS Code a step's flowchart (`chartNode`, with `chartInPane` on) is drawn only in a lens pane the host seats `dock`, the right panel. Never above the prompt: not in the pane seated `inline`, not on the band the mode button chose. Terminal and desktop are unchanged (their band and panes draw it).
- Why: no plugin can widen the Claude panel. None of the `$.ui` operations sizes a surface (d.ts 2382-2640), `PaneOpenArgs.columns` (7646-7657) only sizes the dock, and a plugin can only read the width (`viewport`, `bodyColumns`, `placement`). So the design shows how to get the chart (widen the panel by hand) rather than drawing it small or opening the right pane at a narrow width.
- Mechanism, in the step chart function of `workflowBody` (`R:3580-3629`): `chartOff = site.surface === 'vscode' && !(site.where === 'pane' && site.placement === 'dock')` (`R:3580`). When `chartOff` and the step is open (and `chartInPane`), the chart is replaced by the dim line `Widen the Claude panel to see the flowchart in the right panel.` (`R:3629`); the heading, `Stop turn`, `–`/`□` and the agent buttons are unchanged. With `chartInPane` off, no chart and no line.
- The full-screen control: `fullOff = chartOff && !(site.where === 'band' && site.wide === true)` (`R:3583`). When `fullOff`, `⤢` is drawn as dim `Text`, not a `Button`, because ButtonProps has no disabled flag (d.ts 1093-1198), so it cannot be pressed and writes nothing (`R:3608`). On the band in a wide panel it stays a Button: a press stores the step as the chosen one and opens the right pane on that workflow (`expandBand`), where the chart is drawn. `site.wide` is new on `ViewSite` (`R:3306`); the band hook sets it from `e.viewport?.isFullscreen === true` (`R:4613`, the same signal the pane's seat follows); the pane sites do not set it (a pane is `inline` or `dock`, and `chartOff` already follows its `placement`).
- Both values are pure functions of `(surface, where, placement, wide)`, so the table in 6 tests them without a host.

### 3.6 The session's own surface and the commands (R44.21, R44.23)

- **`ownSurface($)`** (`R:1248`): `(await surfacesNow($))[0] ?? null`. The first of `$.session.surfaces()` (A1); `null` when the list is empty or `surfaces()` throws (`surfacesNow` returns `[]` and never throws). It exists because `command.run` and a button press with no argument carry no surface of their own.
- **`viewBandOnly($)`** (`R:1302`): whether a pinned view is the band alone, so `/ai-dlc:lens` and the mode button open no pane. With `all = surfacesNow` and `own = all[0] ?? null`: `true` when `own` is `terminal` or `desktop` **and `vscode` is not in `all`**; otherwise it returns `bandAllowed($)` (the roster rule and `vscodeBandA`). Truth table (pinned, `vscodeBandA` false unless stated):

## 4. `runListStatus` (R44.5)

```ts
// L:1554
export function runListStatus(members: readonly StatusMember[], runStatuses: readonly string[] = [], spawner: string | null = null): FlowStatus
```

- Rule: `runListStatus` is `workflowStatus(...)` except that a result of `completed` becomes `waiting` when **any listed run's status, trimmed and lower-cased, is not `done`**: `active`, an empty string, or a status the lens does not know (R44.22 extended, decisions 2 and 5; before 44.2.l1.10 only `active` did this). With no run named (`[]`), the agents decide, as in `workflowStatus`. Every other result (`halted` for a `blocked` run or a failed or killed agent, `in-progress`, `waiting`, `pending`) passes through unchanged. `workflowStatus` keeps its own order: `blocked` run, then all runs `done`, then failed or killed agents, then running, waiting, pending, completed.
- The old fault: `workflowStatus` returned `completed` as soon as every agent had ended, whatever the run said (`L:1542`, as of 2026-10-31, before step 44). A run waiting for its next stage or for the human is not completed, so it reads `waiting`.
- **In progress:** the per-agent halted rule (step 44.2.l2.1, ITEM-104). A subagent whose turn ends with `error`, `refusal` or `aborted` becomes `failed` or `killed` only when `$.agent.list()` also lists it as ended (`ENDED`); otherwise it stays `running`, and a later listed `failed` or `killed` still applies. A later listed `running` clears a halt that came only from such a turn end (`haltedByTurn`, `refreshList`). The main agent and teammates are unchanged. **Dropped subagent (decision 16, step 44.2.l2.2, ITEM-104):** a subagent stored `running` that `$.agent.list()` no longer lists, and that has sent no event since, becomes `failed` once `droppedSubagentMinutes` has passed while it is missing (default 15; 0: never; whole minutes 0 to 1440). The time counts only while it is missing: a listed row or any event of the subagent (`heard()`) restarts it, and a subagent the list still shows is never timed out. A halt from this timeout is marked in `haltedByTimeout` (step 44.2.l2.3; before, in `haltedByTurn`): any event of the subagent (`heard`, called from `turn.start`, `turn.step`, `tool.call` and `turn.complete`) or a listed `running` brings it back to `running`. A halt the list confirmed first (`failed` or `killed`, with no timeout halt before it) is not undone by a step, a tool call or a turn end of the agent; the agent's own turn start sets it running again (decision 23, `56-human-decisions.human.md`). **Known limit (decisions 21 and 22, `55-human-decisions.human.md`):** a subagent the timeout halted, which the agent list later reports `failed` or `killed`, keeps its timeout mark, so a later event of its own can still bring it back to `running`; ITEM-106 fixes it. The timeout reads the engine's clock (`$.clock.now()`, read once in `refreshList` before its write, so the updater gets it as a value and `nowMs()` no longer stamps it). Where that rejects, the wall clock stands in and, while the `probes` setting is on, an E4 probe line `clock: 'wall'` is written to `PROBE-LOG.jsonl` (`register.tsx:1124-1127`). When the list call throws, no timeout runs. **Pure updater (decision 17, step 44.2.l2.4):** `refreshList`'s `update` calls `mergeAgentList(agents, list, t, limitMs, marks)` (`lens.ts:825`), which stamps the listed children, applies the listed statuses and calls `planDrops(agents, listed, t, limitMs, missingSince)` (`lens.ts:789`). Both are pure: they read the marks as parameters and write neither their inputs nor the marks, so the engine may run the updater again on a version miss, and a test may call them twice on one frozen input. The apply block after `update` has written (`register.tsx:1139-1149`) is the only place `refreshList` writes `haltedByTurn`, `haltedByTimeout` and `missingSince`. **Known limit (decision 17, `52-human-decisions.human.md`):** the three marks live in module memory, apart from the agent row they describe, so a narrow race between the marks and the row remains. ITEM-106 moves the marks into the row; its decision is written as [ADR-0009](../architecture/decisions/ADR-0009-lens-marks-that-guard-an-agents-status-live-in-its-row-in-agentsa.md) (Accepted, implementation pending ITEM-106). **Known limit (ITEM-104):** a subagent the list keeps showing as running stays in progress until the list drops or ends it. Code: `register.tsx:362`, `:369` and `:377` (`haltedByTurn`, `haltedByTimeout` and `missingSince`), `:384-388` (`heard`, whose `failed` guard is removed, decision 18), `:4402`, `:4441`, `:4511` and `:4528` (its calls in `turn.start`, `turn.step`, `tool.call` and `turn.complete`), `:1105` (`refreshList`, above), `lens.ts:789` (`planDrops`), `lens.ts:825` (`mergeAgentList`), `settings.ts:134-140` (`droppedSubagentMinutes`).
- The run's status is that of its **current** run-state version: the newest version wins (`pickRunState`, `L:2774`; `readRunState`, `R:688`). Nothing changed there: the human's R44.5 ("the newest run-state version wins").
- Who calls which: the run list and the band take `runListStatus` (the run-list builder at `R:2183`: `status: runListStatus(settled, dirs.map(d => runs[d]?.status ?? ''), batch.parent)`). **A step's chart heading takes it too (R44.22, decision 2).** `stepLook` (`R:3547`) returns `{ st: runListStatus(all, [run?.status ?? ''], spawner), both: ... }`, where `run` is the run-state entry of the chart's run, if any. When the run has no readable run state (records but no `run.md` or `run.v*.md`), `run` is undefined and the list is `['']`, exactly as the run list names such a run. So the finished steps of that run read `waiting`, never `completed` (decision 5). This replaces the earlier step-44 rule that kept `workflowStatus` for the chart and the accordion ("a finished step of an active run is `completed`"). It amends 43.2, 6.4 again: the band, the run list and the step charts now take the same inputs and the same function. `workflowStatus` itself is unchanged.
- Truth table (members all ended, no failed or killed agent): `[]` gives `completed` (no run named); `['done']` gives `completed`; `['active']`, `['']`, `['paused']`, `['done','']` give `waiting`; `['active','done']` gives `waiting`; `['blocked','active']` gives `halted`. A run with a failed agent is `halted` whatever its run state says (as before). In the minimised list the precedence is in progress, waiting, halted, pending, completed (the human, entries 2dd and 2de), so an active run now sorts above a halted one.

## 5. One lens view per surface, and the band gate (R44.4 revised)

- The lens band (the `AbovePrompt` hook, its gate at `R:4603`) is drawn by a render when `bandAllowed($, e.surface)` holds (3.4): the render's own surface is `terminal` or `desktop` (R44.21), or, for any other surface, every attached surface draws the band (`bandEverywhere(surfaces)`, `L:2231`, true when the surface list is non-empty and every entry is in `BAND_SURFACES`, `terminal` and `desktop`, `L:2227`), or in VS Code the person chose pinned with the mode button (`vscodeBandA`, its pane closed). `/ai-dlc:lens` and the other commands do not use that predicate: they use `viewBandOnly` (3.6).
