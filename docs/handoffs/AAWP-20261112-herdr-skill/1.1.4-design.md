# Design: herdr skill and herdr panes for spawned agents

## 1. Problem and constraints

Inside herdr (herdr.dev), the orchestrator's subagents and teammates should be visible, each in its own labelled pane (watch mode), or should run as their own `claude` process in a pane (run-in-pane mode). Outside herdr, nothing changes.

Constraints that shape the design:

- **C1. Hooks only observe.** SubagentStart, SubagentStop and TeammateIdle carry `agent_id` and `agent_type`, and SubagentStop adds `agent_transcript_path` (1.1.2). None of them carries the step code, which lives only in the orchestrator's brief. So a hook cannot label a pane "agent + step" (AC-6).
- **C2. Run-in-pane replaces the `Agent` call**, so it has to be driven by whoever spawns, and that is the orchestrator.
- **C3. Agent teams are internal to Claude Code.** A teammate cannot be an external `claude` process that we start: membership, `SendMessage` and the shared task list belong to the lead session (`request-routing`, Mode 5 conditions).
- **C4. The orchestrator runs no checks** (`orchestrator.md:80-84`). Driving panes is not a check, but it needs an explicit, narrow exception, as reading the workflow has.
- **C5. AC-9: a pane must never block a run.** Every herdr call is best-effort, has a short timeout, and its failure is reported, never raised.
- **C6. Windows native (AC-15)** has no `terminal attach`, and its socket is a named pipe. The design must rely only on CLI commands whose Windows behaviour is confirmed (see §8).
- **C7. Settings follow the plugin pattern:** `.ai-dlc/<name>.json` plus `AI_DLC_*` variables, no `/config` rows (`configure-auto-handoff/SKILL.md:22-34`).

## 2. Decisions (summary)

| # | Decision | Traces to |
|---|---|---|
| D1 | One actor: the orchestrator drives every pane through one Node script in the skill, `skills/herdr/scripts/herdr.mjs`, with one `Bash` call per action. Not a hook, and not raw `herdr` commands written by the model (ADR-0010). | C1, C2, C4, C5 |
| D2 | **Watch mode:** `open` before the spawn and `close` after the hand-back (subagents) or after shutdown (teammates). Nothing closes a pane on idle. The pane runs the script's `watch` view. | AC-6, AC-7, AC-8 |
| D3 | **Watch progress** has two layers. The base layer is the run folder (the handoff record, then each record to or from that agent, and the time elapsed), which works for both subagents and teammates. | D4 | **Run-in-pane mode:** the script starts `claude -p --agent ai-dlc:<id>` in a pane through a child wrapper. The wrapper streams progress into the pane and writes the final result to a **result file**. The orchestrator reads that file, never the pane text. | AC-10, AC-11 |
| D5 | **Fallbacks:** herdr is unusable before the launch → spawn with the `Agent` tool and say so. A run that fails after the launch (no result, an empty result, a non-zero exit or a timeout) → a failed hand-back is recorded, then the same step is spawned with the `Agent` tool. | AC-11, AC-12 |
| D6 | A **Mode 5 (agent team) stage always uses watch** behaviour, whatever the setting, and the Routing Plan says so. | C3, AC-10 |
| D7 | **Setting:** `.ai-dlc/herdr.json` holds `mode` (`watch`, the default, or `run-in-pane`) and `runTimeoutMinutes` (default 60). | D8 | **Activation:** the script's `detect` checks `HERDR_ENV=1`, then `herdr` on PATH, then that the server answers. Any miss makes it a silent no-op: exit 0, `{"active":false}`, no output on stderr. | AC-4 |
| D9 | **Scope:** only the orchestrator's own spawns get panes. Nested spawns (for example sqa-engineer's sub-suites) do not. | AC-6, AC-13 |

## 3. Components

```
orchestrator (main session, inside a herdr pane)
  │ Bash: node <herdr skill dir>/scripts/herdr.mjs <cmd> ...
  ▼
herdr.mjs ──── herdr CLI (pane split / rename / run / close; server ping) ──► herdr server (socket / named pipe)
  │   ├─ state: .scratch/herdr/<run-id>/panes.json   (step+agent → pane id, mode, started)
  │   └─ settings: settings.local env > settings env > process env > .ai-dlc/herdr.json > default
  │
  ├─ watch    (runs IN the pane)  reads run folder (+ transcript if found) → prints progress
  └─ child    (runs IN the pane, run-in-pane only) spawns `claude -p --agent ai-dlc:<id>` → progress to pane, result → result file
```

### 3.1 `herdr.mjs` commands (the contract system-engineer details)

Every command prints exactly one JSON line on stdout. It exits 0 on every outcome caused by herdr, including a failure, which it reports as `{"ok":false,"reason":...}` (AC-9). It exits non-zero only on a usage error. Every `herdr` call has its own timeout (5 s suggested).

| Command | Purpose |
|---|---|
| `detect` | `{"active":bool,"mode":"watch"\|"run-in-pane","source":..., "reason":...}`. The orchestrator calls it once per run (Run Loop step 1) and records the result in the run state. |
| `open --run <dir> --step <code> --agent <id> [--record <path>]` | Watch: creates a pane labelled `<agent> <step>`, starts `watch` in it without stealing focus, and stores the pane id. Several `--step/--agent` pairs may be given in one call, for a parallel fan-out. |
| `close --run <dir> --step <code> --agent <id>` | Closes the stored pane and removes its entry. It is idempotent: an unknown or already closed pane gives `ok:true`. |
| `run --run <dir> --step <code> --agent <id> --record <path> --out <path> [--worktree <name>] [--timeout <min>]` | Run-in-pane: opens the pane, starts `child` in it, and blocks until the result file appears or the timeout passes. It returns `{"ok":true,"result":"<path>","exit":n}` or `{"ok":false,"stage":"launch"\|"run","reason":...}`. `stage:"launch"` means the agent never started (→ fallback). `stage:"run"` means it started but gave no usable result (→ failed hand-back, then fallback). |
| `watch ...` | Runs inside the pane only. |
| `child ...` | Runs inside the pane only. |
| `show` / `set <key> <value>` / `validate` | Read and change the setting, as `auto-handoff.mjs` does. |

Run-in-pane runs in the foreground: `run` blocks inside the orchestrator's `Bash` call. A parallel fan-out uses one `Bash` call per agent with `run_in_background`, or `run` with several pairs that waits for all of them. system-engineer picks one. The Bash tool's own timeout (10 min maximum) is shorter than `runTimeoutMinutes`, so a background call is the default.

### 3.2 Watch mode flow (D2, D3)

Subagent:
1. The orchestrator writes the handoff record and updates the run state (unchanged).
2. `herdr.mjs open --step 1.2 --agent agent-manager --record <path>`. On `ok:false`, it notes one line in the run state and goes on.
3. `Agent(...)` exactly as today.
4. The orchestrator stores the hand-back (unchanged), then calls `herdr.mjs close --step 1.2 --agent agent-manager`.

Teammate (Mode 5): `open` when the lead spawns each teammate, and `close` only after the lead has had the teammate's shutdown confirmed. TeammateIdle is never consulted, so AC-8 holds by construction: no code path closes on idle.

The progress view (`watch`) re-reads every 2 s, and only by reading:
- the header: agent, step, label and elapsed time; the first lines of the handoff record (its `## Your task`);
- run-folder events: every `*-<agent>-to-*` and `*-to-<agent>.*` record that appears after the pane opened, with its file name and time. For a teammate this follows its handoffs to other teammates, which is real progress;
- transcript tail (D3, layer 2): the last N assistant text and tool-use lines of the agent's transcript, found by the matching key **the handoff record path appears in the first user message** (every brief starts with that path, `orchestrator.md` step 8). This key is unique across parallel spawns. Where transcripts live is not yet verified (clarify Q2). If the transcript cannot be found, layer 2 is left out silently.

`watch` exits on its own once a hand-back from that agent for that step exists, as a safety net when `close` was missed. It never writes anything.

### 3.3 Run-in-pane flow (D4, D5)

1. Write the handoff record and update the run state as today, with the stage recorded as `mode: subagent (herdr run-in-pane)`.
2. `herdr.mjs run ... --out .scratch/herdr/<run>/<step>-<agent>.result.md`.
3. Inside the pane, `child` spawns `claude` with an argument array (no shell, so no quoting problem on Windows): `-p <prompt> --agent ai-dlc:<id> --output-format stream-json --verbose`, plus `--worktree <name>` when the brief asks for isolation. The prompt is the same one-line brief the `Agent` call would get: "Handoff record (read first; it is your brief): <path>. …". `child` renders each stream event as one line in the pane, then writes the final `result` text to `<out>.tmp` and renames it to `<out>` (an atomic write), plus `<out>.exit` holding the exit code.
4. The orchestrator copies `<out>` verbatim into `<code>-<agent>-to-orchestrator.handback.md` and verifies line 1 as usual (AC-11 unchanged).
5. Failures:
   - `stage:"launch"` → spawn with `Agent(...)` and record "herdr run-in-pane unavailable: <reason>; spawned with the Agent tool" in the run state (AC-12).
   - `stage:"run"` → store a hand-back whose line 1 is `handoff <file>: failed — herdr run-in-pane gave no result (<reason>)`, then spawn the same step with `Agent(...)`. The result is never treated as success (AC-11). The retry is the same stage, not a loop round.
6. The pane closes when the result has been read. On a failure it stays open, for the human to inspect, and the run state names it.

Known limits, documented in the skill, not hidden:
- **L1.** `claude -p` cannot answer permission prompts. The child has the project's settings and permission rules, but not the permission mode of the interactive session. A tool it may not use is denied, and the agent reports it. (The exact flag behaviour is clarify Q4.)
- **L2.** The child's hand-back is the final `result` text. Anything the agent "returns" any other way is lost. Plugin agents already end with their report, so this is fine.
- **L3.** Agent teams cannot run this way (D6).
- **L4.** A `claude` process costs its own session start, and a cold prompt cache for its system prompt.

### 3.4 Mode 5 (D6)

When the setting is `run-in-pane` and a stage is routed to Mode 5, `request-routing` keeps the team and marks the stage `team (herdr watch)` in the Routing Plan. The alternative (forcing the stage to Mode 3 to honour run-in-pane) was rejected: it would let a display setting change the orchestration mode the routing chose for real reasons.

## 4. Why the orchestrator, not a hook (ADR-0010)

| Option | Label with step (AC-6) | Run-in-pane | Teammates | Model forgets | Cost |
|---|---|---|---|---|---|
| A. Hook in the hooks module (classic.SubagentStart/Stop) | no: no step in the payload (C1) | no: hooks cannot replace the spawn | unverified event coverage | n/a | new TS surface in `hooks/auto-handoff` |
| B. Orchestrator runs raw `herdr` commands | yes | yes | yes | yes | ids, quoting, Windows differences and timeouts handled by the model each time |
| **C. Orchestrator calls one script (chosen)** | yes | yes | yes | yes; a missed `close` is caught by `watch` exiting itself | one script and its tests |

C keeps every herdr detail (ids, timeouts, Windows, JSON parsing) in tested code and leaves the model one line per action. What C accepts: a pane may be missing if the orchestrator skips `open`. AC-9 already says that a missing pane is harmless.

## 5. Setting (D7)

- File: `.ai-dlc/herdr.json`, `{"$schema":"./herdr.schema.json","mode":null,"runTimeoutMinutes":null}`, where `null` means "not set here". The schema is shipped as `skills/herdr/templates/herdr.schema.json` with `x-env` per key, and `set` copies it to `.ai-dlc/` (the same pattern as `auto-handoff.schema.json`).
- Precedence: `env` of `.claude/settings.local.json` > `env` of `.claude/settings.json` > process environment > `.ai-dlc/herdr.json` > default. An invalid value is reported by `show` and `validate`, and the next level applies.
- No workspace-trust gate. Neither key can make the plugin do anything the `Agent` tool would not: `run-in-pane` starts the same plugin agents under the same project permission rules. The skill states this reasoning.
- No `off` value: AC-5 names two values. To turn herdr off inside herdr, unset `HERDR_ENV`. Whether to add `off` is open question O1, for the product owner.
- No separate configure skill. The `herdr` skill documents `show`, `set` and `validate`.

## 7. Risks

| Risk | Mitigation |
|---|---|
| The orchestrator forgets `close` | `watch` exits itself when the hand-back appears; `close` is idempotent; a pane is cosmetic (AC-9) |
| Many parallel panes shrink the layout | panes go into one herdr tab per run (labelled with the run id) when tab targeting is confirmed (Q1); otherwise split from the orchestrator's pane |
| `claude` is a `.cmd` shim on Windows, so a spawn with no shell fails | `child` resolves the executable (system-engineer: a `where` lookup or `shell:true` with escaped arguments); tested on Windows |
| The transcript layout changes in Claude Code | layer 2 is optional and fails silently; layer 1 needs only our own records |
| A run-in-pane agent hangs | the timeout → `stage:"run"` failure → a failed hand-back and the `Agent` fallback; the pane is kept for diagnosis |

## 8. clarify: research-assistant (facts this design needs; nothing below is assumed)

- **Q1.** herdr v0.9.5 CLI, Linux/macOS and Windows native: the exact syntax and JSON output of `pane split` (can it target a tab or pane other than the caller's? `--cwd`, `--no-focus`, the `.result.pane.pane_id` path), `pane rename`, `pane run`, `pane close`, `tab create --label` (the id of the tab it returns). Sources: herdr.dev CLI reference, `herdr api schema --json` output, the release notes.
- **Q2.** Claude Code: where a subagent's transcript is written while it runs (path pattern relative to the main session's `transcript_path`, for example `<session>/subagents/agent-<id>.jsonl`), and whether teammates write a transcript the lead's machine can read. Can a process started from the session's `Bash` tool learn the session id or transcript path (an environment variable)?
- **Q3.** Does `claude -p --agent <plugin>:<agent>` load a plugin agent's definition (tools, model, body) as `--agent` does interactively? Do `--output-format stream-json --verbose` events end with a `result` event that carries the final text? Is `--worktree <name>` valid together with `-p`?
- **Q4.** Which permission mode a `claude -p` child gets by default, and whether it inherits project `settings.json` allow rules (L1).
- **Q5.** On Windows, is `claude` installed as a `.cmd`/`.ps1` shim or as an `.exe` (native installer vs npm)? This decides how `child` spawns it.
