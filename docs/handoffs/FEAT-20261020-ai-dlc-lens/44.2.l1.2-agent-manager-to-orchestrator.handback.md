HOST FACTS
F1. A module cannot choose where a pane sits. The surface places every pane: "Placed by the surface (docked in fullscreen, else above the prompt)" (10871). `placement` is read-only on the Pane props (10897-10903). PaneOpenArgs has only id, title, focus, closeOnEscape, holdToasts, rows and columns (7589-7660): no placement, no "stay inline", no active tab.
F2. All panes form one framed region: "one instance per id …, one shown, the rest tabs" (10867-10868). The lens's and keep-alive's panes are tabs of the same region, so they always share one seat. VS Code moves that region between inline (narrow) and docked (wide) by the panel width; that is the surface's decision (15068-15073, "per surface").
F3. The band proper (AbovePrompt) is raised on the terminal and desktop only (10818), never in VS Code. In VS Code, the human's "band" is the inline pane region.
F4. There is no resize event. A module only sees a resize as a fresh `ui.render` of a site it draws, "once per input value (props, viewport width)" (4098). On a Pane render, `placement` and `bodyColumns` arrive as new props. The engine re-draws on a width change "once the resize settles" (10225-10226).
F5. A module cannot open or close a pane while drawing. State writes are refused while ui.render draws (3494); step 43's live error confirms it. Any reaction must be deferred out of the render (`$.clock.after`).
F6. Such a deferred open is "unasked": "never a timer" (15067-15069). An unasked pane is placed only from 144 columns, or 110 for an id the person has opened before and not closed by hand; below that it "waits undrawn" (15070-15074). A resize-driven reopen can therefore stay undrawn in a VS Code panel narrower than the floor.
