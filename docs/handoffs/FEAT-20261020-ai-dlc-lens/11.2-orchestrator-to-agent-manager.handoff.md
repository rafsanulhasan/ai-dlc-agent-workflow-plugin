# 26 — related work joins the parent run: the orchestrator's filing and numbering rule

## The human's request (2026-10-23), verbatim
"Suppose the User asked to do "A" action (feature). the task breakdown broke it to 4 tasks: a.1 - development, a.2 sqa, a.3 review: standards, a.4 review: requirements+acs. while the work is going on, the user asked for two more tasks:
B. related to "A" feature. it either goes to a different run or a different workflow. again task breaking into b.1, b.2 b3, b.4 — here is the bug: it should belong to task a (parent task) and should be named like a.5, a.6, a.7 and a.8 and should go to the same run as A did in the handoff. also new agent spawns should belong to the same flowchart as "A".
C. not related to A. It should get a completely different run and different parent task, and the flowchart should be in a different workflow as well."

## Decisions (human, 2026-10-23)
1. The fix is in **both** the orchestrator's rules and the lens (the lens part is a later step of this run, 27).
2. **Who decides related vs unrelated:** the orchestrator judges from the request (same feature, its files, its docs, its open run); when it is not clear, it asks the human one question before filing the work.
3. **Numbering:** a related request's work items continue the parent run's **top-level** step numbers (parent run at step 4 → B's items are 5, 6, 7, 8), in the parent's run folder; its agents land in the parent's flowchart.
4. Everything that follows from the same parent feature (follow-up fixes, reviews, rules it triggered, docs) belongs to that parent run. Example applied today: three runs opened for lens work were merged into `FEAT-20261020-ai-dlc-lens` as steps 19–25 (see `run.md`, *Merged runs*).
5. An unrelated request (C) gets its own run, its own numbering and its own flowchart, as today.
