## Recommendation (MAJOR): move the three marks into the agent rows in `agentsA`

Move `haltedByTurn`, `haltedByTimeout` and `missingSince` out of module memory and onto each `LensAgent` row in `agentsA`. They should be written by the same `update` that changes the row's status.

**Why the current design can't be right.** Each mark guards one status change of one agent:
- `haltedByTimeout` means "this `failed` may be undone".
- `haltedByTurn` means "a listed `running` may resume this".
- `missingSince` is what decides when the timeout halt happens.

So each rule ties a mark to a status. But the status is in an engine atom whose writes are conditional (`ifVersion`) and retried on a miss (`.tsc/claude-code.d.ts:15541-15552`). The marks are in module Sets and a Map (register.tsx:361, :368, :376) that are changed at other moments. One rule spread over two stores with no shared commit can't be kept atomic, however careful the order of the steps. Everything that is wrong now comes from that split:
1. **W-A only holds by convention.** The updater at :1133-1165 still reads module state while it runs: `haltedByTurn.has` / `haltedByTimeout.has` at :1153, and `missingSince` inside `haltDroppedSubagents` at :1196-1205. It defers its writes to :1166-1175. Being pure depends on everyone following that rule. The kit can't force a conflict, so no test can show it is broken (M2 survives).
2. **The known race.** An event can arrive between the write at :1133 and :1174 (`haltedByTimeout.add`). Its `heard` (:382-386) finds no mark and returns, so the agent stays halted until its next event.
   - A second window of the same kind: the `drops.start` apply at :1171 can run after a `heard` that came in mid-update, so the reset from that event is lost. The timer then counts from `t`, which is a little before the event. It is harmless, but it is the same defect.
3. **Lifetime mismatch.** `agentsA` is engine state and survives a plugin reload. This is the `shape` tag behaviour (d.ts:741-748): the engine keeps the value whole, and only a different tag declines it. The marks are lost on a reload. The comment at register.tsx:358-360 already records the result: after a reload, a halt is no longer cleared by a listed `running`.

**With the marks in the row**, for example `haltedBy: 'turn' | 'timeout' | null` and `missingSince: number | null`:
- `refreshList`'s updater becomes a function of `m`, the list, `t` and the limit only. Running it twice is harmless by construction. M2 can't even be written any more, so remove it from the mutant set rather than try to kill it.
- `heard` becomes one `patchAgent`: clear `missingSince`, and when `haltedBy === 'timeout' && status === 'failed'`, set `running` and `endedAt: null` and clear the mark. It is one compare-and-set write on the same atom, so the race at :1166-1175 is gone. The other side of the race now just loses `ifVersion` and runs again on the new value.
- `turn.complete`'s `haltedByTurn.add/delete` (:4621-4622) and `turn.start`'s `haltedByTurn.delete` (:4473) go into the `patchAgent` updaters those handlers already call (:4471, :4623).
- Apply blocks, `DropPlan` and the three module collections are deleted (:1130-1131, :1166-1179).

I rejected **a separate `marksA` atom**: `update` covers one atom, so the race between two atoms would remain.

### Trade-offs and constraints for system-engineer and agent-manager
- **Shape change.** `LensAgent` gains fields, so bump the atom's shape from `'agents-3'` to `'agents-4'` (register.tsx:239). The cost is that rows stored before a reload in the same session are dropped once. That is acceptable: the lens rebuilds from events and the list.
- **`session.start` behaviour must be kept.** Today it clears the marks (:4129-4131), and sqa has a test: "session.start clears the mark, so neither a listed running nor its own event revives it". As far as I can see, `session.start` does not reset `agentsA`. It reads it at :4141, and I found no write to `agentsA` in the handler. So the new design needs one `update($, agentsA, …)` there that clears the marks in every row. The marks would otherwise outlive `/clear`.
- **Redraws.** `missingSince` changes only when an agent goes missing or comes back, not on every poll. The updater already returns a new object on every poll (`stampTasks` at :1141). I expect no extra redraw cost; I have not measured it.
- **Rows carry bookkeeping.** Fixtures and deep-equal assertions on `LensAgent` may need the new defaults. `blankAgent` (:479-501) gets them.
- **`lastStatus`** (:353) stays in module memory. It only feeds the probe log (E4), which is diagnostic, so it is fine there. Rule of thumb: module memory may hold caches and diagnostics, never a fact that a status change depends on.

## The `clock.now` → `Date.now` fallback (MINOR): acceptable, with two notes
- Keep it. The d.ts says `clock.now` "Resolves milliseconds since the epoch" (:3516-3522), so in a real host the fallback gives the same epoch milliseconds and the behaviour doesn't change. Without it, a rejected clock would abort the whole poll, list included. That is worse than using the wall clock, and sqa's mutant M1 already tests it.
- It does shape production code around a kit limit. The alternative was a `clock.now` stub in every `boot` helper (44.2.l2.3, W-B). That is cleaner but touches every test file, so it isn't worth it now.
- Note 1, mixed clocks: inside the same updater, `stampTasks(..., nowMs())` at :1141 and `blankAgent.startedAt` at :496 use the wall clock, while `endedAt` and `missingSince` use `t`. In production they agree. Under sqa's driven clock, `endedAt - startedAt` can come out odd. If the updater is reworked anyway, have it use `t` for the stamp at :1141. That also makes a re-run deterministic.
- Note 2: the bare `catch {}` at :1123 hides a real host failure. A probe line (E4) when it falls back would make that visible. Optional.

## ADR: yes, but only once the human ratifies it
This passes the write-adr bar:
- It is surprising without context: someone will move the marks back into module Sets "to keep rows clean".
- It is a real trade-off: a shape bump and bookkeeping in rows, against atomicity and lifetime.
- It sets a rule for all lens state, not just this fix: state that guards a status change lives in the same atom as the status and is written by the same `update`; module memory holds only caches and diagnostics.

Proposed: **ADR-0009 "Lens marks that guard an agent's status live in its row in `agentsA`"**. That number is the next free one; ADR-0008 is the latest in docs/architecture/decisions/. I have not written it, because this brief is read-only and the human has not chosen the design. Have me write it once it is approved.

## Effect on the mutants (for system-engineer and sqa to confirm)
- **M2** can no longer be written and should be dropped. The updater's re-run can then be tested directly: a pure reconcile function, called twice on the same input, gives the same output.
- **M10** (turn.start's `heard`) stays equivalent, because turn.start sets `running` itself (:4471). Simplify it there.
- **M16** (`heard`'s `failed` guard): with the mark and the status in one row, the guard could be folded into the mark check. Whether it then becomes reachable or is dead code is system-engineer's call.
