Cache TTL attribution in keep-alive: findings (path:line refer to the uncommitted working tree; cache-state.ts and keepalive.ts were not in the sqa mutation diff as far as I could tell, but I did not diff against HEAD).

1. Fields read. Yes, both ephemeral fields are read. `creationSplit` reads `cache_creation.ephemeral_1h_input_tokens` and `cache_creation.ephemeral_5m_input_tokens` and returns undefined unless both are numbers (plugins/claude/ai-dlc/hooks/auto-handoff/config.ts:385-391; the comment at :383-384 says the mods API type does not declare the field). `splitOf` drops zero splits (keepalive.ts:85-88), and `splitFromTranscript` scans the transcript for the last non-sidechain row with a split (keepalive.ts:95-110). Fallback when `cache_creation` is absent: `creationSplit` returns undefined, so main records no write (cache-state.ts:60-64, :76). Agents get an `unknown` marker when `cache_creation_input_tokens > 0` (cache-state.ts:66). `cache_creation_input_tokens` alone never picks a TTL.

2. Reads. Read attribution is in `observe` (cache-state.ts:77-81). A read moves only the 5m entry, to at+5m, and only when that entry is still warm, the response wrote no 1h tokens, and no 1h entry is warm. Otherwise nothing moves. The 1h entry is never moved by a read. The spec states the same (docs/specs/keepalive-cache-status.spec.md:75-81). The code assumes reads are 5m unless proven otherwise. I did not verify against Anthropic's API docs that reads carry no TTL breakdown. The spec asserts it.

3. Mixed 5m and 1h. Each entry is kept per (source, TTL) (cache-state.ts:8-10, :18). Each track shows its own TTL's entry via `cacheView(ledger, t.name)` (keepalive.ts:170-174, cache-state.ts:112-124). So the 5m line shows the 5m time and the 1h line the 1h time, not a merged value. Approximations: (a) when a 1h entry is warm, a read is unattributed, so the 5m entry can read earlier than it really is (cache-state.ts:80); this errs toward showing cold. (b) `at` is the hook's clock time, not the server's write time (keepalive.ts:113-114, register.tsx:921). (c) The 1h refresh on a 1h ping is undocumented, so the ledger moves only on a 1h write in the ping (cache-state.ts:85-89, LLD OQ2 at docs/specs/keepalive-cache-status.lld.md:198).

4. Gaps. (a) Code already reads both fields. (b) Real gap: `seedFromTranscript` runs only while `hasMain` is false (keepalive.ts:132-133). Once any main entry exists, a later main write that carries no split is dropped (cache-state.ts:60-64) and never reseeds from the transcript. The ledger can then show a track as expired while the cache is warm. The spec's D2a text says "the transcript seed covers it", which is only true before the first entry. (c) Subagent usage is not yet forwarded: register.tsx:917 still filters `!e.agentId`, despite spec D2 (line 89). So the `unknown` path is currently unreachable from real sessions. This matches ITEM-034 being pending, but the README and status line should not be read as covering subagents yet.
