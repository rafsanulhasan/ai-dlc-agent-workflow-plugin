**R1: YES, but only through a hook the lens does not use yet. Confidence Medium.**
- The d.ts `session.send` event (`claude-code.d.ts:4498-4509`, type at :12162-12191) fires "when a plain-text message is about to leave this conversation for another agent or session (the SendMessage tool, or `$.session.send`)".
- Its input carries `to: string`, `text`, `origin.kind: 'model'` for the model's own SendMessage, and `agentId?`, the sender's loop id. `agentId` is absent for the main conversation. :12186-12188 says "a message between two subagents carries the sender's id here".
- So from and to are both present: `from = e.agentId ?? 'main'`, `to` = a name, an agent id or a `from` address (:12164-12166).
- `register.tsx` registers `tool.call` (:2909), `turn.step` and `turn.complete`. It has no `session.send` hook. The 3 "SendMessage" hits in `register.tsx` are not an edge source.
- `tool.call` with `agentId` (:197-203) probably also carries the SendMessage call. I did not verify its input shape. `session.send` is the typed route.
- `session.receive` (:12010-12038) gives `origin.teammate`, the sender's name, with `isVerified`. It is the receiver-side proof.
- Pane-hosted teammates (own terminal pane) run no loop here: no events and no `agentId` (:132, :573). Their sends are not seen by `session.send`.
- Whether `session.send` fires for in-process teammate to teammate sends is only implied by "any loop". Spike it live before relying on it.

**R2: record names give typed from/to pairs. They give no edge between teammates today.**
- `parseRecordName` (`lens.ts:1922`) gives `from`, `to`, `code` and `kind`. Sample from this run: `16.1.1-software-architect-to-system-engineer`, `16.1.2-system-engineer-to-brutal-critique`, `14.1.16.1-product-owner-to-product-manager`, `14.1.16.2-product-owner-to-requirement-analyst`, `14.1.16.l1-orchestrator-to-team`, `14.1.16.l1-team-to-orchestrator`. So sa to se, se to bc and po to pm/ra are derivable by name.
- `stepTrees` (`lens.ts:1978-2011`) hangs nodes by code prefix (`parentCode`). `from` is stored on the node but is never drawn as an edge. `drawChart` draws only parent to child (spawn tree, loop arrows are two-way).
- So `16.1.1` (sa to se) and `16.1.2` (se to bc) both hang under `16.1`. There is no sa to se to bc chain.
- `14.1.16.l1-orchestrator-to-team` makes a pseudo-agent `team`. `typeOfWorker` (:2078) turns it into the type `ai-dlc:team`, which is no real agent. The `to:` frontmatter lists the members: `team (po, pm, ra, bc)`.
- Messages that leave no record: clarify questions and answers, `SendMessage` pings, status chatter and "done" notices. Only a hook (R1) sees these.
- Record names alone cannot show message counts or direction of conversation, only written hand-offs.

**R3: three identifier spaces. Joining them is not free.**
- Record names use agent type ids: `software-architect`.
- Record frontmatter uses `from: software-architect (sa)` and `to: team (po, pm, ra, bc)`. The short name in brackets is free text.
- Runtime uses the teammate name, `sa`, which is what SendMessage addresses (`AgentInfo.name`, :177-183; `AgentTeammateRecord.name`, :595-599). It takes a suffix like `scout-2` when the name is taken.
- `AgentInfo.id` is the loop `agentId`. `teammateId` is `<name>@<team>` and no event carries it (:139-142).
- `AgentInfo.type` is the spawn type, `teammate` when none (:149-154). The lens already uses `type === 'teammate'` (`lens.ts:1447`).
- `session.send` gives `to` as a name or id. Mapping a name to an agent type needs `agent.list()` (`name` to `type`) or `AgentTeammateRecord.agent_type` (:607).
- A teammate spawned with no type has no agent type. Its record names would still use the type id the writer picked.
- The edge key therefore needs a join: runtime name to agent id to record type id.

**R4: layout is a tree and cannot place cross-edges.**
- `layout` (`lens.ts:503-536`) places by spawn depth (`depthOf`). Each level wraps at `size.perRow` (default 8, setting). Width is `widest * col`, with col 120 and row 96.
- A five-teammate team is one row of 5 under the lead. Sibling two-way edges are not drawn, so they would cross or overlap the row without any routing.
- Five teammates give 10 pairs, so up to 20 directed message edges. Record edges are fewer, about 1 per hand-off.
- Needs a separate edge style for messages versus records, count badges instead of one arrow per message, and a toggle. This is my reading, not a source fact.

**Draft ACs**
- AC-1: a team-mode step chart draws a directed edge from sender to receiver for every hand-off or hand-back record whose from and to are both team members.
- AC-2: message edges come from a `session.send` hook, de-duplicated into one edge per ordered pair with a count.
- AC-3: message edges and record edges are visually distinct and individually toggleable.
- AC-4: runtime names map to agent types so message and record edges meet on the same node.
- AC-5: with no `session.send` data (pane-hosted teammate, hook off) the chart falls back to record edges only and says so.
- AC-6: the pseudo-agent `team` is drawn as a group or expanded to its listed members, not as `ai-dlc:team`.

**Open questions for the human**
- Is a count-per-pair edge enough, or must the chart show message order and text?
- Is stored message text acceptable? `session.send` includes `text`, which may be private. Counts only is the safer default.
- Are pane-hosted teammates in scope? They are invisible to the hook.
- Should `team` records expand to members, or show the group as one node?
- An empirical spike on `session.send` for in-process teammate to teammate, and the `tool.call` SendMessage payload, is needed for a hard R1 ruling.
