**W3: overlapping pings.** There was no existing in-flight guard, so I added three module flags:
- `pressing` covers a press from its first read to its redraw. A second press during that time does nothing (debug log `keepalive: ping press ignored: a ping is already under way`).
- `pingBusy` is set by `pingReply` before its first await, so a press and the command can never both ping.
- `pingsOut` is a counter in `ping()` (its body moved to `pingOut`), so scheduled track pings count too. A press or a command run while any ping is out pings nothing. The command replies `keepalive: a ping is already under way; nothing more pinged; <keep lines>`.
- A track's scheduled ping is not held back by a press ping. That case was outside the brief's scope.

**W4: `keepWarmToFile` and `maxPings`.** I chose a smallest fix based on ownership:
- A `maxPings` is "owned" when its value in that file's env equals `max(1, pingsWithin(file's keepWarmFor, pingEvery in force))`, which is the pair this command or the configure skill writes.
- **Set:** writes `keepWarmFor`. It writes `maxPings` (the pings the new time allows at the `pingEvery` in force) only if the file's value is owned, or if the limit in force is below what the new time needs. Otherwise `maxPings` is left alone.
- **Clear:** removes `keepWarmFor`, and removes `maxPings` only if it is owned. A kept value is named in the reply.
- The reply now lists every `…_MAX_PINGS` written, removed or kept.
- To pass the resolved vars to `teamRecord`, `writeJsonSection` now accepts a function of the current section and returns `{ problem } | { vars }`. `writeEnv` returns `vars`.
- **Remaining gap:** a later change to `pingEvery` at another level is not re-synced. A cap that is too high is harmless, because the keep-warm time ends the track first.
- This needed a skill text change, which I made: the `--for` row of `skills/cache-keepalive-configure/SKILL.md`.
