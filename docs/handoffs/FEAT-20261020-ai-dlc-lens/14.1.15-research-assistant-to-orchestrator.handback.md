**2. Constraints in this repo**

- The chat-card entry point is `ui.render` on `ToolUse` at `register.tsx:3198`. It falls back to the native row on error (`register.tsx:3209`). This is the lens's existing precedent for drawing next to chat content.
- The engine exposes an `AssistantMessage` component with a `text` prop (`claude-code.d.ts:10320`). It also exposes `Markdown`, which "draws as it draws an assistant reply's text: its own renderer, links, tables, fences" (`claude-code.d.ts:5871`). Open: whether a hook can swap one fence inside a reply for a picture while keeping the rest. The types show whole-message replacement, not in-fence substitution.
- Svg is absent on the terminal surface (`claude-code.d.ts:3924`, "the one without Svg"). The terminal path is `Image` with `{png}` bytes, bounded at 2 MiB (handback, check E3).
- Svg cap: `SVG_CAP = 131072` (`avatar.ts:13`). `flowchartSvg` drops avatar images largest-first to stay under it (`lens.ts:548-565`). Spike E2: one oversize Svg refuses the whole pane tree. Spike E1: 27 Svg elements were accepted, each up to 130,734 characters, with `<style>`, `<marker>` and `data:` image hrefs passed through unchanged. Scrub on the surface is unverified (checks 17-22 still `needs-human`).
- Trust and network: `classify` (`avatar.ts:205-216`) accepts only `data:…;base64` URIs and file paths. Any other scheme (`http:`, `https:`, `file:`) is refused and never fetched. Paths are trusted only inside `~/.claude.json` folders (`register.tsx:595-604`, `avatar.ts:242`, `avatar.ts:258`), and the real path is checked. Images are sniffed by magic bytes, size-capped and type-checked (`avatar.ts:219-225`).
- Settings pattern: `settings.ts:65` for `avatarImageMaxBytes`, and the `AI_DLC_LENS_*` env and `.ai-dlc/lens.json` keys (per CLAUDE.md's description).
- THIRD_PARTY_NOTICES.md format (`THIRD_PARTY_NOTICES.md:1-60`): one `## <upstream>` heading per upstream; one prose paragraph with a link; the full licence text in a ```text block; a NOTICE block if the upstream has one. CLAUDE.md requires each new upstream there, and each hooks folder to keep an `ATTRIBUTION.md`.

**3. Feasibility and privacy**

- Mermaid offline in-process: feasible. mermaid-inline shows the approach (beautiful-mermaid plus resvg-js, a local Node process). Its output is PNG, so an Svg chart would need a different layout path. Mermaid.js in a webview is not available in the Svg-only lens (no webview element is documented in the d.ts I read).
- LaTeX and math: MathJax 3 or 4 bundled, with no TeX needed for math (claude-latex, figures). Diagram-from-LaTeX needs a TeX install (`latex`, `dvisvgm`).
- PlantUML: needs Java plus `plantuml.jar` (local), or a remote server. None of the six mods does this. Licence of PlantUML not checked.
- Privacy: none of the six sends diagram text off the machine. diagram-pane makes Haiku model calls; `/show-me` sends the text to the model only by its command. A remote renderer would send diagram source (which can contain internal architecture) to a third party. Requirement: default offline, remote only by explicit opt-in.

**4. Draft requirements and ACs**

Scope: the `diagramming` submodule, Claude Code only, in `plugins/claude/ai-dlc-lens/`. Mermaid first, then PlantUML and LaTeX as separate increments.

- R1 Detection: diagram fences in an assistant reply are found by language tag (`mermaid`, `plantuml`, `puml`, `latex`/`tikz`).
- R2 Rendering: offline by default. No network call except where the user opts in.
- R3 Surface: the terminal uses `Image` PNG; VS Code and desktop use Svg. Each surface falls back to the source text.
- R4 Trust: no remote fetch of any image or diagram source. Local tools run only from a configured path.
- R5 Limits: each chart stays under 131,072 Svg characters; a larger chart falls back to source.
- Numbered ACs:
  1. AC-1: An assistant reply with a closed `mermaid` fence shows a picture beneath it on the terminal and VS Code, with the fence source still visible.
  2. AC-2: An unclosed or streaming fence is not rendered until it closes.
  3. AC-3: No outbound network request is made while rendering with the default settings (verified by a capture of the test session).
  4. AC-4: A diagram over the Svg cap, or a render error, shows the source and a one-line reason; the rest of the reply is unaffected.
  5. AC-5: A `plantuml` fence renders only when a local `java` and jar are configured; otherwise the source is shown with a notice.
  6. AC-6: A remote renderer is off by default and needs an explicit setting; when enabled, the lens shows the destination host before sending.
  7. AC-7: Each reused idea or code from a reference mod has its entry in `THIRD_PARTY_NOTICES.md` and its licence text.
  8. AC-8: `plugin validate --strict` and `plugin test` pass for `ai-dlc-lens`.

**5. SA/SE UML diagrams from the planning phase**

Architecture narratives and specs are files, not chat. The software-architect's UML would arrive as chat replies (AssistantMessage) or as Read results of `docs/architecture/**/*.md` (ToolResult). Open: whether the submodule should also draw fences from Read results of planning artifacts. That path needs the same trust check as avatars.

## Open Questions
1. Allow remote rendering (kroki, plantuml.com) at all? My recommendation is no by default, opt-in only, with the host shown first.
2. Which languages first? My recommendation is Mermaid, then LaTeX math (no TeX needed), then PlantUML via a local Java.
3. PlantUML: is a local Java install acceptable as a dependency? PlantUML's licence still needs checking.
4. Should the submodule also draw fences from `Read` results of planning artifacts (SA/SE UML in `docs/`)?
5. Can an `AssistantMessage` hook replace one fence inside a reply while keeping the rest of the text? The types do not show it. Needs a spike.
6. Terminal: PNG via `Image` only, so Mermaid needs a PNG rasteriser (resvg-js). Is that dependency acceptable for the plugin?
7. Apache-2.0 for `figures`: does it have a NOTICE file to reproduce? Not checked.
8. A deeper source read of the six repos (hook usage, exact code reuse) is worth a re-run on Sonnet if the design depends on exact behaviour.
