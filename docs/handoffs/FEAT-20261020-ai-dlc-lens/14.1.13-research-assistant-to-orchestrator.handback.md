# Research Findings: module / submodule / feature / integration taxonomy

## Question
What must change, and where the taxonomy should live, so that a generic, per-repository taxonomy (module > submodule > feature, plus cross-cutting integrations) can feed handoff run states, task-triage breakdowns and ai-dlc-lens flowcharts. Scope is current codebase behaviour only (read-only, plan mode). No web sources. No time sensitivity.

## Method
Read `handoff/SKILL.md` (Naming 24–74, Run state 254–364, Session handoff 389+), `workflow/templates/workflow.json` and `workflow.schema.json`, `workflow.mjs` (validate), `product-planning/SKILL.md`, `task-triage/SKILL.md` (grep hits only), `ai-dlc-lens/hooks/lens.ts`, and `auto-handoff/run.ts`. ## Findings

### 1. Surfaces that would have to know the taxonomy
- **Run folder path.** `docs/handoffs/{LIFECYCLE}-{YYYYMMDD}-{feature-slug}/`, one folder per run (`handoff/SKILL.md:26`). A nested tree (`<epic>/<sprint>/<feature>/<run>/`) is cut at the first placeholder segment by `handoffsRoot` (`auto-handoff/run.ts:56-73`), and the run scan is one level deep, `docs/handoffs/*/` (`SKILL.md:288`). Nested runs would not be found.
- **Run identity.** The run id is the last path segment, lowercased (`lens.ts:986-990`). The same slug under two sprints collides.
- **Run state front matter.** Fixed keys: run, work-item, version, previous, pair, status, lifecycle, mode, current-stage, owner, session, branch, commit, last-record, parent, updated (`SKILL.md:296-313`). No module or feature keys. `parent:` already nests runs (`lens.ts:1392-1414`). Readers ignore unknown keys (`lens.ts:1195`, `run.ts:85-109`), so new keys are non-breaking, but nothing writes or checks them.
- **Stage codes.** A feature is root N, phases N.1–N.5 (`SKILL.md:36-50`). No module is encoded; a taxonomy would be metadata only.
- **Auto-handoff run selection.** `pickRun` filters on branch, `status: active` and session lineage only (`run.ts:162-171`). Two unclaimed active runs on one branch return none. A module filter would be a new input.
- **Workflow file.** `artifacts` has seven fixed keys (`workflow.json:609-617`). The schema sets `additionalProperties: false` (`workflow.schema.json:162`) and a required list (`:163`). `workflow.mjs` checks top-level keys against `TOP` (`:156`) and artifact keys against `ARTIFACTS` (`:155`, `:436-439`). A new section needs a `TOP` entry, a schema property and a validate rule.
- **Backlog item.** Fields: Type, Priority, Status, Milestone, Added, Parent, Agent Chain (`product-planning/SKILL.md:70-83`). Milestone is the only grouping field and the closest thing to a sprint. There is no module field.
- **task-triage output.** The breakdown's run line says "joins run X as a new feature / follow-up under step F" (`task-triage/SKILL.md:132`). No per-item module field.
- **Lens parser.** `parseRun` reads stage rows and the Features table (`lens.ts:1192-1245`). The Sessions column is not read (no match in `lens.ts`). A chart is one feature step (`lens.ts:2091`, `:2169`). Grouping by module needs a new read.
- **Migration.** Existing folders are flat (for example `docs/handoffs/FEAT-20261020-ai-dlc-lens/`). Precedents: the `merged-from-<run>.md` redirect (`lens.ts:1417-1430`) and the Old steps renumber map (`lens.ts:1262-1303`). Nothing else moves a folder and keeps its records valid.

### 2. Where the taxonomy lives
- **A. `taxonomy` section in `workflow.json`.** One file, checked by the existing `validate` and Stop gate. Costs: it is lifecycle and routing config, changed through `agent-manager`, and needs schema, `TOP` and upgrade changes.
- **B. Separate `.ai-dlc/taxonomy.json`** with its own schema and a validate subcommand. Clean separation, but one more file to gate, upgrade and document.
- **C. Per-item front matter** in product-tree or backlog files (`module:`, `submodule:`, `feature:`, `integrations: [...]`). Each item owns its placement and multi-valued integrations are easy. Costs: no central list, so names are not validated.
- **Suggested split (for the caller to decide):** declare the tree once (A or B, validated), assign items with C, copy the keys into run state front matter at Confirm.

**Epic/sprint versus module: a conflict.**
- The human's product tree is agile (epic > sprint > feature > story > task). The taxonomy is product/code (module > submodule > feature, with integrations cutting across).
- A folder gives a feature one parent. Integration2 spans AI-DLC and AI-DLC-LENS, so one folder cannot hold both parents.
- "One run state per wave (planning/design/build/final)" conflicts with Naming: one folder per run, with phases N.1–N.5 already covering planning, build, test, review and docs (`SKILL.md:26`, `:43-50`), and versions are per session, not per wave (`:258-264`).

### 3. Sessions and run steps
- The Stages table has a Sessions column (`SKILL.md:338`), filled as free text. `parseStages` reads only Step, Status, Handoff and Handback (`run.ts:184-203`). The lens does not read it.
- Run-level `session:` records only the last writer (`SKILL.md:286`, `:307`). Auto-handoff chains are tracked by session lineage (`run.ts:152-171`). The session handoff is a scratch file, never committed (`SKILL.md:401`).
- The lens ties a live agent to a step by its brief's record path (`lens.ts:2182-2186`), not by session id.
- **Missing:** a machine-readable list of chain id, session ids and step codes per stage. Without it, the flowcharts cannot map one run across several auto-handed-off sessions (Integration2 (iii)).

### 4. Draft requirements and acceptance criteria
- **R1.** Each repository declares modules, submodules, features and integrations with stable ids, in one validated file. The file is optional.
- **R2.** Each run and backlog item has one module and one submodule, and zero or more integrations.
- **R3.** The plugin ships the schema and validator only; no repo-specific names.
- **AC-1.** `validate` rejects unknown keys, duplicate ids, and items naming an undeclared module or submodule.
- **AC-2.** With no taxonomy file, `validate` and every reader behave exactly as today.
- **AC-3.** Run state gains `module`, `submodule`, `feature` and `integrations` keys at Confirm. Readers ignore them when absent.
- **AC-4.** Each task-triage row carries module, submodule and integrations; a row without them is marked needs-info.
- **AC-5.** `pickRun` can filter by module or submodule. With no filter it returns exactly what it returns today.
- **AC-6.** Run discovery finds runs at any depth, or the tree is rejected. Run ids are unique across the tree.
- **AC-7.** The lens groups charts by module, submodule and integration from run state keys, unchanged when absent.
- **AC-8.** Integration2 (ii) and (iii): a flowchart can be built from another module's records, selected by integration id, and one run spanning several sessions maps to several flowcharts.
- **AC-9.** Flat folders stay readable. Any move leaves `merged-from-<old>.md` and renames no record.
- **AC-10.** The Stages table gains a machine-readable session column (chain id and session ids per row), parsed by `run.ts` and the lens.
- **AC-11.** Integration1 (auto-handoff and keep-alive) is listed under both submodules.
