## Change 1 — feature-root numbering (human, 2026-10-24)
"Step Root For each feature. try to find what which root the base steps actually belong to and move the base step as a substep of that parent and rename accordingly" … "keep the rule in mind". In a run, **each feature is one top-level step (root)**; every hand-off done for it is a sub-step of that root: its build, docs, tests, reviews, fix rounds, **and later follow-ups to the same feature** (a follow-up request about feature 8 goes under 8 as `8.7`, never a new top-level number). Only a new feature takes the next free top-level number. Reviews and critiques never take a top-level number of their own. Reconcile this with what feature 11 wrote: today a related request joins the run "as its next top-level steps"; under the new rule, a related request that is a follow-up to an existing feature goes under that feature's root, and a related request that is a new feature takes the next free top-level number. Keep what still holds (`.0.n` before Confirm, the cut-off for runs that never confirm, `parent:`, loop rounds, the "next free number" definition). ## Change 2 — versioned run state (human, 2026-10-24)
"every run should create a new run state. it should never replace the previous run state. starting with run.v1.md, run.v2.md and so on" — clarified: **a new version per session**; "the auto handoff sessions must not be counted as a separate session. its part of the parent session"; "but it can deprecate any old one". So:
- A run's state lives in `run.v1.md`, `run.v2.md`, …, in the run folder. A session that starts or resumes the run writes a new version (copying the latest version's content forward, then updating it); within that session it updates that version in place. A session seeded by an automatic handoff continues its parent session's version (no new file).
- A newer version may mark an older version deprecated (for example `status: deprecated` / `superseded-by: run.v3.md` in its front matter), but never deletes or overwrites it.
- Everything that reads or writes "the run state" or `run.md` must follow: the handoff skill (*Run state*, *Session handoff*, resuming, "Committing it", the template), the orchestrator's Run Loop (steps 1, 7–11, AAW step 0), the automatic handoff's session-handoff brief text if it names `run.md` (`hooks/auto-handoff/`: check; if it is code, say so and return a request rather than editing it), `skills/workflow` if `artifacts.handoffs` docs name `run.md`, and the docs-status rule if it names `run.md` (the rule is agent-manager-owned: `docs-rules` templates and this repo's copies). The lens is being updated separately (8.6.1.l1) to read the highest non-deprecated `run.vN.md`, falling back to `run.md`.
- Say how existing runs with a `run.md` are treated (read as version 0, or renamed to `run.v1.md` on their next session); the orchestrator will rename this run's `run.md` to `run.v1.md` once the rule and the lens support it.
