**(a) Does a hook see subagent usage per response? POSSIBLE (partly).**
- `turn.step` is the per-response event. Its input has `agentId?` ("the loop the request is made in: a subagent's id... absent on main", d.ts:14376). Its result carries `usage: TurnUsage | null` (d.ts:14443).
- `TurnUsage` is typed as `ModelUsage & {model}`: only `input_tokens`, `output_tokens`, `cache_read_input_tokens` and `cache_creation_input_tokens` (d.ts:6605-6627, 14569).
- The typed usage has no `cache_creation` 5m/1h split. The module already reads the split at runtime from the raw usage object (`config.ts:383-389`), so it may be present but is untyped. UNKNOWN until observed.
- Caveat in the d.ts: a subagent spawned by a plugin's own `$.agent.spawn` "steps past that hook". Model-spawned subagents are visible.
- `turn.complete` also fires for subagents with `agentId`; `register.tsx:799` already notes this.
- The `!e.agentId` filters (`register.tsx:881`) are the module's own choice, not an API limit.
- `agent.list()` gives the id, type, status, `teammateId` and the SendMessage name (d.ts:122-180). Classic `SubagentStart` and `SubagentStop` carry `agent_id`, and `SubagentStop` also carries `agent_transcript_path`.

**(b) Can a module ping a subagent's or teammate's cache prefix? IMPOSSIBLE with the documented API; a workaround is unknown.**
- The main-loop ping is `$.model.fork({prompt})` (`keepalive.ts:444-453`). `ModelForkRequest` is `{prompt}` only (d.ts:6522-6532). It forks "the session's OWN transcript as the main thread last sent it" (d.ts:2672-2678), with no `agentId` parameter.
- `$.model.complete` has no history or tools, so it cannot reuse an agent's prefix. It could only warm a different, self-built prefix.
- `$.session.send({to:{agentId}, text})` (d.ts:2936-2948) does reach an agent. It queues a peer message that makes the agent run a real turn, with side effects and output. It would warm that agent's cache as a by-product, but it is not a minimal, tool-less ping. A teammate waiting for work would wake and respond. Cost and behaviour are unverified.
- `$.session.messages({agentId})` reads an agent's transcript (d.ts:11775-11851). It denies for a pane-hosted teammate, and for a finished agent with no saved transcript.
- To replay the prefix yourself you would need the agent's system prompt, tools and model. The d.ts does not expose these, so this is not feasible.

**(c) Can subagent transcripts be the usage source? POSSIBLE for observation, not for pinging.**
- `SubagentStop` gives `agent_transcript_path`. `$.session.messages({agentId, as:'api'})` returns the agent's messages.
- The module's own `splitFromTranscript` (`keepalive.ts:78-91`) skips `isSidechain: true` rows, so it reads only main-thread rows. Subagent files would need the opposite filter.
- Transcripts record usage only after a response, so they are post-hoc. `turn.step` with `agentId` is the live source.
- I did not confirm the `~/.claude/projects/<proj>/<session>/subagents/agent-*.jsonl` layout on disk or whether those rows carry `cache_creation`. UNKNOWN; I did not open one.

**Design implication for ITEM-034**
1. Observing is feasible. Hook `turn.step` and `turn.complete` where `agentId` is set, and record per-agent last usage, model and time. This gives a cache-warmth estimate (the split from the raw usage if present). Do not rely on the typed `TurnUsage` for the 5m/1h split. Use the `SubagentStop` transcript as a fallback.
2. Pinging is the blocker. No documented call replays a subagent's prefix. G1 Q34 allowed the fallback only if G2 proves it impossible. By the d.ts, a true minimal ping is impossible. `$.session.send` to the agent is the only candidate, and it needs an empirical spike (does a waiting teammate reply, at what cost, does the cache read hit?) before it can be designed on.
3. Recommended ITEM-034 shape: ship observation plus warmth reporting (a "subagent cache cold in N min" line) now. Make `session.send` ping a flagged experiment behind a spike, not a promise.
