## 1. docs/specs/diagramming.spec.md: REVISE

### Blocker
1. D5 (:97) — "Image links and `http(s)` includes are removed … by the lens's existing `classify` rule (`avatar.ts`)". `classify` (`avatar.ts:205-216`) classifies one whole `avatarImage.<agent>` setting value as a data URI, a file path or a refused URL scheme. It does not scan or edit text, so it cannot clean a diagram source. The stories cite the same function (AC-20.5.3), so the error came from there, but a design that points at a function that does something else leaves AC-20.5.3 unbuildable. → Design a new pure `sanitiseSource(kind, source)` in `diagram.ts` and name what it removes per kind: PlantUML `!include`/`!includeurl`/`!import` of a URL, `<img:http…>`, `sprite` URLs and `!theme … from <url>`; Mermaid `click … href` and image `<img src>`/`![](url)` labels; math: `\href`, `\url`, `\includegraphics`. For each, say removed silently or removed with a one-line reason. Add pure-seam rows for every pattern, and say the stories' reference to `classify` is corrected by this spec.

### Major
1. D3 (:84-88) — a PNG rasteriser for diagrams that hold text needs fonts. A WebAssembly resvg has no system fonts, so labels would render blank unless a font is bundled; a bundled font adds a licence (for example OFL) and size. The spike did not cover it. → Make "fonts for the rasteriser" an explicit question for ITEM-053.a (what font, its licence, its size) with a notice entry in D8, and a fallback when text cannot render (show `alt` and a reason). Unverified from here: route the resvg-wasm font behaviour to `research-assistant`.
2. D1 (:69-73) and OQ1 — the default is in-place placement, but the G1-approved ACs 20.1.1-20.1.3, 20.2.1 and 20.3.1 say "beneath the reply". The spec says "one wording per answer" but gives neither. G2 cannot choose between texts it has not seen. → Write both wordings of those five ACs in the spec (A: right after its own fence; B: beneath the reply), marked pending OQ1, and say which test rows change.
3. D3 (:90) — the async fallback ("first render shows the source and `rendering…`, the picture on the next render") needs a trigger for the next render (`$.ui.invalidate`). The LLD "fixes one of two" is too open for a core behaviour. → State the trigger and the guarantee: a render never blocks longer than N ms, and a completed render invalidates the message once. Name N as an LLD parameter.
4. D3 (:81) — beautiful-mermaid draws six kinds; other Mermaid kinds (gantt, pie, mindmap, journey…) are not in the floor. The fallback "renderer error" (D7) covers them by accident. → Say an unsupported kind gives the source and the reason `mermaid diagram type "<x>" is not supported offline`, and add a test row.
5. D8 (:117-119) — the stories' AC-20.7.1 lists diagram-pane, claude-latex, show-me, archpane and mermaid-inline. The spec names only mermaid-inline, LaTeX Inline and claude-code-figures. → Say that no code or idea of diagram-pane, show-me or archpane is reused, hence no entry, and that "claude-latex" is replaced by "LaTeX Inline" (spike), as the stories' wording says "actually reused".

### Minor
1. D6 (:106) `diagramPlantuml` default `true` "takes effect only with a jar" and AC-20.3.2 shows a configure notice when no jar; with the default on, every PlantUML fence of a user with no jar shows that notice. Say that is intended, or show it once per session.
2. D5 (:96) "no code opens a socket": the PlantUML jar is a user program and may; state that the offline guarantee covers the lens's code and bundles, and the jar is the user's trust decision (path trust, D6).
3. Open question OQ3 (vendoring size) needs a number threshold for "accept" (for example the plugin stays under N MB); otherwise G2 cannot decide.
