Q2 Cross-plugin shared state
- `$.store` is the plugin's own key-value store, saved as a JSON file of that plugin under `~/.claude/plugins/store/`. It is shared by all sessions on the machine, capped at 4 MiB, and `get/set/delete/keys` have no namespace argument — https://code.claude.com/docs/en/plugins/mods/interface#keep-state; d.ts "This plugin's own key-value store"
- No documented way for one plugin to read another's `$.store`. The only route is reading the store's JSON file directly with `$.fs.read`. That is unconfirmed: the file's exact name and format are undocumented, and I found no sandbox statement either way.
- Do not couple the two plugins to a file name and format that is undocumented.
- `$.tool.register` and `$.tool.call` are the supported cross-mod channel. A registered tool is named `mcp__<plugin>__<name>`. `$.tool.call` is "the same call the engine makes for the model's tool calls" and rejects when no tool has that name. It does not say whether another plugin's tool can be called — https://code.claude.com/docs/en/plugins/mods/api#add-a-tool; d.ts offset 300000-400000. Unconfirmed in practice; needs a spike.
- Other documented channels: `$.session.send`/`session.receive` (messages between sessions or agents) and `$.fs` writes to an agreed path.
- `$.fs.write` is not atomic (a reader can see a partly written file). Keep data that several sessions write in `$.store` — https://code.claude.com/docs/en/plugins/mods/reference#mods-api-methods
- A keep-alive module living inside the ai-dlc hooks module can expose its state through a `$.tool.register` tool or a store key. ai-dlc-lens could read it through `$.tool.call`, which is the cleanest path if the spike works.
- A plugin's `ui.render` hook can wrap another mod's output with `next(e)`, but the mods API has no method that reads another mod's state — https://code.claude.com/docs/en/plugins/mods/interface#respond-to-presses-and-typing

Q4 agentId / parentAgentId and caller to callee
- `agent.spawn` (`AgentSpawnInput`) carries `parentAgentId` ("the id of the loop the spawn happens in"), `subagentType`, `description`, `prompt`, `model`, `name`, `background`, `fork`, `cwd`, `tool_use_id`. `e.isTeammate` is `true` for a teammate — d.ts offset 0-100000; https://code.claude.com/docs/en/plugins/mods/reference#subagents
- `$.agent.list()` returns `AgentInfo` with `id`, `type`, `description`, `status`, `name`, `parentId` and `spawnedBy`. `parentId` is "the id of the subagent whose loop spawned it; absent when the main loop". `type` is `teammate` for an in-process teammate. `status` is one of `pending | running | waiting | idle | completed | failed | killed`, where `idle` and `waiting` need v2.1.289 or later — d.ts offset 0-100000; reference#mods-api-methods
- Caller to callee edges come from `$.agent.list()` (`parentId`) or `agent.spawn` (`parentAgentId`). `spawnedBy` means something different from `parentId`, but its wording was cut off in my read.
- `e.agentId` is set on `tool.check` for a call made by a subagent or an in-process teammate, and absent for the main conversation — https://code.claude.com/docs/en/plugins/mods/reference#agent-and-organization-fields-on-toolcheck (v2.1.290 or later)
- `tool.call`, `turn.step` and `turn.complete` carry `agentId` for subagent loops; an agent's id is "the same string its loop's `tool.call` events carry".
- `session.send` to a teammate uses `{ agentId }` from `$.agent.list()`.
- There is no `parentAgentId` on `tool.call`. A mod must join `agent.spawn` or `$.agent.list()` records to those events.

Q5 `$.session.usage()`
- It returns `{ startedAt, context, rateLimits, cost }`, where `context` is `{ tokens, window, percent }` and `rateLimits` is a list of `{ kind, percentUsed, resetsAt }` — reference#mods-api-methods; d.ts offset 300000
- The d.ts argument form is `$.session.usage({ breakdown, columns })` with `UsageUnit = 'context' | 'rateLimits' | 'cost'`. The docs state no per-agent scope, so treat it as session or main-conversation only. What `breakdown` and `columns` do is not confirmed from the text I read.
- I found no per-agent context-size API. The nearest per-agent signal is `turn.step` usage per `agentId`: `input_tokens + cache_read + cache_creation` approximates that agent's context fill, but it is a derived figure, not a documented one. `e.messageCount` on `turn.step` also carries `agentId`.
- `session.measure` fires "after each turn, and when a plan limit's percent used changes" and is the push alternative to polling `$.session.usage()`.

Q6 `$.process.run` and `$.fs`
- `$.process.run(argv)` takes an argument vector and runs no shell. It returns `{ exitCode, stdout, stderr }`, defaults to a 30 s timeout (10 min max), and rejects if the program cannot start or times out. `cwd` is relative to the session or absolute — https://code.claude.com/docs/en/plugins/mods/api#reach-files-processes-and-the-network; d.ts offset 200000
- I found no Windows-specific statement, so Windows behaviour is unconfirmed. The existing ai-dlc module shells out to `sh`, `tail`, `tailscale` and `git` through it — plugins/claude/ai-dlc/hooks/auto-handoff/register.tsx:206,223; keepalive/keepalive.ts:90. Whether those run on Windows is not evidenced there. Use `['git', ...]` and `['node', ...]` rather than `sh`/`tail` to be safe. A spike on Windows is needed.
- `$.fs.read`, `$.fs.list`, `$.fs.exists` and `$.fs.stat` take a relative path (under the session cwd, or the subagent's) or an absolute path "used as given". "Where one may go is an `fs.*` hook's to say" — d.ts offset 100000. So reads outside the cwd, such as `~/.claude`, are allowed unless another mod's hook refuses (managed or org mods can).
- `$.fs.stat` mentions `~` as a spelling it cannot resolve, so expand `~` yourself and do not pass it to `$.fs.*`.
- The module itself has no Node APIs, timers or direct file access. Everything goes through `$` — https://code.claude.com/docs/en/plugins/mods/api#reach-files-processes-and-the-network
- `$.fs.read` and `$.fs.write` are capped at 4 MiB per file, so a large subagent jsonl cannot be read whole. Read it in parts through `$.process.run` with `tail -c` or `node -e` (the keep-alive module does this), or use the events. A `$.process.run` call can also be refused by org/managed mods.
- `$.session.messages()` returns the newest 4,096 entries as `{ role, text, toolUses }`. I found no per-agent field, so it is main-session only.
