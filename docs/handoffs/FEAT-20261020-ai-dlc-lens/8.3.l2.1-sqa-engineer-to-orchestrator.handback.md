**Findings** (behaviour I pinned; I changed no product code):
1. `composeCodeMaps` does not chain inside one map. `{a: b, b: c}` stays as is, so `a` resolves to `b`, and if only `c` is on disk, `a` is not found. Chaining happens only across maps (`[{a: b}, {b: c}]` gives `a -> c`). Probably fine, since a single file's map is one renaming, but a hand-written file that lists a chain will not resolve it.
2. A cycle across maps collapses to a self-map: `[{a: b}, {b: a}]` gives `{a: a, b: a}`. This is harmless, but it is pinned.
3. Open question 1 (an unlisted code that is a map key, with the mapped record listed): the brief is drawn at the mapped record. This looks right for stale codes. The only risk is a fresh brief that reuses an old code and has no file yet while the mapped record exists. I would accept it.
4. Open question 2 (a map entry whose record has a different sender or receiver): the brief keeps its own code, unchecked under a current root and `'gone'` under any other. This looks right, because drawing it at another agent's record would be wrong.
5. A `.md` source with a header row but no rule row below it yields `{}`. An indented table is ignored. Neither is a bug.
6. The in-lens tests have no way to read the `runs` atom: the test client has no `$.state`, and intercepting `state.set` broke the `ifVersion` writes. I therefore assert through the chart instead (which disk node a live brief takes over).
7. The phase file maps through the `renames` prefix first (`30.1` becomes `8.6.1`, then the map), so `30.1` is not itself a key of it. That is why my first in-lens attempt, which assumed it was a key, failed.
