- `keepalive <track>: off`: default (:52), reset at each turn start (:632-635); a Stop with no background tasks leaves it unchanged (:658-661). This is the state for every turn without background work.
- `off (disabled)`: track's `enabled` is false (:688).

- `armed, N task(s), warm until HH:MM, ping k/m, keep warm …, stop by …`: a Stop with background tasks, the track's split > 0 (:685-696, runningLine :505-506).

2. **Root-cause candidates for "5m always off"**, ranked:
- (1, most likely, the wording problem) `off` at :635 and :52 is the default for any turn without background tasks, and the no-task Stop path never writes the line (:658-661). So `5m: off` shows on almost every turn regardless of cache state. Tests only cover the armed case (keepalive.test.ts:447-458).
- (2, likely) The split is last-write-wins and sticky. `noteUsage` only records a nonzero split from main-loop responses (register.tsx:881-883 with `!e.agentId`; keepalive.ts:94-97). `lastSplit` is cleared only at :603 and :721, not at turn start (:632-651), and `splitFromTranscript` skips sidechain rows (:84-85). So subagent 5m writes never count, and one main-loop 1h write turns 5m off until the next main 5m write.
- (3, plausible) The main loop itself writes only 1h. Local transcripts show both TTLs in use: 5m rows in many files (21,660 matches across 566 files under `C:\Users\rafsa\.claude\projects\`), 1h rows in 195 files (8,820). Most 5m matches are in subagent files, which the code excludes. Not yet checked: whether a top-level (non-subagent) session has 5m rows with `ephemeral_5m_input_tokens` > 0.
- "Not true" most likely means 5m writes do exist: in subagent transcripts (excluded by design, :84-85, register.tsx:881) and possibly in main-session rows the sticky `lastSplit` (:65, :96) does not show.
- Confidence: Medium. Candidate 1 is confirmed by the code; 2 and 3 need the main-session transcript check.

3. **Anthropic facts** (fetched from https://platform.claude.com/docs/en/build-with-claude/prompt-caching via WebFetch, a summarizing fetch; spot-check the quotes before relying on them)
- Writes: 5m = 1.25x base input; 1h = 2x; read = 0.1x. Per-model reads: Fable 5.1 and Mythos 5.1 at 0.025x, Opus 5.5 and Sonnet 5.5 at 0.05x (same URL, pricing note).
- Refresh: the default 5m entry is refreshed on each use at no extra cost; the lifetime is counted from the start of the request. The page does not state the refresh rule for the 1h TTL (same URL, "Cache lifetime").
- Usage fields: `cache_creation_input_tokens` equals the sum of `cache_creation.ephemeral_5m_input_tokens` and `ephemeral_1h_input_tokens`; `input_tokens` is only the uncached tail (same URL, usage section). The lens split logic depends on this.
- Invalidation: changes to tools invalidate everything; system changes invalidate system and messages; message changes invalidate messages; the prefix order is tools, system, messages (same URL, invalidation table). Compaction and `/clear` create a new prefix, so they start a new write; I did not verify these two against the page.
- Subagents: the page does not cover them. Repo claim at README:150 (teammates use 5m unless `subagentPromptCacheTtl` is `1h`) is unverified against Anthropic's docs.
- Each turn re-writes only the new suffix past the last breakpoint; cached prefix reads are billed at 0.1x. Each request's cost is its reads plus writes plus uncached input plus output.

4. **Lens cost and savings** (`plugins/claude/ai-dlc-lens/hooks/lens.ts`)
- Writes are priced at the 5m rate only (lens.ts:330-336, :311-316; `rate` defaults to `'5m'`), even though the usage carries the split.
