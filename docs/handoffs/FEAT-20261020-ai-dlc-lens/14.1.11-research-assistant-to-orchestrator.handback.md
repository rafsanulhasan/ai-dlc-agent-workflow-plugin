# Research Findings: auto-handoff session naming (FEAT-20261020-ai-dlc-lens, root 16)

Plan mode: read-only. Nothing written, and no memory saved.

## Question
Human rule: the new handoff session is named Session 2 when the current session is the main session. Otherwise it takes the current session's number plus 1 (session 2 gives 3). Does the code do this, and where does it not?

## Method
Read `config.ts:405-423`, `register.tsx:330-460`, `:945-1040`, the tests at `auto-handoff.test.tsx:660-714` and `:1751-1829`, `config.test.ts:105-120`, `types/index.d.ts`, `ATTRIBUTION.md:138-177`, the README and the schema copies. No runtime run. The mods engine type package is not in the repo, so engine signatures are unverified.

## Findings

**1. Current algorithm**
- Lineage read: `storedLineage` returns undefined on any store error (`register.tsx:345-354`). `lineageOf` uses memory for `seededSession`, else the store (`:357-359`).
- Old-session handoff (`handoff`, `:427-449`): `depth = own ? own.depth : 1` (`:429`). `name = own.baseName ?? baseName(title) ?? short(id)` (`:436`). The old session is renamed `sessionName(prefix, name, depth)` only when `renameSessions && depth !== undefined` (`:449`). `renameOld` skips when the title already equals the name, and skips when `/rename` is not listed (`:398-405`).
- Seeded session (`:986-1008`): `prior = own ? own.depth : 1` (`:996-997`). `depth = prior+1`, `baseName` carried (`:998`). Stored as `lineage:<new>` (`:999`). The name is returned as `sessionTitle` only when depth is defined (`:1004-1008`, `:1036`).
- Branches:
  - Lineage with depth N: old keeps N, new is N+1. Matches the human's example (`:998`; test `:1752-1764`).
  - No lineage: depth 1. Old is renamed `Session 1`, new is `Session 2`. Matches the rule, but "no lineage" is also what a non-main session looks like (see 3).
  - Lineage without depth (seeded before depth existed): depth undefined. No rename, no new name. Pinned by test `:693-705`.
  - Store read error: treated as no lineage (`:351-352`).
  - Title with prefix and number: `baseName` strips it (`config.ts:420-422`).
  - Title with prefix but no number: regex needs `(Session \d+)$`, so the prefixed string is returned whole and nested into the new name (`config.ts:420`). Not tested (`config.test.ts:113-119`).
  - Title absent: short id (`:436`; test `:1785-1790`).
  - Title source: `titles` map, set from SessionStart and UserPromptSubmit `session_title` (`:959`, `:971`), then transcript `custom-title`, then `ai-title` (`:384-389`, `config.ts:425-`).

**2. Main-session detection**
- Today: absence of a `lineage:<id>` record (`:427-429`, `:996-997`).
- Nothing in the session API marks main. Title numbers are the only in-band depth signal besides the store.
- APIs the module uses: `$.session.id/cwd/messages/usage/version/surfaces`, `$.store.get/set`, `$.command.list/run`, `$.fs`, `$.model.complete`, `$.clock.after`, and classic SessionStart / UserPromptSubmit inputs (`session_title`) with a `sessionTitle` answer.
- `plugins/claude/ai-dlc/types/index.d.ts:1-41` declares only the `$.state` keepalive type. The engine's full types are not in the repo, so exact signatures are unverified. Confidence on this section: Medium.

**3. Where the rule and the code disagree**
- A. Title "Session 7", no lineage (store lost, or resumed under a new id): code renames the old session to `Session 1` (overwriting 7) and names the new one `Session 2`. Rule: 8. Pinned by test `:1766-1774`.
- B. Lineage without depth, title "(Session 3)": nothing is named. Rule: 4.
- C. Store read error (`register.tsx:351-352`), title "(Session 3)": treated as main, new is `Session 2`. Rule: 4.
- D. Title "[ai-dlc:auto-handoff]: X" with no number: name becomes `[ai-dlc:auto-handoff]: [ai-dlc:auto-handoff]: X (Session 1)`. Rule: no nesting.
- E. Prefix changed mid-chain (`AI_DLC_AUTO_HANDOFF_SESSION_NAME_PREFIX`): `baseName` only strips the current prefix (`config.ts:420`), so old-prefix titles are not unwrapped.
- F. Old-session rename uses lineage depth (`:449`), not the session's displayed number. A session titled 7 with lineage 2 is renamed 2.
- G. The 2 to 3 example works while lineage is intact (`:998`). The reported symptom therefore most likely comes from A, B, C or resume. I could not reproduce it from code alone.
- H. Earlier wording in `docs/handoffs/AAW-20261022-auto-handoff-chain/run.md:19` asks for `[ai-dlc:auto-handoff]:{previous session name}: Session N`. The code carries the original base name instead. Confirm which one is wanted (see 6).

**4. Draft requirements and acceptance criteria**

Requirement: the new session's number is the current session's number plus 1. The current session's number comes from its lineage depth, else its title number. The main session is the one with neither.

- AC-1 Given a fresh session with no lineage and no chain title, when it hands off, then the old session is `P: base (Session 1)` and the new one `P: base (Session 2)`.
- AC-2 Given lineage depth N, when it hands off, then the old session keeps N and the new one is N+1 (existing behaviour, must not regress).
- AC-3 Given no lineage and title `P: base (Session 7)`, when it hands off, then the old session is not renamed to 1 and the new one is `(Session 8)`.
- AC-4 Given lineage without depth and title `(Session 3)`, when it hands off, then the new one is `(Session 4)`, and depth is recorded from now on.
- AC-5 Given a store read error and title `(Session 3)`, when it hands off, then the new one is `(Session 4)` and the fallback is logged.
- AC-6 Given title `P: base` with no number, when it names a chain, then the name is `P: base (Session 1)`, not nested.
- AC-7 Given a prefix change, when a session carries a title with the old prefix, then the old prefix is stripped (scope to be decided, see 6).
- AC-8 Given a resumed seeded session with the same id, when it hands off, then depth comes from the store and the name is unchanged.
- AC-9 Given two chains with the same base name, when each hands off, then each numbers independently. (Open: are the names distinguishable?)
- AC-10 Given `/rename` is unavailable, when a session hands off, then the new one still gets N+1 (existing test `:1792-1800`).
- AC-11 A chain number never decreases or repeats within a chain.

**6. Open questions for the human**

- Two chains with the same base name: is that acceptable?
