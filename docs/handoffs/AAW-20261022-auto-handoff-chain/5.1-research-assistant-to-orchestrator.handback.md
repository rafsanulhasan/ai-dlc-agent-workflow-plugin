## Q1. Does the engine expose workspace trust, and where is hasTrustDialogAccepted stored?

**Answer:** No trust getter in the mod engine. The types have no workspace-trust field, method or input. Grep for trust, workspace, dialog and hasTrust in the 2.1.306 types found nothing on a `$` noun or hook input. The only "trusted source" hit (types :2060) is about managed settings and the organization policy, not the folder. Trust must be read from the file.

The store is `~/.claude.json`, key `projects["<path>"].hasTrustDialogAccepted` (boolean). The docs state this directly: "set `projects["<path>"].hasTrustDialogAccepted` to `true` in `~/.claude.json`, where `<path>` is the repository root, or the folder itself outside a repository" [1]. Scope rules from the same section [1]:
- In a git repo, trust is keyed on the repository root and covers the whole repo, except a nested git repo such as a submodule, which has its own trust.
- In a worktree, the key is the main checkout's root.
- Outside a repo, the key is the start directory, and it covers its subdirectories except a nested git repo.
- Started in the home directory, trust is held for the session only and not written to disk.
- The dialog shows only in interactive sessions. `claude -p` and the SDK never show it.

Local shape (redacted, key names and counts only, no values or paths quoted): `C:\Users\<REDACTED>\.claude.json` contains 13 `hasTrustDialogAccepted` booleans under project entries. The project keys are Windows absolute paths. I could not reliably tell from grep counts whether the separator is `\` or `/`, so that is not established.

Windows normalisation: the docs say nothing about how `<path>` is spelled on Windows (case, separators, drive letter). The matching rule has to be written defensively (see Q3).

Stability across versions: the docs name the key as the manual-trust mechanism, which is the strongest evidence it is a documented contract [1]. Community reports, which are unofficial, describe the flag not persisting after acceptance and the dialog re-firing for some projects [2][3][4]. Those reports conflict with the docs and I could not verify them.

Confidence:

## Q2. Do hooks or mods run in untrusted folders?

**Answer:** Settings-file hooks and the settings `env` block run before trust. The docs table "What runs before you trust a folder" marks "Hooks in settings files, the `env` block and helper commands" as "Used" in both the parent-folder-only column and the `claude -p`/SDK-never-trusted column [1]. Only `permissions.allow`, `additionalDirectories` and `headersHelper` are gated [1]. So the `AI_DLC_*` values in `.claude/settings.json` apply untrusted, as the human's decision assumes.

For the mod, the engine does not gate it on trust, and the repo file is not in that table. `.ai-dlc/auto-handoff.json` is a custom file the module reads itself, so no engine rule covers it. The module must enforce trust on that file. Historically, pre-v2.0.71 hooks ran before the dialog, and that was fixed [5][6].

Confidence: Medium-High. Official table, read from a fetched copy of the page. The mod-specific gap is my inference from the table not listing the repo file.
