# Findings (Question 3: the technical core)

- Primary docs say the API default TTL is 5 minutes, "refreshed for no additional cost each time the cached content is used". The lifetime is measured from the start of the request (platform.claude.com prompt-caching, "Cache lifetime"). The 1h option is `cache_control: {type: "ephemeral", ttl: "1h"}`.
- Prefix order is `tools`, then `system`, then `messages`. Cache hits "require 100 percent identical prompt segments... up to and including the block marked with cache control" (same page, "Cache prefix order" and "Exact matching").
- Claude Code: the main conversation's default TTL is 1h on a subscription within plan usage, and 5m on an API key, cloud provider, or once usage credits are used. Other requests (subagents, workflows, forks, compaction, session titles) default to 5m (code.claude.com/docs/en/prompt-caching, "Which TTL each request gets").
- Settings: `promptCacheTtl` (main; scope "Any file"; `5m`|`1h`) and `subagentPromptCacheTtl` (other requests). Env vars `CLAUDE_CODE_PROMPT_CACHE_TTL` and `CLAUDE_CODE_SUBAGENT_PROMPT_CACHE_TTL`. Precedence: `FORCE_PROMPT_CACHING_5M`, then the bucket env var, then the bucket setting, then subagent `cacheTtl` frontmatter, then `ENABLE_PROMPT_CACHING_1H`, then the bucket default. Requires Claude Code v2.1.242+ (code.claude.com/docs/en/settings-reference; code.claude.com/docs/en/prompt-caching).
- The docs describe "Project context" (CLAUDE.md, memory) as changing "after /clear or /compact", and say /clear resets that layer. They do not say how /clear interacts with the cache. The cache is "effectively scoped to one machine and directory". Sequential sessions share the prefix only if the git status snapshot taken at startup matches (code.claude.com/docs/en/prompt-caching, "Cache scope").
- Fork semantics: "A fork... inherits the parent's system prompt, tools, and conversation history exactly, so its first request reads the parent's cache" (same page, "Subagents and the cache").
- Consequences (inference from the above, Medium):
  a. After /clear and the seed, the old conversation is gone, so its messages cannot be read from cache. Only the shared prefix (system, tools, CLAUDE.md, auto memory) can hit, and only if its entry is still live and the cwd and git snapshot match.
  b. The gap between the old session's last request and the seed is the handoff's own duration, since the brief is written by Haiku (a separate request) before /clear. For that gap the shared prefix is probably still warm without any ping, because a hit refreshes the TTL. The ping matters only for long gaps, which is its designed use during background tasks.
  c. Keep-alive arms only on `classic.Stop` with background tasks (`register.ts:216`). A seeded session starts with none, so the mod is not armed in the new session.
  d. The ping is a fork, so it falls in the "everything else" bucket and is 5m by default even on a subscription. The mod's 1h assumption (`register.ts:7-8`) therefore holds only if `subagentPromptCacheTtl` is `1h`, or if a 5m-bucket read does not shorten a 1h entry. The docs do not say which. Unverified.
- Verification method from the docs: `claude -p "hello" --output-format json` and read `usage.cache_creation.ephemeral_1h_input_tokens` vs `ephemeral_5m_input_tokens`. `/usage` shows a `Prompt cache (main)` line (v2.1.251+).
- Unverified third-party claim (a claudeissues report) that 2.1.218+ stopped requesting 1h for the main conversation. The official docs describe per-bucket defaults and do not mention it. Treat it as unverified: https://claudeissues.com/issue/84253-bug-claude-code-2-1-218-no-longer-requests-1h-prompt-cache-ttl-every-5-min-gap-f
- Context7 was not used: no context7 tool is loaded in this agent. Sources are the Anthropic and Claude Code docs above.
- Confidence: High on the documented TTL, refresh and prefix rules. Medium on what /clear does to the shared prefix. Low on whether a 5m-bucket fork read resets a 1h entry's lifetime.

# Findings (Question 4: integration points, code read)

- Pre-clear: auto-handoff queues `/clear` at `plugins/claude/ai-dlc/hooks/auto-handoff/register.tsx:502-509`, after `fired:` is set. Stop the keep-alive timers before this point, and also on `classic.SessionStart` with `source === 'clear'` (`register.tsx:905-924`).
- Timers are module-level and process-wide (`register.ts:18`). A timer armed in the old session survives `/clear`. Its callback calls `$.model.fork`, which targets the current session. `stop()` runs only on `turn.start`, `classic.Stop`, or overage. So a timer can fire between `/clear` and the seed. Make the state per session id.
- Compaction: `compactOnCap` (`register.ts:176-180`) can compact while auto-handoff has a pending `/clear`. Gate it on auto-handoff's pending/in-flight state.
- Module variables survive `/clear` but not hot reload. Auto-handoff already keeps lineage in `$.store` for this reason (`register.tsx:50-60`). Keep-alive's per-session overrides already use the store (`register.ts:30-33`). Follow the same pattern.
- Tool gate: I did not verify one. My grep was truncated by unrelated matches. Re-check before design.
- Command naming under ai-dlc is unverified. Whether `$.command.register` in a second module keeps the name `/keepalive` or gets a prefix depends on the engine; I found no evidence either way.
- Confidence: High on the code points cited. Medium on the timer-fires-after-clear risk (reading of the code, not run).
